## 1. 停工位举证:两边现在各自怎么跑

停工位口径要的是 live,不是读代码得出的推断。基线 `fb58034` 上两端各跑了一遍**真代码**:

- **CLI 那一侧**跑的是真的 `node cli.js exec episode.produce`。上游端点由一个只实现
  `/api/state`、`/api/wf/smart-review`、`/api/llm/chat`、`/api/volc/{image,video}`、`/api/ffmpeg/compose`
  的桩顶着(评审分数由桩给,`lastReview` 按服务端那份合并口径写回),CLI 与产品代码一个字没改;
  重抽次数按桩收到的 `POST /api/volc/video` 现数。
- **浏览器那一侧**把真的 `js/produce.js` 装进最小 `window` 壳里跑 `SB.autoSmartReview`,
  `Review.reviewShot` / `SBGen.createShotVideo` 打桩计数,回执原样取 `dock.say` 的每一行。

### 1.1 问题一:浏览器审片「再生成」按镜还是按集?计数器挂哪?

**按镜**。`js/produce.js` 是 `for (const s of targets)` 外层、`for (let attempt = 0; attempt <= maxRetry && !pass; attempt++)` 内层,
`attempt` 每换一镜归零——**计数器挂在镜上**,既不挂集也不挂项目,而且只活在这一次调用的内存里,
不写 `ep`、不落库,再点一次「一键成片」重新从 0 开始。

到顶时的回执(live 原文,`sbConfig.maxRetry = 5`、两镜恒 5.0 分):

```
达标线 7.0 分 · 不达标先按问题修订提示词再重生成(每镜最多 5 次)· 超限转人工处理 · 评审期间可正常操作页面
❌ 5.0 分,已达最大重试,转人工处理
━━ 完成:达标 0 镜 · 自动重生成 10 次 · 待人工 2 镜 ━━
返回 {"pass":0,"retry":10,"manual":2}
```

**回执说的与它做的对得上**:说「每镜最多 5 次」,实测逐镜 `{"s1":5,"s2":5}`。

### 1.2 问题二:CLI 一轮整集还是可按 `shotIds` 子集?共用同一条 limit 吗?

**整集分轮,而每一轮里真的是子集**。`cli.js` 是 `for (let attempt = 1; attempt <= maxRetry && low.length; attempt++)`,
轮内 `episode.generateVideos` 与 `episode.smartReview` 都带 `shotIds: fix.revised`。
三镜夹具(镜 2 一审 8.5 分达标,镜 1/3 恒 5.0 分,`sbConfig.maxRetry = 3`)live:

```
低分 2 镜,按审片意见修订重抽(第 1/3 轮)…   批量生成:2 镜待处理
低分 2 镜,按审片意见修订重抽(第 2/3 轮)…   批量生成:2 镜待处理
低分 2 镜,按审片意见修订重抽(第 3/3 轮)…   批量生成:2 镜待处理
每批评审的镜号:[[1,2,3],[1,3],[1,3],[1,3]]    重抽总次数:6
低分 2 镜(1镜5分、3镜5分),修订重抽后仍不达标,质量闸门已阻断合成(riskyCompose 可放行)
```

首轮整集三镜,其后三轮只碰 `[1,3]`——达标那一镜一分钱不再花。**limit 也确实是同一条**:
两端都调 `Domain.reviseRetryLimit`,那道 `1..5` 钳位与缺省 2 在 `js/domain.js` 里只此一份(基线 SK-25 那条契约守着)。

### 1.3 问题三:同一组低分镜,两边会不会一边还能跑、一边已到顶

**会,而且两个方向都会。** 同一份夹具、同一个 `ep.sbConfig.maxRetry`、命令入参都不给 `maxRetry`,
基线 `fb58034` 上现数的逐镜重抽次数:

| `ep.sbConfig.maxRetry` | 浏览器 逐镜重抽 | CLI 逐镜重抽 | CLI 轮次日志的分母 |
| --- | --- | --- | --- |
| 5 | **5** | **2** | 第 x/**2** 轮 |
| 2 | 2 | 2 | 第 x/2 轮 |
| 1 | **1** | **2** | 第 x/**2** 轮 |
| 5(另给 `--args '{"maxRetry":5}'`) | 5 | 5 | 第 x/5 轮 |

配 5 时 CLI 两轮就到顶,浏览器还能再跑三次;**配 1 时反过来**——浏览器一次就转人工,
CLI 照跑两轮,每镜多烧一次真钱(`Domain` 自己那段注释写着上限存在的理由就是「每一轮都真花钱」)。
最后一行是判据:命令入参显式给 5,CLI 立刻跟浏览器一样跑满 5——**差的不是循环形状,是喂给同一个函数的候选**。

```js
js/commands.js:354  ep.sbConfig.maxRetry = Domain.reviseRetryLimit(args.maxRetry, ep.sbConfig.maxRetry);
cli.js:1205         const maxRetry     = Domain.reviseRetryLimit(args.maxRetry);      ← 分集配置那一档没喂
```

现场求值(同一集、`sbConfig.maxRetry = 5`):浏览器那条链回 **5**,CLI 那条链回 **2**。

## 2. 停工位成立,但成立的是口径面——循环形状一字不动

任务口径给了两条出路,本槽走的是第二条,理由是第 1 节那三张实测把它们分得很开:

**形状不同 ≠ 次数不同源。** 两端调度粒度确实不同构(一个逐镜深挖、一个整集分轮),
但**逐镜可重抽次数由同一个上限定死**,故同一份夹具下两端的花销逐格相同。修完之后同一个三镜夹具:

| | 重抽总次数 | 逐镜 | 评审次数 | 达标镜 |
| --- | --- | --- | --- | --- |
| 浏览器 `autoSmartReview` | 6 | `{s1:3, s3:3}` | 9 | 1 |
| CLI `exec episode.produce` | 6 | `{s1:3, s3:3}` | 9 | 1 |

排法不同、回执说法不同(一边「每镜最多 N 次」、一边「第 x/N 轮」),而**钱一分不差**。
把 CLI 改成按镜、或把浏览器改成整集,收不到任何一格上的差——那两件事要动的是浏览器侧进度面板语义
与逐镜计费节奏,属产品口径,产品没下令前不做。

**成立的那一面是「limit 两套解析链」。** 两端都调同一个函数不等于同源:同源要求的是
**同一份数据在两端解析出同一个数**,而基线上同一集解析出 5 和 2 两个数。
`Domain` 那段注释登记的候选链原话就是「(如 命令入参 → 分集 sbConfig)」,浏览器两档都喂、CLI 只喂第一档,
于是用户在分集「参数配置」面板上调过的次数在 headless 那一侧读不到。

## 3. 改的是一行实参

```js
// 候选链与浏览器命令层逐档同序:命令入参 → 分集 sbConfig → 缺省。少给一档不是"少读一个可选值",
// 而是同一集在两端解析出两个上限——用户在参数配置面板调过的次数在 headless 这一侧读不到,
// 调低时这边多烧几轮真钱,调高时这边先到顶(浏览器还能再跑)。
const maxRetry = Domain.reviseRetryLimit(args.maxRetry, ep.sbConfig && ep.sbConfig.maxRetry);
```

`ep` 是这一行上面 `execCtx` 已经取好的服务端快照,不多一次请求;`&&` 那道防空是因为
CLI 拿到的是裸快照,而命令层那一侧的 `ep` 已由 `ensureSBCfg` 兜过底——**两端的取法本就不同,
逐字相同反倒会逼出一份假的统一**,故第 4 节那条契约判的是档位与次序,不是字面。

**有意不在实参里写 `args.maxRetry || ep.sbConfig.maxRetry`**:`||` 会把"读不出来"(`'abc'`、`{}`)
与 0 并成同一件事,而"哪个候选算数"这一段的口径归 `Domain` 那一份——测里有一格
(`args.maxRetry = 'abc'`、`sbConfig.maxRetry = 3`)专门量这个差:择先链回 3、`||` 回 2。

修完的 live(与第 1.3 节同一张表同一份夹具):`maxRetry=5` → 逐镜 5(两端);`maxRetry=1` → 逐镜 1(两端)。
CLI 的轮次日志分母随分集配置走(`第 1/5 轮`、`第 1/1 轮`),循环还是那个循环。

## 4. 两条判据,各守一面

| 套件 | 用例 | 守什么 |
| --- | --- | --- |
| `domain` | `reviseRetryLimit 两端候选链同序:同一集同一份 sbConfig,浏览器与 CLI 的 produce 解析出同一个上限` | 行为面:把两端 produce 里那一行的**实参原样取出来**,在同一份夹具上各求一次值逐格对账 |
| `contract` | `修订轮次的候选链只登记一处:Domain 写明「命令入参 → 分集 sbConfig」,两端 produce 都得把两档喂进去` | 取数口:登记面那段注释还在,两个消费点的档位/次序/不许 `||` 并档 |

**行为面那条有意不在测里重写一遍候选链**——那就是第三份口径,改真链时它不会跟着走。
判据把 `js/commands.js` 与 `cli.js` 里 produce 那一段切出来(按各自的下一处注册点收边,
别的命令那处同名调用不算),抠出 `Domain.reviseRetryLimit(` 的括号配对实参,再在同一份 `{args, ep}` 上求值。
取数口失效(锚点找不到、段内没有这个调用)先红在自己那句上,不留成恒真。

**这两条不是一条的子集,分工由 M2 量了出来**:两端一起退化成只读命令入参时,
行为面那条的**相等断言全绿**(两边都回缺省 2,确实相等),红的是同一条用例末尾那三句反向钉住
(`sbConfig` 那一档要真读得到)与契约那条。相等这件事两侧一起改照样成立,是这一目录反复量到的老坑
(W164 的 M5、W170 那次「值一样也是第二份投影」同形),故反向那三句与源级那条都不能省。

**两条都不登记进 `GUARD_TOPICS`**(任务口径);SK-25 那条既有的契约照旧守着形状面,见 M6/M8。

## 6. 仍欠(如实留着,本槽不动)

- **形状面仍不同构**,如第 2 节所判:浏览器逐镜排、CLI 整集分轮,回执说法不同。SK-25 的仍欠段按新实况改写过——
  改前那句「同一份次数口径在两端数的不是同一件事」现已与实测不符(第 2 节那张表两端逐格相同),
  改后点名的是**调度粒度与回执说法**,`autoSmartReview` / `逐镜` 两个锚点原样留着(基线那条契约仍钉着它们)。
- **写回不对称**:浏览器命令层把解析结果写回 `ep.sbConfig.maxRetry`(它是 `autoSmartReview` 唯一的读处,
  写回是把入参递下去的通道),CLI 只读不写。于是「浏览器带 `--maxRetry 4` 跑过一轮」会改变此后两端的缺省档,
  而「CLI 带 `--args maxRetry:4` 跑过一轮」不会。本槽只收读侧那条链,写侧多一次落盘属另一件事,不顺手做。
- **两端的计数器都不落库**:`attempt` / 轮次都只活在那一次调用的内存里,重跑即从 0 开始。
  这一面两端一致,不是缺陷,记在这里是因为第 1.1 节问到"计数器挂在哪"——答案是挂在这一次调用上。
- **`episode.smartReview` 单独调用时不吃 `args.maxRetry`**:两端都只读 `ep.sbConfig`(`maxRetry` 只登记在
  `episode.produce` 的参数面上),这一面两端同样一致,故不属本槽的口径题。
