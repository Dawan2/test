# Agent 业务流分析与编剧/导演类 skill 前沿案例参考(2026-08)

> 性质:**参考分析文档**,不改业务代码。结论供筛选,未经确认不落地。
> 范围:①梳理本平台 Agent 业务流(侧栏虎鲸元 Agent / 专家工坊与雇佣 / cli.js / mcp.js / wf-core / prompts / knowledge / domain / gsettings / 导演助手 / 导演设定注入),指出可优化点并按优先级排序;②对编剧/导演类 skill 做多源检索,给出 2022–2026 可核验的前沿系统与一线实践案例。

---

## 一、结论摘要

1. **本平台 Agent 层的功能面已对齐(部分超出)一线实践的结构**:分层生成(剧本→理解→场次节拍→分镜表)、多角色评审(五角色评审 + 修订环)、多方案并行择优、主体库/@引用/首尾帧链、命令注册表 + 结构化回执 + 自修复轮、CLI/MCP 机读入口——这些正是 2024–2026 学术系统与商业产品的共性机制。
2. **主要差距不在功能面,而在贯通面**,与 AGENTS.md 的发展重点一致。按优先级:
   - G1 专家方法论断层:雇佣专家的 persona 只进对话助手,不进智能分镜/理解/审片工作流(双端一致地不注入);
   - G2 「审→改→重抽→复审」闭环只在浏览器 autoSmartReview,服务端 `/api/wf/smart-review` 与 CLI `episode.produce` 只有质量闸门没有修订重抽环;
   - G3 虎鲸对话 Agent 编排(路由→回复→ops→自修复→纪要)仍在浏览器,服务端化 `/api/wf/agent` 既是 README 已声明的计费根治路径,也能让 CLI/MCP 获得对话式 Agent 能力;
   - G4 用户个性化记忆(agentMemory)未被工作流层与 CLI/MCP 消费;
   - G5 命令注册表覆盖面止步分集主线,主体/项目域无命令,且 README 与代码存在两处漂移。
3. 前沿案例的共同骨架是「**分工角色 + 显式评审环 + 编排者 + 共享状态**」;skill 注册与编排范式(渐进披露、按需加载)对本平台的知识库注入与专家 skill 结构有直接参考价值,列为可延后项。

## 二、Agent 业务流全景

### 2.1 用户意图入口(六类)

| 入口 | 载体 | 进入方式 |
|---|---|---|
| 集级导演助手 | `js/agent.js`(分集工作区右栏) | 自然语言 + 快捷指令 + 情境 chips + 事件续谈卡 |
| 全局虎鲸元 Agent | `js/agent-global.js`(右侧抽屉) | 自然语言 → `routeIntent` 轻量 LLM 意图路由到 7 个板块 Agent(导演/剧本/主体/分集/分镜/生成/成片,`AGENT_BOARDS`) |
| 板块协作 | 制片页「智能体分工」`openBoard` | 带板块人设 + 板块记忆锁定进入 |
| 纯本地推导入口 | `stateDigest` 系(agent-ops.js) | 开场白 `openingLine`、情境 chips `dynamicChips`、下一步引导 `digestNote`——零 LLM 成本 |
| 事件驱动入口 | `js/bus.js` → `subscribeBus` → `pushEvent` | 批量出片/审片/合成/拉片完成后推可操作事件卡 |
| 外部 Agent | `cli.js`(exec/workflow,语义 exit code)、`mcp.js`(29 工具 + resources + prompts)、`Ctrl+K` 命令面板 | 机读 JSON,与 UI 同一命令层 |

### 2.2 专家/skill 的选择与人设解析链

- **风格专家雇佣**(`experts.js hireExpert`):写入 `settings.hiredExpert` + **导演设定五维**(`directorSetting` = 专家 dims)+ **提示词三件套**(tplImage/tplVideo/tplReview)。风格专家对生成主线的影响完全经由这三个落点传导。
- **功能专家板块雇佣**(`p.boards[key].expert`):persona 经 `boardExpertBlock` 注入板块 Agent 系统提示词;上游已定稿板块经 `upstreamFinal` 作为权威约束注入。
- **会话身份下拉**(`ep.agentPersonaId` / `AC.gPersonaId`):生效人设解析顺序 = **面板下拉 > 板块雇佣 > 全局雇佣 > 无**。
- **专家工坊**(`FORGE_SYS` 元智能体):对话式生成完整专家 skill JSON(name/role/kind/persona/dims/tpl),规范化后入 `customExperts`。
- **专家自进化**(`evolveExpert`):把 `agentMemory` 的用户纠正/偏好 LLM 蒸馏为 ≤4 条进化条款追加进 persona(仅自定义专家)。
- **双端单源**:预置专家注册表已下沉 `js/experts-data.js`(UMD),服务端 `/api/wf/*` 经 `projTypeOf` 推导解说/剧情模式。

### 2.3 提示词注入管线 —— 对话层

```
system = 基础人设(虎鲸导演助手/板块 Agent)
       + KB.block()          知识库三域压缩核心(编剧/导演/AI抽卡,~500 字)
       + persona 块           2.2 的解析链结果
       + memBlock(text,scope) 记忆召回(同板块 4 + 最近 3 + 关键词命中 3)
       + 协议块               ops 协议 + cmdProtocol(命令白名单,cmd-registry 单源)
                              + queryProtocol(10 类按需查询)
user   = 会话纪要(compactChat 蒸馏) + 最近 12 条
       + 剧本摘要 + compactShots(整镜截断)
       + focusBlock(工作台定位) + AgentRefs.block(📎 对象引用,活内容快照)
       + stateBlock(工作台实时状态:出片/失败/过期/审分/在飞)
       + 用户指令
```

### 2.4 提示词注入管线 —— 创作工作流层(wf-core 双端单源)

```
智能分镜 system = Prompts.get('sb.system', 覆盖表) + KB.DR_SHOT + KB.DR_AXIS
智能分镜 user   = buildSBUser(styleOf 画风·影调 + globalSetting + projType(专家推导)
                 + directorNote(导演设定五维) + conceptInject(构思定调) + langOf + genres
                 + 本集理解 undToText + SPLIT_RULES + PROMPT5 + 主体表(含形态全称)
                 + eventsText(事件图谱,sourceRev 判旧) + feedback(五角色评审修订意见) + 剧本)
审片 prompt     = KB.reviewBlock() + tplReview + directorNote + 三维评分 + 拆解规则检查
```

浏览器 `sb-llm/understanding/review` 与服务端 `/api/wf/*` 逐字节同源;环境差异(Store/settings/覆盖表)经 ctx 显式注入。**注意:专家 persona 不在此管线内(见 G1)。**

### 2.5 执行编排与回执闭环

- **ops 协议**:数据类(update/insert/delete/move/batch/beatupdate/sceneupdate/subject)、动作类(run:cmd+args,白名单 = `Commands.list()` 自动生成)、导航类(goto/select)。
- **分级审批**:read 直执 / edit 预览确认(自动模式直执) / edit-hi(删除)恒确认 / exec(run)恒确认且费用明示。
- **执行链**:`Commands.execute`(8 条领域命令,cmd-registry 三端单源)→ 结构化回执 `{ok,status,result,error,cost,next}` → `cmdDigest` 消化 + `next` 自驱 → **自修复轮** `selfFixRound`(step:'fix',≤2 轮,不另扣费)→ `verifyOps` 落数回读校验 → 冲突面板(发送时指纹基线 `detectConflicts`)→ `memRemember` 沉淀。
- **辅助环**:按需查询循环(≤2 轮,q1/q2 步骤槽位)、预排模式(参数表单确认后执行)、持久计划 Plans、问题中心 Issues 一键处置、发布门 Release 10G。

### 2.6 断点与状态闭环

- 计费五件套 + operationId 幂等 + 步骤槽位(route/q1/fix/und/genN/revN…)——一条消息/一次工作流只扣一次。
- jobs 任务中心断点续查、`workflow`/`episodeState` Domain 单源四态、`rev/contentRev/sourceRev/graphRev/inputHash/snapshotHash` 判旧链贯穿 理解→分镜→生成→审片→成片→发布门。
- 双向流动已有:审片 issues → `Review.optimizeShot` 修订提示词 → 重抽(浏览器);拉片建集 → 理解 → 分镜;分镜画面 → 存为主体形态/资产库反哺。

### 2.7 一图流(文字版)

```
用户意图 ──┬─ 集级助手 ─────────┐
           ├─ 虎鲸元Agent─routeIntent─→ 板块Agent(7)
           ├─ 情境chips/事件卡(本地推导,零LLM)      │
           └─ CLI / MCP / Ctrl+K ──────────────────┤
                                                    ▼
                人设解析链(下拉>板块雇佣>全局雇佣) + KB + 记忆 + 状态摘要 + 引用

                                                    ▼

                                                    ▼

                                                    ▼
        Domain 判旧链 + jobs 断点续查 + Issues/Plans/Release 状态闭环
```

## 三、可优化点(按优先级)

### 3.1 贯通类(建议优先)

**G1|专家方法论进创作工作流(高)**
现状:雇佣专家的 persona(创作原则文本,如打脸四步结构、旁白驱动叙事)只注入对话助手;智能分镜/本集理解/智能审片工作流的 system 恒为 `Prompts` 默认 + KB,专家只经 dims(五维)与 tpl 三件套间接传导。浏览器与服务端一致地不注入,属设计空档而非两端漂移。
影响:「专家雇佣」对产出的作用被截断在对话层——用户雇了导演,拆镜工作流却不知道该导演的叙事方法论。
落地方向:`wf-core` 已有 ctx 显式注入通道(directorNote 同款),补一个 `personaNote`(persona 截断 ≤200 字),浏览器从 `hiredExpert()`、服务端从 `st.hiredExpert + tree.customExperts` 取,双端同源;`experts-data.js` 已是 UMD,无新增依赖。改动面:wf-core.js + sb-llm/understanding/review 委托点 + server.js wf 端点各一行级。

**G2|审→改→重抽→复审闭环补齐 headless 链路(高)**
现状:浏览器 `autoSmartReview` 有完整质量闭环(不达标 → `Review.optimizeShot` 按 issues 修订提示词 → 重抽 → 复审,超限转人工);服务端 `/api/wf/smart-review` 只出报告;CLI `episode.produce` 的审片步只做低分阻断合成(质量闸门),无修订重抽环。
影响:外部 Agent/跑批走 CLI 时,主线「审片反哺生成」断在报告层,低分镜只能人工回 UI 处理。
落地方向(二选一):① CLI `episode.produce` 在 lowShots 非空时按 issues 调 LLM 修订提示词(llm.optimize)+ `episode.generateVideos --shotIds 子集` 重抽 + 复审,循环 ≤maxRetry(语义与浏览器 produce.js 完全同构);② 服务端 `/api/wf/smart-review` 增加 `optimize:true` 选项返回修订后提示词,由调用方决定是否重抽。①改动集中在 cli.js,不动服务端。

**G3|虎鲸对话 Agent 编排服务端化 `/api/wf/agent`(中高)**
现状:对话 Agent 的编排(routeIntent → 回复 → ops → 自修复 → 纪要蒸馏)在浏览器,经 `llm.agent` 步骤槽位计费;README 已如实记录 llm.* 同族标签价差残留,且十三轮评估结论是「根治只能靠服务端工作流端点接管提示词编排」。同时 CLI/MCP 只有命令面,没有对话面——外部 Agent 要获得虎鲸同等的 ops 协议/记忆/状态摘要能力只能自己拼。
落地方向:与二十一轮三条工作流同构——新端点接收 {pid,epid?,text,scope},服务端拼装 2.3 的注入管线(KB/persona/记忆/状态摘要均可从 state 树取),复用 wfLLM 步骤槽位(route/main/q1/q2/fix),返回 {reply,ops,receipts}。浏览器面板与 CLI 新命令 `agent`/MCP 工具同吃一个端点。改动量最大,建议在 G1/G2 之后。

**G4|个性化记忆的双端消费(中)**
现状:`agentMemory` 存 state 树(云同步没问题),KB 种子已双端(knowledge.js UMD);但服务端 wf 端点不注入记忆(智能分镜不知道用户沉淀的偏好与纠正),CLI/MCP 无 memory 读写命令。
落地方向:wf 端点按 scope 注入 top-N 记忆文本(与 `memRecall` 同算法,可下沉为 UMD 纯函数);CLI 补 `memory list/add` 两命令 + MCP 资源 `hujing://memory`。改动小,收益是「越用越懂你」贯通到全链路。

**G5|命令注册表覆盖面 + 文档漂移修正(中)**
现状:cmd-registry 8 条命令集中在分集主线;主体/项目域无领域命令,Agent/计划/问题中心的一键处置能力受限。两处漂移(见 3.3)。
落地方向:按需求补 2~3 条高频命令(如 subject.generateImage、project.extractSubjects),三端词表由注册表自动跟随;同步修正 README。

### 3.2 可延后

- **D1|板块 stage 与主线状态两套口径**:`upstreamFinal` 依赖 `p.boards[].stage` 手工定稿,与 `Domain.workflow` 是两套状态;可让 stage 默认值从 Domain 推导,手工定稿只做覆盖。
- **D2|意图路由降本**:`routeIntent` 每条消息一次 LLM 调用;可先按关键词/命令面本地预判,LLM 兜底。
- **D3|逐镜审片的上下文感知**:当前单镜评审是孤立的(整集共性汇总在后);可在单镜 review prompt 注入前后镜一行摘要,衔接类问题(跳切/景别不递进)判得更准。改动仅 wf-core buildReviewPrompt 一处。
- **D4|评审环引入辩论/仲裁式双席**:现有五角色评审是并列打分;关键分歧(如拆镜方案)可用两席辩论 + 一席仲裁,先做单点实验再定。
- **D5|连抽自动择优**:连抽 ×N 已有、审片已有,可串成「抽 N → 自动评 → 留最优」的可选开关;属新能力,不做主线贯通前不建议。
- **D6|专家 skill 三段式与按需注入**:FORGE_SYS 产出的专家是单段 persona;可演进为「名称+触发描述(常驻)/ 方法论正文(命中注入)/ 参考条目(按需)」三级结构,与 `KB.SECTIONS` 按名取用打通——对话上下文更省,专家可挂更长的方法论而不挤占 token。
- **D7|MCP 资源面补齐**:现有 4 个只读资源;可补 issues/release/memory 资源与「审片修复流程」prompt 模板。

### 3.3 文档与代码漂移(如实记录,本次不改代码)

1. README 发布门 G9 描述「fix 挂 `Commands.execute('subject.generateImage', …)` 一键补图」;实际 `release.js` G9 为导航类处置并在注释如实标注「无对应领域命令」。`subject.generateImage` 未在 commands.js 注册。应修 README 或补命令(归入 G5)。
2. `cli.js` `episode.produce` 头注释仍写「智能审片…CLI 侧该步如实标 skipped」;二十一轮后实际已走服务端真实评审 + 质量闸门,注释过时。

### 4.2 分案要点(结构化方式与评审环)

- **Dramatron**:证明「层级化 + 每层可编辑中间产物」是长剧本一致性的正解;15 位行业编剧/导演实测正反馈。本平台的 剧本→理解→场次节拍→文字分镜→分镜表 分层与逐层判旧(sourceRev 链)已同构,且多了「过期传播」这一层——结构上不落后。
- **Agents' Room**:编排者按叙事理论把写作拆给「冲突/人物/情节/背景」四类规划 Agent,产物写进共享 scratchpad 再交写作 Agent。启示在于**规划角色的分工粒度**(本平台功能专家已有钩子工程师/爽点架构师/结构医师/对白医生等同粒度角色,但它们只在对话层被动应答,没有被编排进「剧本生成」的固定流水线)。
- **HoLLMwood / FilmAgent**:显式 Writer↔Editor(或 Critique-Correct-Verify)评审环是产出质量的主要来源;FilmAgent 的消融实验表明,协作良好的多智能体(GPT-4o)可胜过更强的单模型(o1)。本平台五角色评审 + <90 分重拆 ≤2 轮已是同类机制;差距在 G2(headless 链路)与 D4(辩论式仲裁)。
- **IBSEN**:导演 Agent 的职责是「按目标重排剧情 + 调度演员」,人类介入时以目标为锚重规划——与本平台「持久计划 Plans + 冲突面板 + 确认闸」的人机协作语义一致。
- **MovieAgent / Anim-Director / VideoDirectorGPT**:导演 Agent 的关键产物是**结构化视频计划**(场景/实体/布局/一致性分组),而非自然语言描述——与本平台 canonical 生成请求(`buildVideoRequest` + shotRefImages 打标)同思路。
- **AniMaker**:两点值得注意:①把「抽卡」形式化为候选树搜索(MCTS-Gen),预算内择优;②评审(AniEval)**携带前后镜上下文**逐段打分。前者对应 D5,后者对应 D3,都是低成本可验证的单点。
- **SkyReels**:国内一线「一键成剧」平台形态,证明「剧本模型 + 分镜模型 + 主体定制 + 合成」的流水线产品成立;其分镜生成把剧本拆「全局(场景/景别/构图)+ 主体(角色/动作)」两路再汇集,与本平台「本集理解 + 主体表注入拆镜」两路合流的设计同构。
- **LTX Studio / 可灵**:商用侧的共性是**主体库为中心的一致性工程**(@引用、参考图绑定、首尾帧锚点、镜头内多镜切分)。本平台的主体/形态/@引用/镜头组/首尾帧链在功能面已覆盖;可灵的「单请求多分镜(multi_shot)+主体绑定 ≤3」提示了未来把「镜头组整组」压为单请求的可能性(依赖上游模型能力,暂观察)。

### 4.3 skill 注册与编排范式

- **Agent Skills(Anthropic,2025-10)**:skill = 目录 + SKILL.md;三级渐进披露(名称+触发描述常驻 ~100 token → 正文命中加载 <5k token → 脚本/参考文件按需读)。2025-12 成为开放标准。要点:**skill 的「何时用」描述与「怎么做」正文分离,靠触发描述做路由**。
- **MCP(2024-11 开源)**:工具/资源/提示三面协议。本平台 mcp.js 已实现三面(29 工具 + 4 资源 + 2 提示模板),接入形态与业界同步。
- 对本平台的映射:`prompts.js`(核心提示词注册表 + 覆盖表)、`knowledge.js`(KB.SECTIONS 按名取用)、`cmd-registry.js`(命令元数据三端单源)合起来就是本平台的 skill 注册层;当前差距是**注入策略是全量或关键词召回,而非「触发描述路由 + 正文按需」**(对应 D6)。
