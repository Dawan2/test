## 4. 四类冲突的解法

### 4.1 长行 README:取基线侧 + 按 word-diff 折回对侧增量

两份 README 里几条上千字的长行,每一槽都会撞。基线侧几乎总是超集(它含着前面所有槽的收敛),对侧只带自己那点增量,`git` 却只能整行二选一。沿用 W29 起的口径:

```
git diff --word-diff=porcelain --word-diff-regex='[^,。;:、()「」`]+' <分支base> <分支head> -- README.md
```

拿到对侧的**逐词增量**(本槽四次各 2–4 条),取基线侧那行,再把这几条按语义插回去。**不用 `git checkout --ours`**:那会把对侧增量整行丢掉,而且丢得无声无息;逐块择侧只负责去掉冲突标记,增量折回是单独一步、可逐条核对。

本槽折回的增量共 9 条,例如:`8 条注册表提示词` → `9 条` → `10 条`(两槽各加一条,数字要连着改两次而不是各改各的)、`w43` 往 `memory` 套件描述里插的「闭环结论回流」那段、`w44` 往 skill 索引句里插的「编排面已落地 N 条」那段。

### 4.2 折回之前先查:这条增量是不是已经自动合进来了

合 `w43` 时,`docs/skills-wave/README.md` 的两块冲突里没有 SK-26 那条摘要句,我据此**手写了一条**折进摘要区;下一次合 `w44` 时才看到——`w43` 自己的 SK-26 摘要句写在**非冲突区**,早就自动合进来了,同一件事因此在摘要区写了两遍。已在 `w44` 那次合并里把手写的那条撤掉,保留 `w43` 自己那条(更细、且是作者原话)。

> **口径**:折回对侧增量前,先在**整份文件**里搜一遍该增量的关键词,确认它不在非冲突区。冲突块只覆盖两侧改到同一行的部分,对侧在别处新增的整行(新 bullet、新表格行)是**自动合并**的——只看冲突块会漏判成「对侧这条没进来」,于是补写出第二份。

### 4.3 两条分支各清一条 `pending` 时,冲突两侧都不对

`tests/unit.js` 里有一条钉「剩余 `pending` 清单」的断言。基线侧(已含 `w43`)写的是:

```js
'SK-05:orchestrate', '剩余 pending 应只剩 SK-05 的编排面一条'
```

`w44` 侧写的是:

```js
'SK-26:orchestrate', '剩余 pending 应只剩 SK-26 的 orchestrate 一条'
```

两条**都不是并入后的实况**:`w43` 清掉 SK-26、`w44` 清掉 SK-05,两条都合进来之后短名单已经**一条 `pending` 都不剩**。取任一侧都会红,而且红得有误导性(看着像谁的功能没合进来)。按实况另写成空串,并把上方那段注释改成「编排面最后两条都已落地」的双向说明:

```js
assertEq(Skills.list().filter(s => s.pending.length).map(s => s.sk + ':' + s.pending.join('+')).join(','),
  '', '编排面两条落地后短名单应已无 pending');
```

> **口径**:「剩余清单」型断言(剩余 `pending`、剩余缺口、剩余余量)在多分支并入时是**必然要重写**的一类——两条分支各划掉清单里的一项,谁的字面都不等于并集的结果。判据是**并入后现跑一遍取实况**,不是在两侧字面里挑一个。附带的注释要同时点名两条各清了哪一项,否则下一槽读到空串会以为清单从来就是空的。

### 4.4 对侧顺带抬高的下限要取严格并集

同在 `tests/unit.js`,`w44` 把编排面已落地条目数的下限从 `>= 3` 抬到 `>= 4`(它自己落地了 SK-05 全链)。这一处**没有冲突**、自动合并了——但并入 `w43` 之后 SK-26 的编排面也落地了,实际是 5 条,`>= 4` 虽然能过,却比实况松一档。按 W38 那条「各加严一半时取严格并集」的口径把它跟到 5:

```js
assert(orch.length >= 5, '编排面已落地的条目不应少于 5 条(主线全链/主线前段/审片修订闭环/一键成片投影/结论回流)');
```

实测 `Skills.playbooks()` 现投影五条:`core.playbookProjection`、`eps.frontPipeline`、`review.reviseLoop`、`review.memoryFeedback`、`film.produceProjection`。

> **口径**:自动合并的断言也要复核一遍下限是不是被并入抬松了。冲突标记只标「两侧改到同一行」,**「一侧改了、另一侧让它的前提变了」不产生冲突**,却同样会让断言脱离实况——这类要靠"合完把该断言的实测值再跑一遍"兜住。

### 4.5 README 数字对账:每一步都靠断言自己报,不手算

`contract` 套件有一条「README 数字对账」用例,按 `tests/unit.js` 的套件表求和后与 README 里的用例数比对。本槽四次合并里它红了三次(368、374、375),每次照它报的实测值改 README 一处即可——**不手算、不预填**。`w44` 那次它没红,正好印证 3.1 的判断(那 40 行断言加在既有用例内部,用例数不变)。

> **口径**:名集比对出现差集时,先按「旧名 → 现名」找配对再下结论。分叉点早于某次改名的分支,它的名集里必然留着旧名;差集不为空**不等于删了测**,但差集里每一条都必须能指出它现在叫什么、改名发生在哪一槽。
