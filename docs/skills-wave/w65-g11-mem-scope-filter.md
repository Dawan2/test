## 1. 改前的实况

W43 落地 SK-26 回流面时,`note` 的仍欠段与 memory 套件里一条源级断言一起把这处余量钉在案:

```js
// js/skills.js SK-26 note
'仍欠(G-11):回流条目蒸馏进专家 persona 仍要人在专家库点「从使用记录进化」,'
+ 'evolveExpert 只对自定义专家开放、读记忆时不按板块过滤,自动进化与预置专家仍无出口'

// tests/unit.js memory 套件
assert(/const mem = \(Store\.state\.agentMemory \|\| \[\]\)\.map\(m => m && m\.text\)/.test(ex),
  'evolveExpert 现仍读全量记忆文本(不按 scope 过滤)');
```

`js/experts.js` 那一行读的确实是整个桶:

```js
const mem = (Store.state.agentMemory || []).map(m => m && m.text).filter(Boolean);
```

**为什么这一行是真问题,而不是洁癖。** 记忆桶里的条目从来就是带板块的:`memAll`/`memSeed` 播的标准沉淀与知识库
种子各自挂 `分镜`/`剧本`,`memFeedback` 的审片与发布结论挂 `成片`,浏览器「记住…」与 CLI `memory add` 也都收
`scope`。桶里同时躺着「定调:全片低饱和青橙,六维缺口按导演页补」(导演板块)和「相邻景别不硬切」(分镜板块)。
过去那一行把两条一起塞进蒸馏输入,LLM 蒸出来的条款被**追加进 `e.persona`**——而 `persona` 是
`WfCore.personaNote` 注入到该专家每一条链路上的东西。也就是说:导演板块的六维缺口一旦蒸进分镜专家,
它此后在每一次拆镜、每一次分镜评审里都带着不属于自己的口径工作,而且**没有撤回口**(条款进了 persona 文本)。

召回侧不存在这个问题:`memRecall` 是"同板块优先 + 全局最近 + 关键词加权补召",串错板块只影响**这一次**对话的上下文,
下一轮重算。蒸馏侧是写死。所以两者不能共用一个取样口——这是本槽的全部判断。

## 2. 过滤规则

两步,都是纯函数,放在 `js/wf-core.js`(专家对象 / 项目树 / 雇佣状态 / 板块词表一律经参数注入,函数体不碰 `window`,
与该文件其余函数同纪律):

### 2.1 第一步:这个专家在哪几个板块生效

```js
W.expertBoards({ expert, projects, hiredId, boards }) // → ['剧本', '分镜'] | []
```

判据**不新造**,直接沿用 `personaFor` 已有的那一套——**板块雇佣 > 全局雇佣**:

| 情形 | 结论 |
|---|---|
| 某项目 `boards['分镜'].expert === e.id` | `分镜` 计入 |
| 全局 `settings.hiredExpert === e.id`,且该板块没单独雇人 | 该板块计入 |
| 全局雇的是它,但该板块另雇了专家 | 该板块**不**计入(与 `personaFor` 一样被顶掉) |
| 无项目 / 空项目列表 | 按纯全局雇佣状态判(与 `personaFor` 传 `boards=null` 同形) |
| 同一专家在不同项目雇在不同板块 | 取**并集** |
| 既没被板块雇、全局雇的也是别人 | 回 `[]` |

板块序取**入参词表**的顺序(浏览器传 `AGENT_BOARDS` 的键),不按项目里的书写顺序——同一专家同一雇佣状态下
产出稳定,提示词里那句「生效板块:剧本/分镜」不会随项目数据的书写顺序抖。

### 2.2 第二步:按板块收条目

```js
W.memForBoards(mem, boards) // → [{text,time,scope,…}]
```

- 只收 `scope` 落在 `boards` 里的条目;
- **无 `scope` 的条目一律不收**(旧数据与 CLI 不带 `--scope` 的手工沉淀都在这一类)——板块归属拿不准就不蒸馏;
- 按 `text` 去重(同一条偏好在两个生效板块都沉淀过时只蒸一次);
- `boards` 为空、记忆桶缺失、脏入参 → 回 `[]`;不改入参(与 `memWrite`/`memSeed` 同纪律)。

**回空数组是"跳过"的信号,不是"全部板块"的简写。** 这条写进了函数注释,也各有一条断言钉住。
有一条用例专门把两侧的分工摆在一起对照:同一个空板块下 `memRecall` 仍会补全局最近(上下文用),
`memForBoards` 回空(写死进 persona 的东西必须是本板块的)。

### 2.3 `evolveExpert` 侧:两道闸都在扣费之前

```js
const boards = WfCore.expertBoards({
  expert: e, projects: Store.myProjects(), hiredId: (Store.state.settings || {}).hiredExpert,
  boards: (window.AGENT_BOARDS || []).map(b => b.key),
});
if (!boards.length) return U.toast(`「${e.name}」还没在任何板块生效(…),无法确定该蒸馏哪个板块的沉淀`, …);
const bt = boards.join('/');
const mem = WfCore.memForBoards(Store.state.agentMemory, boards).map(m => m.text);
if (!mem.length) return U.toast(`「${bt}」板块暂无使用记录(导演助手记忆)可供进化,…`, …);
if (!U.requireCredits(1, '专家自进化')) return;
```

两道闸都落在 `Tasks.start`/`U.charge` **之前**,与原先「暂无使用记录」那道闸同位同口径:不登记任务、不扣费、
不退费——**计费口径一字未动**(有断言数 `__tasks.length === 0` 与 `__charges.length === 0`)。
文案都点名是哪个板块 / 缺的是哪一步,不给"什么也没发生"的空提示。

`system` 与 `user` 两侧都补上了板块:`system` 里是「根据用户与创作助手在「分镜」板块的历史协作记忆……
与该专家人设领域及「分镜」板块职责相关」,`user` 里是「生效板块:分镜」+「「分镜」板块历史协作记忆:」。
测试断的是**两侧都不得出现别的板块的正文**——只查 `user` 会漏掉把记忆拼进 `system` 的那类改法。

**人手触发点原样保留**:三个调用点(专家编辑区的「🧠 从使用记录进化」、我的专家库卡片的「🧠 进化」、
专家面板卡片的同名按钮)一个没动,没有任何地方改成自动蒸馏。现码里它本来就是人点的,产品就是那样,本槽只补过滤。

## 3. 为什么生效板块取"雇佣事实"而不是专家的 `role`

预置专家的 `desc` 里写着"适合分镜板块雇佣"、"适合剧本/分集板块雇佣",`role` 有 `导演/编剧/摄像/策划/其他` 五档。
按 `role` 映板块看着更省事,但那要**新造一张 `role → 板块` 表**,而 `策划`/`其他` 两档映到哪个板块没有依据,
自定义专家的 `role` 更是用户在工坊表单里随手选的一个下拉值,与它实际被派去干什么无关。

雇佣事实是用户**显式声明过**的:全局雇佣写在 `settings.hiredExpert`,板块雇佣写在 `p.boards[key].expert`,
这两处正是 `personaFor` 判"这条链路该注入谁"的输入。蒸馏面沿用同一份输入,好处是口径自洽——
**该专家的 persona 会被注入到哪些链路,就只吃这些链路所在板块的沉淀**。不新造映射、不新造词表。

代价是"造出来但一次没雇过"的自定义专家点进化会被挡下(第 2.3 节第一道闸)。这是有意的:它的 persona 还没被注入
到任何地方,现在就往里写死板块偏好,等于替用户猜它将来会被派去哪个板块。文案给了可操作的下一步
(全局雇佣,或到「制片 → 智能体分工」按板块雇佣)。

## 7. 交接

1. **G-11 剩两面,都还没做**(第 4 节的表):①**自动进化**——回流条目进 `persona` 仍要人点按钮。要接得先定产品口径:
   自动蒸馏会**不可撤回地**改写 persona 且每次 1 积分,挂在哪个时机(每 N 条同板块沉淀?审片闭环后?)、
   要不要给"进化条款可回滚"(现在 `persona` 是纯文本,条款进去就分不出是哪一轮蒸的——`e.evolutions` 只有计数),
   这些定不下来就不该动人手触发点。②**预置专家无进化入口**——W43 交接说的"落到自定义副本"是既有设计
   (`Experts.normExpertDraft` 造副本、`customExperts()` 落库都是现成的),欠的是复制时机与"副本已由哪个预置专家派生"
   这个字段,以及副本被雇佣后 `projTypeOf` 之类按 id 判定的地方要不要跟着认派生源。
2. **本槽的过滤口径有一处产品余量**:全局雇佣的专家在"没被板块专家顶掉"的板块上一律生效,故它的生效板块可能是
   七八个板块——过滤在这种情形下**几乎不缩小输入**。这不是 bug(它确实在这些链路上工作),但若产品认为
   "全局风格专家只该吃导演板块的定调偏好",那是一条口径变更,改 `expertBoards` 一处即可,`memForBoards` 不用动。
   现有断言里有一条(`全局雇佣的专家按全部板块取沉淀`)钉着当前口径,改口径时它会先红提醒。
3. **无 `scope` 的旧条目现在一条也蒸不进去**。桶里可能躺着用户早年手打的偏好(浏览器「记住…」在有板块上下文时才带
   `scope`,CLI `memory add` 不带 `--scope` 也不带)。要救这批,现成的口是 `WfCore.memMigrateBoard`
   (W53 落地,CLI `memory migrate --from --to`),但它按**旧板名**迁,迁不了"没有板名"的那批;
   要接就给它补一个"无 `scope` → 指定板块"的分支,并且必须是用户显式指定板块的动作,不能猜。
4. **蒸馏输入不再是"全量记忆"这件事会改变提示词长度**。同一专家同一记忆桶下,蒸馏 `user` 侧比过滤前短
   (通常短很多),`max_tokens: 600` 与 `temperature: 0.3` 未动。若日后发现某板块沉淀太多把 `user` 撑爆,
   截断口径应该学召回侧(`memRecall` 的 `slice(-4)`)按板块取最近 N 条,而不是退回全桶再截。
