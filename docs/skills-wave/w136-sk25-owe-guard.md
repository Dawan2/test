## 2. 为什么偏偏是这一条漏了

`G-03` 的重抽面随 W131 落地(见 `w131-g03-shotids.md`),那一槽把 SK-25 的 `note` 改成分面写:

同槽新加的两条 `contract` 用例钉的都是**已落地那半**(镜集恒等、四处消费点不自筛),
"仍欠那半还写着没有"这件事当时没人接——落地面有判据、欠账面靠自觉,这是本目录里反复出现的形状。

叠上一层:`G-03` 的关联索引里有**两条** skill(`review.stage` 与 `review.reviseLoop`),
故既有那句「`G-01`/`G-02`/`G-03` 的关联索引应仍在」在 SK-25 单独摘键时也不红——
`Skills.gaps()['G-03']` 只是从两条变一条,长度仍非零。摘键这一路同样是空的。

## 3. 补的这一条

`contract · SK-25 仍欠段护栏(G-03 余面):段在不在与段里点名的两处余量对照源码,抹段或写成已清都红`

写法对照 SK-26 那条现有护栏(`专家工坊两步人设(源级)` 末尾那几句):先钉段与段里的锚点,
再**反向**逐处对照源码钉住"点名的余量此刻确实还在"。两向缺一不可——只钉前半,
把欠账写成已清能被逮住,但哪天余面真收编了、记账没跟着改,那句欠账就成了一句陈年谎话而全绿;
只钉后半,整段抹掉照旧全绿。

### 3.1 前半:段与段里的锚点

| 断言 | 接住的改法 |
|---|---|
| `sk25.gaps` 含 `G-03`、`Skills.gaps()['G-03']` 含 `review.reviseLoop` | 摘键(既有那条因两条 skill 而接不住) |
| `note` 含 `仍欠(G-03)` | 整段抹掉 |
| 仍欠段含 `收敛次数` + `maxRetry` | 只留形态那一面、或把收敛面写成已清 |
| 仍欠段含 `autoSmartReview` + `逐镜` | 只留收敛面、或把形态面写成已清 |
| 仍欠段**不含** `Domain.reviseTargets`/`WfCore.reviseSubset` | 把已交账那半挤回欠账段(记账失真的反面) |
| `note` 不匹配 `G-03…(清账|已闭合|两面到此|全部落地)` | 留着仍欠段、另起一句宣布 `G-03` 结清 |

两个余面各要两个锚点(一个名词 + 一个源码里真有的标识符),是因为单锚点太容易被一句改写绕开:
只查 `maxRetry` 时把「仍没有登记口径」改成「已合成一份」照旧全绿,那正是审计那次变异的形状。

### 3.2 后半:两处余量对照源码

**余面一(收敛次数无登记口径)** 的实据是"两端各就地钳一份缺省值,双端单源层里一个字都没有":

```js
assert(/Math\.max\(1, Math\.min\(5, \+args\.maxRetry \|\| 2\)\)/.test(cli25), …);        // cli.js
assert(/Math\.max\(1, Math\.min\(5, ep\.sbConfig\.maxRetry \|\| 2\)\)/.test(prod), …);   // js/produce.js
assert(dom.includes('D.REVIEW_MIN = 7;'), …);                                            // 对照项
['domain.js', 'wf-core.js'].forEach(f => assertEq((…match(/maxRetry/g) || []).length, 0, …));
```

第三句是对照项,不是凑数:同一份 `domain.js` 里**达标线有 `REVIEW_MIN` 这样一份登记、收敛次数一个字没有**,
"有登记口径"长什么样与"没有"长什么样在同一个文件里并排放着,这一面欠着才算量得准。
哪天收敛口径真下沉成 `D.reviseMaxRetry` 之类,第四句当场红,逼着同轮改记账。

**余面二(两端闭环形态不同构)** 的实据是两侧循环的嵌套方向:

```js
const iShotLoop  = prod.indexOf('for (const s of targets)');
const iRetryLoop = prod.indexOf('for (let attempt = 0; attempt <= maxRetry');
assert(iShotLoop >= 0 && iRetryLoop > iShotLoop, …);      // 浏览器:重试嵌在逐镜循环里
assert(!/revise(?:Targets|Subset)/.test(prod), …);        // 浏览器:整集重抽面派生一处不引
// CLI:轮次循环,且循环体内现取整集重抽面
assert(cli25.slice(iCliLoop, iCliLoop + 1400).includes('low = await reviseTargets(args, f)'), …);
```

取的是**位置关系**而不是两条循环各自在不在:两条循环单独看都能长期存在,
"重试在逐镜循环之内"才是"逐镜重试"这句记账的机器形态。浏览器那侧一旦改走整集子集重抽,
第二句(不引派生)与第一句(嵌套方向)会先后红,记账必须跟着改。

## 5. `G-03` 此刻仍欠什么(原话未动)

SK-25 的 `note` 一个字未改,余面照旧是这两条:

1. **收敛次数无登记口径**:`maxRetry` 的取值依据与"收敛到第几轮算够"没有判据,
   `cli.js` 按 `+args.maxRetry || 2` 钳、`js/produce.js` 按 `ep.sbConfig.maxRetry || 2` 钳,各跑各的。
2. **两端闭环形态不同构**:浏览器 `autoSmartReview` 是逐镜连着重试 `maxRetry` 次(镜内循环),
   CLI `episode.produce` 是整集低分子集重抽 `maxRetry` 轮(集外循环)。

本槽只给这两句话补了护栏,一面都没有落地。要动第 2 条得先定浏览器那侧的进度面板语义与逐镜计费节奏
能不能接受改成分轮——那是产品口径,不在本槽范围(与 `w131-g03-shotids.md` 第 7 节的交接同调)。
