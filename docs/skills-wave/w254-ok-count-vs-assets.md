## 一、live 复现:两端同形,而且不是只有主体侧

复现夹具照 W251/W248 那两档的形状搭:同 id 三位/三行 + 一位不相干的,`withProject` 桩在末轮开跑前把末位/末行从表里删掉(模拟这一趟跑到一半别处改了表),序数 2 越界,兜底退回首位。引擎桩按下发次序给各不相同的产物 url(否则同一张图写三遍量不出真假),落库面读 clone 语义的 disk 夹具。

| 形态 | 引擎实收 | 改前回执 | 到手产物 | 判 |
|---|---|---|---|---|
| 主体 `subject.generateImage` 点名 `["dup"]`,末位被删 | 3 次全成功 | `ok:3 failed:[]` | **2 位**(首位拿的是第 3 轮那张,第 1 轮那张被盖) | 漏 |
| 主体同一路,没有并发改表 | 3 次全成功 | `ok:3 failed:[]` | 3 位,三张各不相同 | 一致 |
| 镜头 `episode.generateVideos` 点名 `["dup"]`,末行被删 | 3 次全成功 | `ok:3 failed:[]` | **2 行**(首行拿的是第 3 轮那段) | 漏,**与主体侧同形** |
| 镜头同一路,同 id 一行不剩 | 2 次(第 3 轮定位就失败) | `ok:2 failed:[1]` | 2 行 | 一致(如实进 `failed`) |

**「同形」这件事得量出来才算数**:W251 只在主体侧读到这个数,记的时候没说镜头侧是不是也这样。现跑两条命令各走一遍,`ok` 与到手数岔开的那两格逐格对齐——两条命令的循环骨架逐字同形(`okCnt++` 都紧跟在引擎调用返回之后,与「这一轮写到了哪一位」无关),所以只改一侧就是留一半。

## 二、停工判据怎么走完的:note 说的是计费口径,一个字没说落库

停工条件是「产品意图就是引擎成功次数,且 note 已说明落库合并」。前半成立,后半不成立。现取那一趟的 note 全文只有两件事:

- 「这一趟按 3 位逐位跑、逐位计费」——说的是**计费**按几位算
- 「比点名数多花了 2 位的钱」——说的是**多花**了几位的钱

两句都在钱这一侧,没有一个字说「这 3 次调用的产物落到了几位身上」。而「多花了 2 位的钱」这句话本身还在往反方向推:它默认那 2 位钱各买到了一位的产物(正常一趟确实如此),读到 `ok:3 failed:[]` 的人只会更确信三位各有独立产物。真实情况是其中一位的图被同一趟的后一轮盖掉,下一轮它仍判缺图、仍要再扣一笔。

故判**真漏**,不停工。收法按明令走最小的那一格:

- **不改 `ok`**:它记的是引擎调用成功次数,那 3 次都真发生、真扣了钱。把其中一次改成 `fail` 来凑落库数,是拿假失败掩盖真扣费——回执会同时说错两件事(引擎没成功、这笔钱不该收)。
- **不改计费**:两条命令照旧走 `Tasks.run` / `metered` 那一套按调用次数计,本槽 `billing.js` 与两端计费入口零 diff。
- **不剥兜底**:`nthSubject`/`nthShot` 那两处退位与委托一个字没动(W251 已论证过删它是行为面退化)。

## 三、改的是哪一格:回执多一个 `landed`,外加岔开时的一句话

两条批量命令的 `result` 恒带 `landed` = 这一趟的产物真落到了几位/几行。

```
result: { total: 3, ok: 3, landed: 2, failed: [], … }
```

`landed` 的取数不是事后再扫一遍表(引擎在离线占位下可能给回同一个 url,按产物去重会误低报),而是**每轮当场记下本轮写到了哪一位**:座位键 = `id + '#' + 它在同 id 那几位里排第几`,收进一个 `Set`,`landed` 就是这个集合的大小。同一位被两轮写到时集合只涨一格,这正好是「共位」的定义。

- 落在 CLI 那两处的 `withProject` 回调里、写完产物之后——失败的那一轮不记座位,故 `landed` 永远不会把没落地的算进来。
- 岔开时另经 `note` 说清「3 次调用、2 位落库」,单源 `Domain.landedNote(okCnt, landed, unit)`,两端与 `Commands.digest` 同读一份;相等的正常一趟一句不加(那时 `ok` 就是到手数,重复一遍是废话)。
- **一位/一镜也没跑那几路一律带 `landed: 0`**(CLI 与浏览器共 11 个出口全带上)。字段时有时无的话,调用方每次读 `landed` 都得先判 `undefined`,而 `undefined` 与 `0` 在数字比较里的行为差得远。

live 复现同一组夹具改后重跑:主体侧 `ok:3 landed:2`、镜头侧 `ok:3 landed:2`、两条正常一趟都是 `3/3`,note 只在前两格出现。

## 四、两处自己红出来的坑,都值一记

### 4.1 座位键只记行内序数会当场作假

第一版座位键写的是「它在同 id 那几位里排第几」,没带 id。跑既有判据当场红 2 条(`generateVideos` 与 `subject.generateImage` 各一条「正常批量的成功回执一句不加」):点名三个**各占一位的不同 id**时,三位的行内序数全是 0,集合大小 1,于是 `landed:1` 而 `ok:3`,回执反倒平白报出一句「产物只落到 1 位」——**为收一个假话而造了另一个假话**。

这一格能被既有判据接住不是运气:W239/W242 那两条「点名几个 id 就跑几个 id 的正常批量一句不加」钉的正是「不许对正常一趟多说话」,新字段一旦在正常一趟上算错,先红在它们身上。本槽另补一档正面钉住(三个不同 id → `3/3`),不让下一个人只靠那两条的副作用发现。

### 4.2 判词收数不许用 `+x`

第二版 `landedNote` 里写的是 `const o = +okCnt, l = +landed`。`+null` 是 0、`Number.isFinite(0)` 为真,于是**调用方根本没给这个数**时判词照样开口:「这一趟 3 次调用成功,产物只落到 0 位」。那是漏传参数,不是落库真丢了。改成 `typeof x === 'number' && Number.isFinite(x)` 收数,非数一律回空。

两处的形状是同一个:**新字段的边界不在"算得对不对",在"算不出来时说不说话"**。

## 五、本文最该抄走的一格:两端 `ok` 的口径本来就不同,只是正常一趟恒等

复现时顺手量出的读数,比这个漏本身更值一记——两端的 `okCnt` 从来不是同一件事:

| 端 | `ok` 怎么数出来的 | 实质 |
|---|---|---|
| CLI `subject.generateImage` | `okCnt++` 紧跟在 `genImage` 返回之后 | 引擎调用成功次数 |
| CLI `episode.generateVideos` | `okCnt++` 紧跟在 `genShotVideo` 返回之后 | 引擎调用成功次数 |
| 浏览器 `subject.generateImage` | `if (s.image && s.image !== before) okCnt++` | **这一位到手了新图没有** |
| 浏览器 `episode.generateVideos` | `pend.filter(s => Store.shotVideoReady(s)).length` | **表里有几行真就绪** |

浏览器那两处数的本来就是 `landed` 那件事。两端之所以从没对不上,是因为浏览器那一端写的是循环里拿到的**那个对象**、没有第二次寻址,共位这个形态它根本走不到——**两个口径在正常一趟上恒等,岔开只可能发生在 CLI 那一侧**。

这有两个后果值得记:

1. 「两端回执逐格相同」这类判据(W239/W242/W248/W251 都有)在这条漏上**恒真**,一条都拦不住它。能量出它的只有「引擎实收次数 vs 落库产物数」这个**同一端内部**的对照。
2. 补 `landed` 时浏览器那两处**照样把座位算出来**,而不是写 `landed: okCnt`。现在两个数在那一端恒等,是那一端的实现形态决定的;哪天它也改成回最新树按序数重取,两个数会自己岔开,而不是继续默契地相等。
