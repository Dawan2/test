# W213 停工位现场:「免确认自动执行」档到底跑不跑得掉 `expert.evolve` —— **不成立**,改把判据钉住

基线 `cursor/w208-integration-f258`,tip `4285bc7`。W208 残留第 2 条写的是:

> 浏览器 Agent 面板那条路本槽没有新判据:主路 `exec` 级 run op 恒经 `U.confirm`,
> 若日后给面板开出"免确认自动执行"档,得同轮把 `cmdManual` 接进去。

本槽先去量「那一档是不是已经有了」。**量下来是:开关在,但它不是那一档**——
`settings.agentAuto`(「⚡ 自动执行」)管的是数据类改动免预览,`exec` 级 run op 在它开着时照旧过 `U.confirm`。
既然没有免确认的 run 路,就没有东西可以接 `cmdManual`,**产品码一行未动**;
本槽交付的是把这条判据从注释里的一句话落成用例:**一旦出现跳过 `U.confirm` 的 run 下发路径,它必须先过 `WfCore.cmdManual`**。

W210(compose 指纹跳过)、W211、W212 一条没碰,W206 / W207 / W209 同样没等。

## 三、判定:不成立,且不许靠"发明一个开关"把它变成成立

任务给的否决条件是「若没有这条开关、所有浏览器 run 都 confirm,停工位不成立」。
现场符合这一条:开关有,但它不豁免 `exec`。**故不接 `cmdManual`,也不新造第二个开关**——
造一个免确认档再接闸,等于自己先挖坑再填,产品面净损失一道人工闸。

按任务口径改钉判据。判据的形状不取「`agentAuto` 开着时必须 confirm」(那只钉住今天这一个开关名),
取**下发点分类**:`AgentOps` 那两个动作执行器的每一处调用,都要能归进四类之一——

| 类 | 谁 | 凭什么放行 |
|---|---|---|
| 闸内 | `runOps` / `runOpsG` | 落在某个 `U.confirm(…)` 的实参跨度内 |
| 非 exec | `safeActs` / `safeActsG` | 名单由 `opRisk(o) !== 'exec'` 过滤出来 |
| cmdManual | 自修复轮的 `retries` | 名单由 `WfCore.cmdManual` 过滤出来 |
| 人手点击 | 预览卡「应用修改」的 `actOps` / `g.acts`,chips 与事件卡的别名字面量 | 用户点的那一下就是授权;别名面另有一条闸(见下) |

归不进去就是红。新开一条不经确认的 run 路,要么把它送进 `U.confirm`,要么先过 `cmdManual`,
要么在清单里说明它凭什么不用——三条都不做,用例当场报「未归类:<那个实参>」。

别名面单独一条闸:chips 与事件卡是点一下就走、不过 `U.confirm` 的,而它们只发得出 `ACT_CMD` 里的中文别名,
所以**别名表里不许出现人手动作命令**。今天表里 6 个命令没有一条是 `manual`,这条钉住往里塞的那一手。

## 四、落地了什么

`tests/unit.js` 的 `agent-ops` 套件 +5 条,产品码 `js/` **零 diff**:

1. exec 类 run 在两条路上都只在 `U.confirm` 闸内下发(另钉住下发点各只有一处——新开的那处也得进闸);
2. 免确认直执行那一支按 `opRisk` 排除 exec(行为面另取 `opRisk({op:'run'})==='exec'` 现证);
3. 上面那张分类表,逐文件按源序比对;
4. `ACT_CMD` 别名面不夹带人手动作(反向钉住别名表不许被顺手清空——清空是砍功能不是设闸);
5. 三个 agent 文件里不许出现第二个免确认开关字面(`agentAutoRun` / `autoConfirm` / `skipConfirm` / `noConfirm` / `confirmFree`),
   同时反向钉住现有 `agentAuto` 那一档还在(它管的是数据类改动免预览,不是本条要拦的东西)。

前三条共用两个源级扫描小工具(`confirmSpans` / `dispatchActsArg`):按 `()[]{}` 配平、跳过字符串与模板字面量,
所以判的是"这一处调用在不在那个回调里",不是"附近有没有出现 `U.confirm` 这几个字"。

按任务口径没碰的:`compose` 指纹跳过扣费、`generate` 的 `memWrite`、`playbook` / `execStep`、`gaps()` 键、
`GUARD_TOPICS`(一条不登记)、`manual` 字段(仍只此一位,没有第二份)。
人手 evolve 入口四端(专家库「🧠 进化」按钮 / CLI `exec` / MCP `hujing_expert_evolve` / 服务端端点)一条不减,
C 格读数就是浏览器那个入口仍跑得成的现证。

## 七、残留与交接

1. **集级内嵌面板 `Agent.render` 是活代码但没有挂载点**:`js/sb-views.js` 的「📎 加入对话」与 `js/sb-board.js` 里
   两处仍在写 `ep.agentOpen = true` 并触发重渲,而没有任何地方按这个标志渲染面板——
   本槽只把它当作"另一条要一起判的路"来量(判据对它照样成立),没有去动挂载与否这个产品口径。
   要摘要接由产品面决定;真摘的话本槽那两条源级用例里 `agent.js` 那一格得同轮改。
2. **预览卡「应用修改」这一路不经 `U.confirm`**:它归"人手点击"类——卡面上逐条列着
   「⚠ ▶ 执行:expert.evolve(按该功能规则扣费)」,点下去就是授权。语义上够,但它与另外三类不同,
   靠的是 UI 上写清楚而不是代码里的闸;哪天预览卡改成"一键全应用"而不再逐条列出动作,这一格就得重判。
3. `runGlobalActions` 的 `run` 分支只认「策划」「译制」两个别名、不接命令名——全局抽屉那侧的 `exec` 确认闸
   今天拦的是一条本来就走不通的路。要给全局侧接上命令层时,那道闸从"冗余"变成"承重",别顺手删。
4. `cli.smoke` 两条失败沿旧,本槽未查。
