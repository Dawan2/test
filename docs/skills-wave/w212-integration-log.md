## 二、四棵树机检:哪些是并集,哪些是 git 直接取对侧

冲突块数不等于成色。逐文件比对 基线 `B`(各自叉点)/ 我方 `P1` / 对侧 `P2` / 合完 `M` 四个 blob:

**三次合并的产品文件成色完全一致**——`js/agent-ops.js`、`js/cmd-registry.js`、
`js/commands.js`、`js/plans.js`、`js/sb-views.js`、`js/wf-core.js`、
`cli.js`、`server.js`、`mcp.js`、`tests/integration.js` 全部是 **`P2 == B`,git 整份取我方**。
这一格是本槽产品零 diff 的**机检来源**,不是"看着没冲突所以应该没变":
三支自各自叉点起就没碰过任何产品文件,故 W208 带进来的 W203 `cmdManual`/`agentNormalize`、
W204 的 CLI 写回、W201 的 `execStep`、W198 的 playbook 扫描一个字都不可能被冲掉。

**真三方(两侧都改过)只有三个文件**,`M` 三次都是**手工并集**、不等于任一侧:

| 文件 | 三次成色 | 怎么并的 |
|---|---|---|
| `README.md` | 真三方 | 长行按掩码比对先证"只差数字"再取我方,数字按 live 订正 |

## 三、`README.md` 长行怎么核的:掩码比对而不是人眼看

那句一万多字的单元测试长行三次都撞冲突。处置是**先证成色再决定取哪侧**:
把两侧**所有数字整体掩成 `#`** 再逐字符比对,三次都得"掩码后逐字节相同"——
即两侧的差别**纯粹是数字、没夹带散文**,故整句取我方(它带着 W203/W204 的新段落),
再把数字按合完 live 改。不合规的做法是直接 `--ours`:那在两侧真有散文分歧时会静默吞掉对侧。

W209 那次另有一处**没冲突但是真新增**的散文(第 532 行):
它在我方自 W205 起没碰过的位置上,git 自动合入,内容是"这道闸只管 `execStep` 一个漏斗,
故全仓还有没有别的路能替用户跑计划步另有一层普查判据钉着"那整段。
零冲突块不等于不必核——单独把它读了一遍确认是 W209 该带进来的正文,不是残留。

## 四、本槽最值钱的一格:两侧改同一行、改成同一个值,git 零冲突自动合上,而 live 是第三个数

W207 那次,`README.md` 第 361 行(contract 段自报的断言条数)两侧**都**从 134 抬到了 **135**:
我方是 W205 抬的,对侧是 W207 自己抬的。两侧新值逐字相同,故 git **一个冲突块都没给**,
自动合上一个看起来天经地义的 135。

但两侧抬的是**两条不同的用例**,合完 live 实跑是 **136**。

这一格与 W208 那条"即便自称数字与 live 恰好相同也是量出来的"是同一课的反面:
那次是"抄来的碰巧对",这次是"git 替你合出来的碰巧错"。两次的结论是同一条——
**数字一律按合完 live 实跑现取**,既不抄被合入支自称,也不信 git 自动合并的结果,
更不默认留旧值。本槽因此在每次合并后都整跑一遍 `tests/unit.js` 让对账用例自己报差额,
按它报的数订正,而不是自己心算。

## 五、W209 的「处数 / 文件表」按 live 重算

W209 有一条 contract 普查用例,`SOURCED` 表把"`cmd` 是变量的下发口"逐处登记来路与把关方,
并**按处数点名**做全等断言(不是 `>=`)。这张表是在 **W205 的树**上点的数,
而 W208 带进来的 W203 动过 `js/agent-ops.js`——**下发点有没有变得多了一处,必须当轮重算**。

重算方式是**用仓库自己的 `blankNonCode`**(从 `tests/unit.js` 里现取出来)在
`js/` 全树 + `cli.js`/`mcp.js`/`server.js` 上把 `Commands.execute(` 的调用点扫一遍,
在**合完的 tip** 与 **`a2e08b6`(W205 树)** 两棵树上各跑一次,两边读数逐字相同:

- 字面下发点 **15 处**(表里那条下限是 `>= 15`)
- `cmd` 是变量的下发口 **5 处**:`js/plans.js → st.cmd`、`js/issues-ui.js → it.cmd`、
  `js/release.js → fix.cmd`、`js/cmdpalette.js → e.name`、`js/agent-ops.js → cmd`,各 × 1

结论:**W203 改的是 `agentNormalize` 的 ops 过滤与 `selfFixRound` 的重试白名单,
没有新开 `Commands.execute(` 的下发点**,故 W209 那张表原样成立,**一处没放宽、一个数没改**。
这里有意**没有**走"少几个也行"那条路(把全等改成 `>=` 等于把这条普查判据废掉),
也**没有**拿 W205 的陈旧处数硬套——两者都会让集成线说假话,只是方向相反。

顺带记一格**自己的工具出错**:第一次重算时用的是随手写的 blanking,
它在 `js/release.js` 的某处正则字面量上失步,把 `fix.cmd` 那处**漏掉了**,只数出 4 处,
而用例是绿的。差别指向的是我的脚本不是判据——换成仓库自己的 `blankNonCode` 后
两边都得 5 处。**普查类判据复核时要用被判据自己那份扫描器,别另写一份来"独立验证"**,
另写的那份出错时给出的是反向误报。

## 七、名集比对(`|` 切、**多重集**、不 unique-sort)

按 `套件 · 用例名` 成集,用**多重集**(同名多条要各计一次,unique-sort 会把它们吃掉):

- W206 相对叉点 `0010394` 新增 **2** 条
- W207 相对叉点 `0010394` 新增 **1** 条
- W209 相对叉点 `a2e08b6` 新增 **2** 条
- 基线独有(即 tip 上**丢失**的)**0** 条
- 三支新增里 tip 上缺的 **0** 条
- tip 多出(基线 + 三支新增之外的)**0** 条
- 自洽:`622 + 2 + 1 + 2 = 627` = live tip

即**零吃测**:没有一条被合并吃掉,也没有一条凭空多出来。
另复核 tip 上 `套件 · 用例名` 标签**全局唯一**(重名会让这套取证工具吃掉其中一条)。

取名集时有一处**取证工具自己的坑**要记:名集是从实跑输出里抓的,
而失败行会把失败原因缀在名字后面。头一次比对时基线快照是在 README 数字还没订正、
对账用例正红着的时候取的,于是同一条用例在两边"名字不同",报出一条假的"丢失 1 条 / 多出 1 条"。
处置是**快照一律在全绿的 commit 上取**,不是把那条差异解释掉。
