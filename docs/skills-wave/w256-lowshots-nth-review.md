## 一、先 live:展示的问题原文到底来自哪一行

### 1.1 现跑读数:不是「都来自首行」,是后几行干脆空着

夹具(`loadAgentOps` 沙箱,真 `js/domain.js` + 真 `js/agent-ops.js`):
三行分镜 `sh0` / `dup` / `dup`,同 id 的两行**有意不排在表首**(实位 2、3,序数 0、1),
各自那一行的 `reviews` 里各存各的报告(`rA` 首行「主光不足」、`rB` 次行「机位穿帮」),
`lastReview.perShot` 按整集审片的写回口径逐行各记一条(`sh0` 9 分、`dup` 5 分、`dup` 4 分)。

基线 `adf7442` 上直调 `AgentOps.stateDigest`:

```
lowShots  [{n:2, score:5, issues:["首行:主光不足"]},
           {n:3, score:4, issues:[]}]
chip.text …镜头2(5分):首行:主光不足 / 镜头3(4分):详见审片报告…
```

两件事一次读齐:

- **镜号已经分开了**(`2,3`):W253 的 `order` 取实位,这一格现跑是对的,不必再动。
- **第二条的 `issues` 是空数组**:`find` 首行拿到的是实位 2 那一行,它的 `reviews` 里只有 `rA`,
  而这一条要找的是 `rB` → `rep` 为 `null` → 走「报告被挤出最近 5 条」那条降级路。

所以交接里「问题原文是不是都来自首行」这句话,现跑量出来的形态要更准一点:
**取的是首行那一份 `reviews`,但因为按 `reportId` 认人,后几行落到的是空**,
而不是印出首行那句话。两者错得一样严重(镜号与问题清单对不上号),
但**报错的样子不同**——空数组会被 chip 的 `|| '详见审片报告'` 兜底吃掉,
在界面上看起来像「这镜的报告过期了」,而不是像一处寻址错误。
下一个人照「印成首行那句」去复现会复现不出来,故如实记在这里。

> 唯一会印出首行那句话的情形是同 id 两行**指向同一个对象**(数组里两个引用);
> 那种表上两行的 `reviews` 本来就是同一份,取哪一行都对,不构成错。

### 1.2 停工条件:两条都不成立

- **「现跑已按行取」**:§1.1 反过来,不成立。
- **「产品有意展示该 id 首行问题」**:同一个 `d.lowShots` 对象里,`n` 是按实位逐行分的、
  `issues` 是按 id 取首行的——一条记录里两种寻址口径,读出来就是自相矛盾
  (镜号说第 3 行、问题清单说首行那份)。要「有意展示首行」得连镜号一起按 id 收成一条才自洽,
  而那正是交接明令不许做的方向(W253 §1.3 同一条理:按行出目标就得按行取材)。

### 1.3 射程:这份 `issues` 到底谁在用

`d.lowShots` 有四个消费点,只有一个真读 `issues`:

| 消费点 | 用到的字段 | 本槽是否受影响 |
|---|---|---|
| `stateBlock` 状态摘要注入 | `n` / `score` | 否(镜号早就按行分开) |
| `openingLine` 开场白尾注 | `n` | 否 |
| `dynamicChips` 修订 chip 的指令正文 | `n` / `score` / **`issues`** | **是**——发给助手的问题清单 |
| `js/issues.js` low-review 条目 | 另走 `Domain.reviseTargets`,不读本对象 | 否 |

即这一处只落到「发给助手那句话里带不带得上问题原文」,**不写回任何库**
(写回面 W253 已经收完:`reviseSubset` 取材 + `reviseLowShots` 写回)。
按交接「只展示、不写回」的定性一致,故本槽只改取材、不碰别的。

## 二、改了什么(`js/agent-ops.js` +3 −1,其中两行是注释)

```
const s = (ep.shots || [])[t.order - 1];
```

`order` 是同一次 `Domain.reviseTargets` 调用里刚算出来的实位(1 起),直接当下标用,
与 `WfCore.reviseSubset` 那一句 `shots[t.order - 1]` 逐字同形——
第二份口径不在本层另立(既不在这里数一遍序数,也不拿 `t.nth` 当行号:
`nth` 是「第几行同 id」,同 id 的行不在表首时它与实位根本不是一个数,§三 变异 2 就是这一手)。

越界与判旧两档不必在本层再兜:`reviseTargets` 已经把「同 id 的行不够数时退回首行」
和「报告判旧一律回空」判完了,`order` 出来必定落在当前分镜表的实位上;
`s` 取不到时后一句的 `t.reportId && s` 照旧回 `null`,降级路一个字没改。

唯一 id 的表逐字节等价(同 id 只有一行时 `find` 那一行就是 `shots[order - 1]`)。

## 三、钉测试(`tests/unit.js` +1 条,`agent-ops` 套件)

新用例「同 id 多行时每条低分镜的问题原文取自己那一行的 `reviews`(取首行即红)」一条钉三档:

1. 镜号按实位分行(`2,3`)——W253 那一格的回归位,与本槽这一格摆在同一条用例里对照着读;
2. 各条的 `issues` 取自己那一行的报告(`2:首行:主光不足 / 3:次行:机位穿帮`);
3. chip 指令正文里每一镜配的清单也是它自己那一行的(`镜头3(4分):次行:机位穿帮`),
   即真正被消费的那一句话,而不只是中间对象。

夹具两处是刻意的,少一处就漏判:

- 同 id 两行**排在表中而非表首**:序数(0、1)与实位(2、3)因此对不上,
  「拿 `nth` 当行号」这一手才量得出来(两行若在表首,那一手全绿)。
- 末行的 `reviews` 表头**另有一份事后单镜报告** `rB2`:整集那份不在 `[0]` 位,
  「不按 `reportId` 认人、直接 `reviews[0]`」这一手才量得出来(W134 立的那条精确取回,顺带守住)。

`tests/integration.js` 未加(本槽不新增端点,`/api/wf/smart-review` 的 `lowShots` 走 `reviseSubset`,
W253 已收);`tests/cli.smoke.js` 未加(这一格不过 CLI)。

### 3.1 变异三手,逐手红 1

| # | 怎么改坏 | 结果 |
|---|---|---|
| 1 | 退回 `find(x => x.id === t.shotId)`(基线那一句) | 红 **1**:`实际 "2:首行:主光不足 / 3:"`——后一条空着,正是 §1.1 的读数 |
| 2 | 拿 `t.nth` 当行号(`(ep.shots \|\| [])[t.nth]`) | 红 **1**:`实际 "2: / 3:"`——两条都串到别家那一行,连首行那条也不对了 |
| 3 | 不按 `reportId` 认人,直接 `(s.reviews \|\| [])[0]` | 红 **1**:`实际 "2:首行:主光不足 / 3:事后单镜报告"` |

方法性的两格,原样记下:

- **变异 2 比变异 1 错得更远,但报错句读起来更容易误判**:变异 1 只有后几条空,
  变异 2 是两条全空——「全空」看起来像「报告都过期了」这种数据问题,
  而实际病灶是行号口径用错。判词里因此把三种错法一起写进那一句断言的说明里
  (`回取首行 reviews 时后几行取不到会空,拿 nth 当行号则串到别家`),读报错的人不必回头翻代码猜。
- **变异 3 是补夹具补出来的射程**:夹具第一版每行只有一份报告,`reviews[0]` 与按 `reportId` 取
  结果相同,这一手当场全绿(670/670)。加上那份事后单镜报告之后才红——
  同一条用例,射程从两手扩到三手,没多开一条用例。
