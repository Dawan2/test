# W126 · 契约段自报的断言条数进对账:那个 N 改成「九条」也全绿的洞

> 槽位范围:`tests/unit.js` 的 `contract` 套件新增 1 条用例 + 抬 2 个既有下限字面,`README.md` 同步两处数字与一句口径,本记账件加索引行。
> **零产品代码改动**(`js/`、`server.js`、`cli.js`、`mcp.js`、`billing.js` 一行未改),不动发布门口径、不新增计费动作、**不删任何用例**。
> 基线 `cursor/w123-integration-7b41` head `635fc7a`(未合 W124/W125)。

## 1. 病灶:立契约那段话自己不在契约里

`README.md`「文档数字对账契约」那一段开头写着「`node tests/unit.js contract` **十一条**断言把它们钉在实测值上」,
后面逐条讲这些断言各自钉住什么。段里点名的每一个数字都有判据接着——CHECKS 条数、就绪检查面数与条数、
三个套件的用例数、短名单/KB/提示词/命令/专家数、记账件份数——**唯独开头这个 N 自己没有**。

W123 的核验实测过一次(`w123-integration-log.md` 第 6.3 节):把「十一条」改成「九条」,`contract` **101/101 全绿**,
一条都不红。也就是说这段话立的是全仓最密的一层数字契约,而它自报的那个数是段里唯一一个纯手写、写错没人管的数。

代价不只是"写错没人管"。这个数每加一条契约断言就要动一次,而它同时是三条集成线在同一句散文上反复撞车的那个字:
`w107-integration-log.md` 记过一次三边给出「五 / 七 / 六」而**没有一个在合并后成立**、只能合完现取为八;
`w122-integration-log.md` 记过一次「九 → 十」并注明"人工核对为真"。**人工核对为真的次数越多,越说明它该有判据。**

## 2. 落地:口径定死为「这个套件实跑出来的条数」

新增一条用例,接在既有那条「单元测试用例数由 `tests/unit.js` 实计」之后,**既有对账条一条不删、一字未改**:

```
assertDocNum('README.md', /`node tests\/unit\.js contract` 套件[(（]实测 (\d+) 条断言/g,
  SUITES.contract.length, 'contract 套件断言条数');
```

取数口是 `SUITES.contract` 的长度,也就是 `node tests/unit.js contract` 实跑出来的那个总数(本槽 **102**);
沿用既有 `assertDocNum` 的两层口径——数字对不上红,**那句话被改写或删掉同样红**。

### 2.1 为什么不是「这段里做数字对账的那几条」

历史上那个 N 数的不是套件条数(`contract` 当时已跑 100/100 而那句写着「十条」),而是**这段散文点名的那些条目**——
一个由人挑出来的子集。要给它立判据就得先回答"哪几条算数字对账",而这个问题**没有机器边界**:

- 按名字关键词圈(`README 数字对账:` 前缀)——`集成/冒烟 report(...) 不许落在循环里`、`三套件用例数只增不减`、
  `单元用例名全局唯一` 这三条都在段里点了名却不带那个前缀,圈不进来;为它们改名等于给"按名成集比对证明没删测"
  那件取证工具制造一次全仓改名,代价远大于收益。
- 按源码里加一对首尾标记注释圈——判据就变成"标记还在不在、新条写没写进标记内",
  **漏在标记外的新条永远不会被数到**,与今天这个手写数漂移的方式是同一类,只是换了个地方漂。

故本槽换掉的是口径而不是判据形式:那个数从此指**整个 `contract` 套件的条数**,来处唯一、加减任何一条契约用例都当场红,
不需要任何人回答"这条算不算数字对账"。段里那些条目仍逐条写在散文里,只是不再另报一个手点的数。

README 那句话同步改成写明口径的形态,而不只是换个数字:

> `node tests/unit.js contract` 套件(实测 102 条断言,含下面这些数字对账在内的全部契约用例;**这个条数本身也进对账**,现取 `SUITES.contract` 实计,套件加减用例而这句话没跟着改即红)把它们钉在实测值上

「含下面这些数字对账在内的全部契约用例」这半句是有意写死的:不写清楚,下一个人照旧会把它读成"数字对账那几条",
按旧口径去点数,而点出来的值与断言期望的值只在偶然情况下相等。

### 2.2 正则里那对括号写成 `[(（]`

README 这段用的是全角括号。既有几条对账的正则一律写成 `[(（]` 半全角都收(文案在半角/全角之间反复过),本条沿用同一形态;
全角那半在源码里写成 `\uFF08` 转义——这个字符在编辑链路里被规范成半角过一次,当场表现为「找不到该数字表述」的假红,
写成转义后不再受此影响,行为与直接写字面完全一致。

### 2.3 顺带抬的两个字面

按各自条目写明的规矩抬,只改数字、其余判据一字未动:

| 下限 | 抬档 | 依据 |
|---|---|---|
| 三套件棘轮里的 `unit` FLOOR | `477` → **`478`** | 「新增用例时把下限抬到当轮实况」,对应本槽这一条用例 |
| 记账件份数 FLOOR | `138` → **`139`** | 「新开一槽记账时把下限抬到当轮实况」,对应本记账件这一份 |

## 3. 变异验证(五条,逐条单独施加、跑完复原)

| 变异 | 结果 |
|---|---|
| 1. README `实测 102 条断言` → `100`(改小) | 红 **1 条**:`contract 套件断言条数:README.md 与实测不符(实测 102,文档 100)` |
| 2. 同一处 → `103`(改大) | 红 **1 条**,同一条判据反向报:`实测 102,文档 103` |
| 3. 把 `实测 102 条断言` 整段改写成 `若干条断言` | 红 **1 条**:`找不到该数字表述(改写文案时须同步本断言)`——删掉措辞绕不过去 |
| 4. `contract` 套件真加一条用例、README 两个数都不动 | 红 **2 条**:本条报 `实测 103,文档 102`,W23 那条报单元总数 `实测 479,文档 478`,两条各指一处 |
| 5. `contract` 套件真删一条既有用例(词表单源那条)、README 不动 | 红 **3 条**:本条 `实测 101,文档 102` + 单元总数 `实测 477,文档 478` + W121 下限 `不得少于 478(实测 477)` |

变异 1/2/3 是本槽新接住的那一路——**同样三条变异在基线 `635fc7a` 上一条都不红**(W123 已实测过其中的改小那条,
本槽把改大与改写两个方向补齐)。变异 4/5 记的是分工:条数变动会同时惊动"套件条数"与"单元总数"两个口径,
两条报错各说各的那一处,不混成一句。

## 6. 交接

1. **这个数现在跟着整个 `contract` 套件走**:往 `contract` 加一条与文档数字无关的用例(比如词表单源那类)
   同样要动 README 这句话。这是取"来处唯一"换来的代价,好过让它继续没有判据。
2. **段里各条对账的分工仍只写在散文里**,没有第二个数去点它们。要给"数字对账这一类断言有几条"立判据,
   得先给这一类立一个机器认得出的边界(见 2.1 两条路各自的代价),不建议顺手补。
3. **抬 FLOOR 仍是新增用例的槽的义务**:两个下限字面都在 `tests/unit.js` 的 `contract` 套件里,
   一个在三套件棘轮那条的表里、一个在记账件份数那条的 `FLOOR` 常量上。
4. **集成槽合它时注意**:契约段那句话与 `单元测试(N 项断言` 这两处,是历来"两侧同值故自动合上而合入后不成立"的高发处
   (W117/W122/W123 各记过一次)。这两个数现在都有相等判据接着,合完跑一次 `node tests/unit.js contract` 即可现取,
   不要在冲突块里二选一。
