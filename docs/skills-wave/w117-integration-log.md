## 4. 逐处怎么解

### 4.1 目录索引表:两侧各带自己那一行,现查为真并集

冲突块两侧:

```
<<<<<<< HEAD
| [w114-int-dup-casename.md](./w114-int-dup-casename.md) | … |
=======
| [w115-g13-next-prompt.md](./w115-g13-next-prompt.md) | … |
>>>>>>>
```

各一行、文件名不同,**取并集成立**,按波次号排成 `w114 → w115`。

这一步照 W109/W112 交待的做法**现查**而不是套结论:逐行比对两侧的文件名集合、确认无交集之后才取的并集。
W107 那次同一张表现查出来的答案是相反的(对侧带的 `w101` 行早已在我方表里,机械并集会得到两行同名索引,
而三条索引断言一条都报不出"重复行"),**判据同一条、答案未必同**。

`w115` 那行索引里「结论是**合格余量为 0**」这句按任务口径原样留着——
它不是会过期的余量数,是这一槽的结论本身,删了这行索引就不知道那份核实件交的是什么账。

### 4.2 份数那一行:两侧写同一个数、`git` 不报冲突,而那个数合并后是错的

两侧各自把「索引表共 N 份记账件」由 `129` 改成 `130`(各算"基线 129 + 自己那一份"),
**字面逐字节相同**,三方合并直接当成"两边做了同一件事"合上,冲突块里根本看不到它。
合并后目录里是 131 份(基线 129 + `w114` + `w115`),`130` 当场不成立。

接住它的是 W105 立的三方对齐,不是通读。把它退回 `130` 现跑:

```
$ node tests/unit.js contract
FAIL | contract · docs/skills-wave 索引完备性:记账件份数由 README 明写并与目录/索引表三方对齐,且只增不减
     | 目录里的 wNN-*.md 份数应等于 README 明写的份数…:期望 130,实际 131
===== 98/99 PASS, 1 FAIL =====
```

改成合并后 live 的 `131` 即转绿(合并提交里写的就是 131);本文与本文的索引行落地后目录是 **132**,
明写份数与用例里的下限 `FLOOR` 一并抬到 **132**(棘轮见 4.4)。

**这一处值得单独记一笔的理由**:W57 记过"同一数字两侧相等 ≠ 合并后仍正确",但那次两侧给的是两个不同的错数、
进了冲突块、有人来判;这一次两侧给的是**同一个**错数,`git` 的三方合并按定义认为"无分歧",
于是它连被看一眼的机会都没有。**"两侧写法一致"这件事本身不是任何一种正确性证据**——
凡是"基线值 + 我这一份"这种算法算出来的数,合并后一律要按 live 重算一遍。

### 5.3 零吃测:多重集双向对照全空,且那处去重盲区这一次撞不出来了

| 套件 | `w114` 增量 | `w115` 增量 | 与基线增量相交 | 期望集 \ live | live \ 期望集 |
|---|---|---|---|---|---|
| `unit` | +1 / −0 | +0 / −0 | **0** | **0** | **0** |
| `integration` | +1 / −1(改名) | +0 / −0 | **0** | **0** | **0** |
| `cli.smoke` | +0 / −0 | +0 / −0 | **0** | **0** | **0** |

```

```

`integration` 那条 `+1 / −1` 是 `w114` 的改名,**不是删测**:
消失的 `项目不存在 404` 与新出的 `wf/release 项目不存在 404` 在 `tests/integration.js` 里是同一行
