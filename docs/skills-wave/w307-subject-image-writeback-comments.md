## 三、改了哪几句(共三处,两个文件)

### 3.1 `cli.js` `subjects-dedupe` 头顶那段(本槽的正题)

改前:

```
 * findSubject/subject-image/subject-copy 全按 id 取首位,后面几位结构性够不着;而两端选人闸按位筛(ids.has(s.id)),
 * 点名一个 id 跑一次批量补图,库里重复几位就登记几笔生图钱——本命令是把这批存量收拾干净的那条路。
```

改后(按 §2.1 那份读数写,形状照 W305/W306 收镜头侧那句时那一副):

```
 * findSubject/subject-image/subject-copy 全按 id 取首位,后面几位按 id 够不着;而两端选人闸按位筛(ids.has(s.id)),
 * 点名一个 id 跑一次批量补图,库里重复几位就登记几笔生图钱
 * (那几笔各落各的位:exec subject.generateImage 点名子集与整库两档都按 nthSubject 逐位写回、几位各得一张图,
 * 浏览器同名命令写的就是循环里那一位;按 id 点名单位的 subject-image / subject-copy 仍走 findSubject,写回的只有首位)
 * ——本命令是把这批存量收拾干净的那条路。
```

两处动作与镜头侧那次逐格同形:
「后面几位**结构性**够不着」改成「后面几位**按 id** 够不着」(原句主语就是那三个取数口,
读作全局论断即与「几笔钱几位各得一张图」自相矛盾;限定语一加,两句读的是同一件事的两面),
再把那几笔钱**各落到哪一位**按 §2.1 的读数补成一段括注。

段内后半(`引用面有意一个字不动…改 id 的只有那些任何引用都指不到的后续位`)一个字没动:
它说的是**引用面**,而 `nthSubject` 是批量循环回最新树上按序数重取自己那一位、不是谁对谁的引用;
去重只改后续位的 id,批量补图照旧按序数逐位跑得到,那句话与新补的括注不冲突。

4. **主体侧那一路同形的空缺**:§2.1 ⑤ 那格(`subject-copy` 按 id 取源落首位)现取同样只在一次性脚本里量过,
   树上没有它的判据。与第 3 条同形,一并留给判据面那一槽。
5. W302/W303 起仍活着的那几条,本槽一条没代修、原话逐条保留:
   - **发现存量重复仍得先走到主体库那一页或分集工作区顶栏**;整树导入/恢复与 `state-put` 照旧能写进重复 id

     合并成一份模板的代价比 W306 记的时候再高了一点点。

## 十、这一槽可复用的一件事

**同一句话在树上散着几份时,「上一槽判过准」不等于「这一处判过」。**
本槽 §3.2 / §3.3 收的那两份镜头侧措辞,与 W305 §3.2 亲手改准的接入指南那句是同一句话,
而 W305 §四 那张全树扫描表里没有它们的行——扫描的词表命中得到,是那一遍漏了。
判「同类假话」时,词表扫出来的每一处都要在表上占一行(哪怕结论是「准」),
表里缺的那几行不是「判过留下的」,是没人看过的:下一槽读这张表时无从分辨这两者。
配套的做法是把**同一句话的所有副本**先按锚点句聚成一组再逐份判,
而不是按文件逐处判——本槽 `cli.js` 两份 + `README.md` 一份 + 接入指南一份,正是一组四份。
