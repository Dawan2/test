## 2. 读完的实况:两步收尾时手里有什么

### 2.1 生成(批量生成视频)

两端收尾处的结构化回执逐字段相同(`js/commands.js:99` / `cli.js:1027`):

| 字段 | 含义 | 判定输入 |
|---|---|---|
| `total` | 本轮待处理镜数 | `shots.filter(!final && !shotVideoReady)`,再按 `shotIds` 子集收窄 |
| `ok` | 本轮出片成功镜数 | `Domain.shotVideoReady`(在线时离线模拟占位不算) |
| `failed[]` | 失败镜(`shotId`/`order`/`error` 截 80 字) | `s.video.status === 'failed'` |
| `skipped[]` | 未确认被跳过的镜 | `!s.confirm` 且未 `confirmAll` |

都是已落盘的结构化字段,**都可判定**。任务给的三个候选里前两个(本集成功镜数、失败镜数)就在这里。

### 2.2 合成(合成成片)

合成是**零 LLM 步**(浏览器 `js/sb-io.js:455 doCompose` 走 `Media.ffCompose`、任务登记的 `model` 就是 `本地合成`;
CLI `cli.js:915 composeCore` 走 `POST /api/ffmpeg/compose`)。成功收尾处能拿到的比"是否落盘"多得多:

| 字段 | 含义 |
|---|---|
| `r.count` / `items.length` | 实际拼接段数(与本集镜数的差额 = 无任何素材被跳过的镜) |
| 静帧代替段数 | `shots.filter(!shotVideoReady && image)`——这些镜以分镜图入片 |
| `ep.composedSrt` | SRT 软字幕是否产出(无对白/旁白则为 `null`) |
| `ep.composedAudio` | `Domain.audioRenderList().summary`:`mixed`/`offline`/`stale`/`missing` 四个数 |
| `ep.composedInputHash` / `composedDialogueSig` / `composedSourceRev` / `composedGraphRev` | 判旧指纹四件套 |

任务给的第三个候选(成片是否落盘)在这里,而且这一堆里它是**信息量最小的那个**——见第 4 节。

## 3. 否决的四条理由(逐条带取证)

### 3.1 决定性的那条:这两步没有自己的提示词,回流下去没有读者

W61 之所以敢一次接四步,是因为它的 `scope` 一律取 `WfCore.WF_BOARD` 单源,而那正是**同一步的提示词召回记忆时用的同一个键**
——"回流下去下一轮同一步吃得到"因此是结构上保证的,不靠约定。这条保证在生成与合成两步上直接不成立:

```
WF_BOARD = {understanding:'导演', 'smart-storyboard':'分镜', 'smart-review':'成片',
            'extract-subjects':'主体', 'split-episodes':'剧本'}   ← 五个键,没有生成、没有合成
```

- **合成**零 LLM,全链没有一句提示词,谈不上"下一轮同一步召回"。
- **生成**用的是镜头自己的 `s.prompt`(经 `Domain.buildVideoRequest` 装配),这条链上**没有任何 `memBlock` 调用点**
  ——全仓 `memBlock` 的消费点只有理解/分镜/审片/拆集/提取主体五个 wf 步与 Agent 对话(`server.js:3334/3373/3412/3426/3532/3592/3655/3721`、
  浏览器 `js/agent.js:265`、`js/review.js`、`js/episode-util.js`、`js/proj-upload.js`)。

所以 `生成`/`成片` 两个板块的回流条目只会落到两个**旁路**:Agent 对话(3.2 节)与专家蒸馏(3.4 节)。
这与前六步的情形有本质差别:前六步回流的条目会回到**产生它的那一步自己的提示词**里,形成闭环;这两步不会。

### 3.2 唯一的旁路已经在同一份提示词里喂了实时的同一批数字

`生成` 板块的记忆只有 Agent 对话会召回(浏览器 `js/agent-global.js:389` 按 `AC.gBoard.key` 召回、
服务端 `server.js:3712-3721` 按请求 `scope` 召回)。而**同一份提示词的 user 半本来就带一段实时状态摘要**:
浏览器 `AO.stateBlock`(`js/agent-ops.js:452`,四个调用点:`js/agent.js:463/491`、`js/agent-global.js:583`、`js/agent-ops.js:134`),
headless `WfCore.agentStateText`(`js/wf-core.js:768`,`/api/wf/agent` 的 `buildAgentUser` 里)。

同一集(10 镜:6 成功 / 2 失败 / 2 未确认)下并排实测:

```
--- 两端 Agent 对话提示词里本来就有的实时行 ---
★ 工作台状态(第一集):共10镜/6已出片/2失败/2未生成/2待确认;下一步:处理失败镜

--- 假如按 W61 同结构给「生成」步写一条回流,它会长这样 ---
生成闭环回流·第一集:本轮出片 6/8 镜;失败 2 镜(已退费);跳过未确认 2 镜

--- 假如按同结构给「合成」步写一条回流 ---
合成闭环回流·第一集:成片已落盘,拼接 8 段;字幕 SRT 已产出
```

实时那一行**包含了回流那一行的全部内容**,还多给了 `2未生成` 与 `下一步:处理失败镜`;
更要紧的是它是 live 现算的,而回流条目是上一轮跑批那一刻的快照——用户单镜重抽修好两个失败镜之后,
实时行会变成 `8已出片`,回流行仍写着 `失败 2 镜`。两行会**并排出现在同一份提示词里**,后者只会让模型在两个互相矛盾的数之间挑一个。
这就是 W61 说的"噪音副本",但位置比它写的更具体:不是"与发布门重复",是**与同一份提示词里紧挨着的那一行重复且更旧**。

失败镜这一面还有第三处实时判定:问题中心 `js/issues.js:169` 的 `failed-shots`,`high` 危、
`detail` 逐镜带失败原因(每条截 36 字,最多 4 条)、并挂 `cmd: 'episode.generateVideos'` + `shotIds` 一键重试。
"上一轮为什么失败"这个唯一看起来只有回流才留得住的面,在失败**仍成立**时问题中心已经逐镜给了;
失败被修好之后它就是已解决的历史,而回流的用处按 W61 定的口径是"上一轮做到什么程度、还差什么",不是"上一轮出过什么事"。

### 3.3 合成这一步已经有自己的结构化回执落盘,回流是同批字段的第二份副本

审片之所以该回流,是因为 `ep.lastReview` 虽然落了盘,但**下一轮的审片提示词不会去读它**,只会读记忆桶。
合成不一样:`composed` / `composedAt` / `composedUrl` / `composedSrt` / `composedAudio` / `composedInputHash` /
`composedDialogueSig` / `composedSourceRev` / `composedGraphRev` 就是这一步的结构化回执,而且**已经有一整圈现成读者**
——`Domain.epComposedReady`(判旧)、`Domain.workflow` 的 `film` 步、问题中心 `composed-stale`(`js/issues.js:196`)、
发布门 G1、成片库与版本对比。往记忆桶再抄一份,不多一个读者,只多一份会过期的副本
(成片判旧之后,`epComposedReady` 会翻成 `false`,而记忆里那句"成片已落盘"不会跟着翻)。

### 3.4 写下去有三处可量化的负作用

**(a) 成片板块的召回窗会被稀释。** `memRecall` 的同板块优先段是 `filter(scope).slice(-4)`(`js/wf-core.js:131`),
而合成的板块只能是 `成片`(`WF_BOARD['smart-review']`)——正是 W43 放审片回流的那个板块。四集项目实测:

```
现况(成片板块只有审片回流)——下一轮逐镜审片提示词召回到:
- 审片回流·第1集 / 审片回流·第2集 / 审片回流·第3集 / 审片回流·第4集

若合成也回流到成片板块——同一份提示词召回到:
- 审片回流·第3集 / 合成回流·第3集 / 审片回流·第4集 / 合成回流·第4集 / …
```

优先段里的审片条目从 4 条掉到 2 条,换进来两条**审片提示词用不上**的合成流水。这是净负收益。

**(b) 50 条上限会提前 6 集开始挤掉用户自己沉淀的偏好。** 记忆桶是全局的(`state.agentMemory`,不分项目),
`memWrite` 超上限按 `slice(-MEM_MAX)` 从头截。现况每集占 3 个回流键(`und`/`sb`/`review`)+ 每项目 3 个
(`split`/`extract`/`release`),再加两个每集键就是每集 5 个。实测两种口径下"用户自沉淀条目开始被挤掉"的集数:

```
现况(每集 3 键:und/sb/review)  → 第 16 集起开始挤掉用户自沉淀
若再加生成+合成(每集 5 键)      → 第 10 集起开始挤掉用户自沉淀
```

W61 明写回流"不刷满 50 条上限挤掉用户自己沉淀的偏好",按键原地更新只挡住了"同一集反复跑"这一路,
挡不住"集数变多"这一路(见第 5.2 节——这是本槽顺带核出的一处**已存在**的问题,不是本槽引入的)。

**(c) `生成` 板块的条目会成为制片主任专家的蒸馏输入。** W65 之后 `evolveExpert` 的记忆源按该专家的生效板块硬过滤
(`WfCore.expertBoards` + `WfCore.memForBoards`),在 `生成` 板块被雇佣的专家会拿到该板块的全部条目去蒸馏 `persona`。
纯跑批遥测("上一轮 8 镜出 6 成功")蒸进人设,是往方法论里灌项目统计——W65 把蒸馏收窄到板块,正是为了让蒸馏输入干净。

## 4. 任务点名的三个候选逐个判

| 候选 | 可判定? | 有读者? | 判定 |
|---|---|---|---|
| 本集成功镜数 | 是(`ok`/`total`) | **无新读者**。唯一旁路的同一份提示词里,`stateBlock`/`agentStateText` 的 `N已出片` 实时给同一个数,口径同源(都从 `Domain.episodeState` 出) | 否决:同一提示词内的更旧副本 |
| 失败镜数 | 是(`failed[]`) | **无新读者**,且实时面比回流面更全:同一提示词的 `N失败`、问题中心 `failed-shots`(high,逐镜带原因 + 一键重试)、发布门 G6 | 否决:三处实时判定的更旧副本 |
| 成片是否落盘 | 是,但在"成功收尾"这个位置上**恒为真** | 有意义的不是"落没落盘"而是"落的这份还算不算数",那是 `Domain.epComposedReady` 的 live 推导,回流一个布尔反而会在成片判旧后继续说"已落盘" | 否决:常量不是结论 |

另外把第 2.2 节那几个"看起来还没人判"的合成字段也过了一遍,结论一致:
静帧代替段数与拼接段数都是 live 可推(`Domain.composeSeqOf` + `shotVideoReady`);
`composedAudio` 的 `mixed`/`offline`/`stale` 已经**逐字段落在 `ep.composedAudio` 上**(两端同口径写回),
现取一次就有,不需要第二份;SRT 有无同理(`ep.composedSrt`)。三者都落回第 3.3 节那条。

**什么情况下这三个数会重新变成该回流的?** 见第 7 节——判据不在"数字够不够硬",在"这两步有没有长出自己的提示词"。

## 5. 顺带核出的两处记账不准(本槽不改,登记在此)

### 5.1 SK-04 `note` 里"归发布门 G3/G7"这个指认不对

`js/skills.js:962` 那句括号写的是"素材产出的判定面归发布门 G3/G7"。实测两端门表:

```
g1-workflow | 主线步骤全完成      g3-review     | 审片均分 ≥ 7
g4-stale    | 过期镜=0            g5-unconfirmed| 未确认镜=0
g6-failed   | 失败镜=0            g9-subjects   | 主体图齐全=0缺图      g10-billing | 计费账目核对
```

G3 判的是**审片均分**(`js/release-core.js:51`、`js/release.js:96`),G7 判的是**合规敏感词**(`js/release.js:152`,
headless 七门里根本没有 G7)。真正判素材产出的是 **G4/G5/G6**(过期镜/未确认镜/失败镜),外加问题中心的 `failed-shots`。
结论不受影响(那句话的落点"这几个数已经有人实时判"仍成立,而且判得比它写的更多),
但门号写错会让下一个读者按 G3/G7 去查、查不到而以为这条余量没核过。

**本槽不改它**:任务在否决分支上明写"不要空改代码",且 `tests/unit.js:7699` 的锚点是 `['生成与合成', '解析向导']`
两个字面、与门号无关,改门号是纯措辞订正。留给下一个**正当碰 `js/skills.js`** 的槽顺手改成
「素材产出的判定面归发布门 G4/G5/G6 与问题中心 `failed-shots`」;若那时想把理由也换成本槽第 3.1 节那条,
注意 `仍欠` 段里必须保住 `生成与合成` 这四个字,否则上面那条用例当场红。

### 5.2 回流条目会随集数增长挤掉用户自沉淀(已存在,非本槽引入)

第 3.4(b) 的实测顺带证明:现况下**16 集起**回流条目就会把用户自己"记住…"沉淀的条目挤出 50 条桶。
`memWrite` 按 `fb` 原地更新解决的是"同一集反复闭环不双写",解决不了"集数一多键就多"。
本槽不动它(不在范围内,且改法有多种:按 `fb` 前缀限每类保留最近若干条 / 淘汰时优先淘汰带 `fb` 的 / 上限按项目分桶),
但要接 SK-26 的下一个槽应当先看这一处——**它比"再加两步回流"重要得多**。

## 7. 交接:这条余量在什么条件下才该翻面

**不要**因为"六步都回流了,就差这两步"去补齐它——覆盖面的整齐不是目的,有读者才是。翻面的判据只有一条:

> 生成或合成这一步长出了**自己的、会按板块召回记忆的提示词**。

具体可能的触发点有两个:

1. **生成侧长出提示词编排步**。目前 `s.prompt` 是分镜步产出的、由 `Domain.buildVideoRequest` 装配的;
   若将来出现"按上一轮出片结果自动改写生成参数/提示词"的 LLM 步(那会是一个新的 wf 端点 + 一个新的 `WF_BOARD` 键),
   届时"上一轮 N 镜失败、失败集中在哪几类提示词"就有了**产生它的那一步自己的读者**,回流才成立。
   注意那时该回流的多半也不是"成功 N 失败 M"这个总数,而是失败与提示词特征的对应关系。
2. **合成侧长出剪辑决策 LLM 步**。合成现在是纯 FFmpeg 拼接;若将来转场/节奏/取舍由 LLM 决策,
   "上一轮几段用静帧代替、几镜配音是离线占位"就变成那一步的下一轮输入,回流同样成立。

在此之前,这两步的正确做法是**继续走实时面**:数字要看就现取 `Domain.episodeState` / `Domain.audioRenderList`,
问题要处置就走问题中心的 `failed-shots`(带一键重试)与发布门 G4/G5/G6。

另外三条留给接手人:
