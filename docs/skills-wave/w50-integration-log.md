## 4. 三类冲突的解法

### 4.1 长行 README:取基线侧 + 按 word-diff 折回对侧增量,折回前先查非冲突区

两份 README 里几条上千字的长行每一槽都会撞。沿用 W29 起的口径:

```
git diff --word-diff=porcelain --word-diff-regex='[^,。;:、()「」`]+' <分支base> <分支head> -- README.md
```

拿到对侧的**逐词增量**,取基线侧那行,再把这几条按语义插回去。**不用 `git checkout --ours`**:那会把对侧增量整行丢掉,而且丢得无声无息。

本槽真正需要折回的只有一条:`w46` 往 `plans.js` 的单测描述里插的那段(`fromWorkflow` 按投影推导、`Plans.projection()` 自省表、两步不占计划步、需授权状态出导航步不预设 `args`)。

其余增量**都在非冲突区自动合进来了**,按 W47 4.2 那条口径,折回之前先在整份文件里搜了一遍关键词逐条查证:

| 对侧增量 | 查证方式 | 结论 |
|---|---|---|
| `w46`:MCP 工具数 31 → 33 + `hujing_playbook` 那句 | 在 `README.md` 搜 `33 个` / `hujing_playbook` | 已自动合入,**不折回** |
| `w46`:`docs/AI助手接入指南.md` 同一处两行 | 该文件整份自动合并,`git status` 显示 `M` 无 `UU` | 已自动合入,**不折回** |
| `w49`:注册表 10 条 → 11 条(两份 README 各一处) | 搜 `11 条注册表提示词`(得 1)与 `10 条注册表提示词`(得 0) | 已自动合入,**不折回** |
| `w49`:`agent.system` 收编那段说明 | 搜 `agent.system`(得 3 处) | 已自动合入,**不折回** |

四条全部命中"已自动合入",一条都没有重复折回。W47 那槽是**写重了一条才发现**这个坑,本槽把它当检查表用在了折回之前——这条口径的成本是四次 `grep`,收益是零重复。

### 4.2 「一侧对、一侧是它分叉时的旧实况」:数字往回退的那一侧一定不对

这跟 W47 4.3 的「两侧字面都不对」是**不同**的形态。本槽 `docs/skills-wave/README.md` 那块摘要冲突里,对侧(`w46`)写的是:

```
`Skills.playbook('core.playbookProjection')` 从 `null` 变成九步、`playbooks()` 从三条变四条,……
- `WfCore.memRecall/memBlock` 有了直接单测(memory 套件 6 条),……
```

基线侧写的是「从 `null` 变成九步」(没有"从三条变四条"这半句)与「memory 套件现 12 条」。

两处都是**基线对、对侧旧**:`w46` 叉自 `b86ead5`,那时 `w43` 的 SK-26 回流面还没并进来,所以它看到的 `playbooks()` 是四条、memory 套件是 6 条;并入后实测 `playbooks()` **五条**(`core.playbookProjection`/`eps.frontPipeline`/`review.reviseLoop`/`review.memoryFeedback`/`film.produceProjection`)、memory 套件 **12 条**。基线侧因此有意删掉了"从三条变四条"那半句(数字一槽一变,写死了就得一槽一改)。

按"对侧增量要折回"的惯性,很容易把这两个数字一并折回去,那就是**把已经收敛过的实况改旧**。

> **口径**:冲突两侧的数字**不一致且对侧更小**时,先问"对侧的分叉点在哪一槽"。叉点早于某次增量的分支,它带的是那次增量之前的旧快照;这种"增量"不是增量,是回退。判据仍然是**并入后现跑一遍取实况**——本槽 `playbooks()` 与 memory 套件条数都是现跑出来的,不是从两侧字面里挑的。
>
> 同一条口径的反向用法:`w49` 那次冲突里,对侧在回归测试长行上**只差用例数**(它的 371/375/376 都是自己那条分支的实测),word-diff 出来除数字外零增量,那就干脆整行取基线侧、一处都不折回,再让 `contract` 断言把用例数报出来。

### 4.3 并入让非冲突区的散文过期——没有断言兜底,只能通读

W47 4.4 记的是「自动合并的**断言**下限被并入抬松」。本槽撞到的是它在**散文**上的对应形态,而且更麻烦:断言至少还会红一次,散文不会。

两处都在 `docs/skills-wave/README.md` 那条「记账诚实位」长行里,都**在非冲突区、都自动合并、都因为并入而不再成立**:

**第一处**(合 `w46` 之后)。基线侧写着:

```
`G-11`(自进化)与 `G-12`(计划步骤/流程模板两处投影)按关联索引口径仍挂在各自条目上。
```

`w46` 落地的恰好就是"计划步骤"那一半,它自己的 `js/skills.js` `note` 也如实改成了「G-12 仍挂账:MCP 流程模板补主线中段那一半未动」——但 `note` 的改动在代码里、这句散文在文档里,两边不在同一个冲突块,`git` 不会提醒。按并入后的实况改为:

```
`G-11`(自进化)与 `G-12`(投影落点)按关联索引口径仍挂在各自条目上——
```

**第二处**(合 `w49` 之后)。同一行里 W45 那段结尾写着「SK-03 的仍欠段换成 Agent 单轮对话步(人设句与 ops 协议同写在 `WfCore.buildAgentSystem` 一个模板串里)」——`w49` 落地的恰好就是这一处。按它自己 `note` 的实况补了一句「**W45 点名的那处余量随 W49 收掉**」,并把仍欠段跟到新的一处(浏览器多轮对话面板的分集面板 / 全局抽屉 / 预排模式三份措辞);同时点明**只人设句可覆盖**,其后的 ops 协议 / 命令白名单 / 返回 JSON 约定仍由 `wf-core` 拼,那半是 `agentNormalize` 的解析契约、不开放改写。按 2.3,这一句**不挂记账件链接**。

## 5. 没删测的取证

### 5.1 名集比对:并集与合并后**逐条相等**

按 W29 起的做法,用**用例名集合**而不是数字证明没删测:从两条分支与基线各跑一遍 `tests/unit.js`,取运行器打印的 `PASS|FAIL | <套件> · <用例名>` 去重排序,与合并后的名集比对。

| 来源 | 用例数 |
|---|---|
| 基线 `w47 @ 8366727` | 375 |
| `w46-g12-playbook-proj-deb4` | 371 |
| `w49-agent-system-prompt-96c0` | 376 |
| 三者名集**并集** | **380** |
| **合并后主干** | **380** |

两向差集**都为空**(`comm -23` 与 `comm -13` 各跑一遍,均无输出),即三条名集的并集与合并后主干**逐条相等**。这是这一系列集成槽里第一次不需要解释差集:W47 那槽的并集比合并后多 3 条(全是基线早已改名的旧名),本槽两条候选分支的叉点(`b86ead5` 与 `8366727`)都**晚于** W35 的七面改名与 W39 的 note 翻面,带的是改名后的快照,故一条旧名都没有。

> **口径**:差集为空是好结果但不是必然结果,别把它当成"名集比对可以省掉"的理由——差集为不为空取决于候选分支的叉点落在哪次改名之前还是之后,这跟"有没有删测"是两件事。要证的始终是**并集里的每一条都能在合并后找到(同名或指得出现名)**。
