## 四、棘轮格的第三种合法路径:两侧改成**同一个值**,git 一个冲突都不报

五个棘轮格逐格现取四棵树,加上它们在根 README 里的孪生数字:

**本槽最值得抄走的一格在第一行。** W237 把这类格分成两种偶然:自动取对侧取对了的,靠"另一侧没动过";
报了冲突的,靠"两侧都动过"。本槽出的是**第三种:两侧都动过,而且动成了同一个值**——
git 视之为同一处改动,连冲突都不报,直接把 654 合进去,而合完的 live 是 655。

这一格**没有任何棘轮判据接住它**:`live >= floor` 成立,差额 1 格在 `SLACK = 3` 的预算内。
接住它的是它在根 README 里的孪生数字——那个数走的是**相等**那一层(文档明写数必须等于实测,不许落后),
于是原始 merge 树跑出来恰红 1 条:

```
FAIL | contract · README 数字对账:单元测试用例数由 tests/unit.js 实计(套件表求和)
      | 单元测试用例数:README.md 与实测不符(实测 655,文档 654):期望 "655",实际 "654"
```

**读这条报错的人被指向的是 README 那个数,不是 `FLOOR`。** 把红的那一处改掉(README 654 → 655)、
`FLOOR` 留在 654,整套 `141/141` 全绿(第六节反事实第二档实测)。也就是说:

> 上一槽刚写进明面的那条口子,在它落地后的**头一次合入**里就现形了,
> 而且是以一种 W236 自己没记的机械形状——不是"抄了偏低的某一侧",是"两侧抄成了同一个偏低值"。

W236 量的是"冲突解里抄某一侧"这一路,前提是**有冲突**。本槽这一格连冲突都没有,人工复核的入口
