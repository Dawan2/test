# W121 · 三套件用例数棘轮:unit / integration / cli.smoke 各钉一条「只增不减」下限

> 槽位范围:`tests/unit.js` 的 `contract` 套件新增 1 条用例 + 抬 1 个既有下限字面,`README.md` 同步三处数字与口径,本记账件加索引行。
> **零产品代码改动**(`js/`、`server.js`、`cli.js`、`mcp.js`、`billing.js` 一行未改),不动发布门口径、不新增计费动作、**不删任何用例**。
> 基线 `cursor/w117-integration-8b2d` head `9adcf0f`(未合 W113/W119/W120)。

## 1. 病灶:对账钉的是"相等",而删测的人两边一起改

W102 把 `integration` 与 `cli.smoke` 的用例数收进 `contract` 对账(见 `w102-ledger-assert-smoke-int.md`),
连同 W23 立的单元用例数那条,三个套件的数字此后都由代码实况反推、写错即红。

这层契约拦得住的是**单侧改**:改文档不改代码红、改代码不改文档红。拦不住的是**双侧一起改**——

真删掉 `tests/integration.js` 里一行 `report(...)`,再把 `README.md` 的 `130` 改成 `129`,
实测数与文档数仍然相等,W102 那条一个字不报;`tests/cli.smoke.js` 与单元套件同理。
也就是说**"没人删测"这件事,在三个套件上至今没有任何机器判据**,靠的仍是评审时人去看 diff。

这不是假想:一条用例被删掉与一条用例被改写(改判据、改夹具)在 diff 里长得很像,
而数字栏两边同步改过之后,全绿的测试结果会给出"这一改没动任何契约"的错误背书。

## 2. 落地:三条下限,实测与文档分开各钉一次

新增一条用例,接在既有那条「集成测试与 CLI 冒烟用例数由各自套件源码实计」之后,**既有断言一条不删、一字未改**。

| 套件 | 取数口径 | FLOOR |
|---|---|---|
| `tests/unit.js` | `SUITES` 套件表求和 | **476** |
| `tests/integration.js` | 行首 `report(` 的行数 | **130** |
| `tests/cli.smoke.js` | 行首 `report(` 的行数 | **102** |

三个 FLOOR 都是**本槽合入时的 live 条数**(unit 的 476 已含本槽新增这一条)。判据两句:

1. **实测数 >= FLOOR** —— 少一条用例当场红,报的是"用例被删了",与文档写什么无关。
2. **README 明写数 >= FLOOR** —— 把文档数字改小来迁就删除时红在这一句;
   那句话被整段删掉同样算红(沿用「找不到该数字表述即红」的口径),否则删掉措辞即可绕过下限。

两句分开钉,是为了单看报错就知道被改小的是哪一侧:只删测不改文档时,第 1 句与 W102 的相等那条一起红;
两侧一起改小时,第 1 句红而相等那条绿——报错本身就说明了"这是一次同步改小"。

抬下限的规矩与记账件份数那条一致:**新增用例的槽把 FLOOR 抬到当轮实况**;
确要删测的槽得先动这个字面,而动它就必须在记账件里说明理由,不再是"两处数字各改一位即静默通过"。

### 2.1 为什么不并进 W102 那条,也不与循环禁令混成一句

`contract` 里已有一条「每条用例须是独立一行的 `report(...)` 调用」——它报的是**登记形态被破坏**
(`report` 塞进循环或回调后,一行会跑出多条,静态点数不再代表实跑条数)。
本槽这条报的是**用例被删了**。两件事的处置完全不同:前者要把那一行拆回逐条登记,后者要么恢复用例、要么在记账件里给出删除理由。
合成一条断言会让报错文案必须同时描述两种病灶,读的人得先自己分辨中了哪一种——故分开成条,一条一个失败含义。

同理也没有把下限塞进 W102 那条 `forEach` 里:那条循环体的每一轮都要跑相等断言,
下限混进去之后,报错行号一样、用例名一样,失败含义又糊在一起。

### 2.2 `tests/e2e.js` 仍在对账与下限之外

`e2e.js` 按 tab 列表循环登记用例(`for (const t of TABS) { … report('项目tab·' + t, …) }`),
**行首 `report(` 的行数本就不等于实跑条数**——README 写 63 项断言而行首点数只有 56 行。
这个差额是真实的,不是文档写错;给它设下限等于给一个假值设下限。
要把它收进来得先把那个循环里的用例改成逐条登记,超出本槽范围。
另按目录纪律,`node tests/e2e.js` 只在用户明确要求时跑,本槽没跑。

### 2.3 顺带抬的那个字面

`docs/skills-wave` 记账件份数那条下限(同一套件里既有的 `FLOOR`)按它自己写明的规矩
「新开一槽记账时把下限抬到当轮实况」从 `132` 抬到 `133`,对应本记账件这一份。
只改这一个数字,该条其余判据一字未动。

## 3. 变异验证(五条,逐条实测:前四条转红,第五条验"只增仍绿")

| 变异 | 结果 |
|---|---|
| 1. 删 `tests/integration.js` 一行 `report(...)`,README `130` → `129` | 红 **1 条**:`集成测试用例数不得少于 130(实测 129)`;W102 那条相等断言**仍绿**——正是本槽要接的场景 |
| 2. 删一行 `report(...)`,README 不改 | 红 2 条:下限那句 + W102 的 `实测 129,文档 130`(单侧改本来就拦得住) |
| 3. 只把 README `130` → `129`(不删测) | 红 2 条:`README.md 写的 129 低于下限 130` + W102 的相等那句 |
| 4. 删一条单元用例(`tasks` 套件首条),README `476` → `475` | 红 1 条:`单元测试用例数不得少于 476(实测 475)` |
| 5. `tests/integration.js` 真加一行 `report(...)` 并同步 README 到 `131` | 全绿(只增仍绿,棘轮不挡新增) |

变异 1 是本槽唯一真正新接住的那一个:同一改法在基线上(`w117` head 的独立 worktree 里逐字复现)
**475/475 全绿、一条不报**,而在本槽红且只红这一条。

## 6. 交接

1. **下限只覆盖用例数,不覆盖判据强度**:把一条用例的断言体掏空成 `assert(true)`,条数不变,本槽这条不报。
   要接这一面得另立"判据密度"口径(比如每条用例至少一处 `assert`),那是另一个槽。
2. **`tests/e2e.js` 的 63 仍在对账与下限之外**,原因与代价见 2.2——要收它得先把 tab 循环里的用例改成逐条登记。
3. **抬 FLOOR 是新增用例的槽的义务**:三个数字散在同一条用例里,新增用例后不抬下限不会红(只增仍绿),
   但下一次真删测时下限就只挡到旧水位。判据不可能替人抬,故写进这里备忘。
4. 三个 FLOOR 的字面在 `tests/unit.js` 同一条用例的表里,改一处即可,不必翻 README。
