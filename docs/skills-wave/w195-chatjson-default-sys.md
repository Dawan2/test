# W195 · `chatJSON`/`chatJSONRobust` 的缺省人设「你是专业助手。」:停工位不成立(零产品代码改动)

一句话结论:**停工位不成立**,故**不收进提示词注册表**,产品代码一行不改。

那句缺省确实会**原样进 system 位发到上游**(第 2.1 节实测),但**没有一个生产调用点会走到它**——
`js/` 全量 42 个调用点**逐点都显式给了 `system`**,省略的 0 处(第 2.2 节)。
「用户覆盖不到」这半句在字面上成立(它不在注册表),但它够不到任何一次真实请求:
42 个调用点的人设句**全部最终取自注册表**(31 处 `Prompts.get`/`fill` 直取、5 处经 `WfCore` 装配口、
6 处经本地装配口或基对象,末端仍是 `Prompts.get`),用户在「全局默认值 → 核心提示词 skill」改的正是这些。
覆盖表也造不出「`system` 变空从而踩中缺省」的旁路(第 2.3 节)。

所以这一处是**层内兜底**,不是产品面的可覆盖项。本槽按停工纪律不改产品码,
把上面三面 live 落进 `tests/unit.js`(+1 条,三面九句断言),
让「它打不到上游」此后由判据接着——**新加一个不给 `system` 的调用点即红,那一刻停工位才第一次成立**。

**基线**:`cursor/w189-integration-5b9b` 的 `a895ab8`。W187–W194 各支一律未取(含在飞的合入员与 smartReview 槽)。

## 1. 停工位原话与它指的东西

W192 澄清:账本 **G-13 / SK-10 / SK-11** 三处「仍欠」段点的不是失败回退,而是这两行:

```js
// js/api.js:176  chatJSON
const sys = { role: 'system', content: (opt.system || '你是专业助手。') + ' 只返回纯 JSON,…' };
// js/api.js:199  chatJSONRobust
const sysMsg = { role: 'system', content: (system || '你是专业助手。') + ' 只返回纯 JSON,…' };
```

既有判据(`contract` 套件那条全仓内联人设名单)只钉住两件事:**这两处还在**(`|| '你是专业助手。')` 计数为 2)、
**它还没进注册表**(`def === '你是专业助手。'` 命中 0 条)。两条都是"现状还在"的正向断言,
**没有一句说它到底会不会被发出去**——停工位要问的正是这一句。

## 2. Live 举证(基线 `a895ab8` 现跑,数字全部实测)

### 2.1 第一问:缺省会真发到上游吗——会

`vm` 沙箱装真源码 `js/api.js`,截住底层 `API.chat` 读 `messages[0].content`:

| 入参 | 实际发到上游的 system 位 |
|---|---|
| `chatJSON({ messages })`(不给 `system`) | `你是专业助手。 只返回纯 JSON,不要输出 markdown 代码围栏或任何解释性文字。` |
| `chatJSONRobust({ user })`(不给 `system`) | 同上,逐字节一致 |
| `chatJSON({ system: '', … })`(给空串) | 同上——`\|\|` 判的是真值,空串同样兜底 |
| `chatJSON({ system: '你是分镜师。', … })` | `你是分镜师。 只返回纯 JSON,…`,一字不垫 |

**这一问答"是"**:缺位时它不是个死字面,是真会进请求体的人设句。

### 2.2 第二问:哪些调用路径省略 `system`——**一个都没有**

全量扫 `js/`(70 个文件),按实参形态分类。42 个调用点:

| 形态 | 处数 | 落点 |
|---|---|---|
| 实参对象字面量顶层直给 `system:` | 39 | 见下表分布 |
| `Object.assign({}, X, {…})` 的基对象 `X` 顶层给了 | 2 | `js/agent.js:498`(`llmOpt`)、`js/agent-global.js:397`(`llmOptG`) |
| 整参透传(`opt => API.chatJSONRobust(opt)`) | 1 | `js/understanding.js:8`,`system` 由它那 5 个上游调用点决定,5 处都在上表里 |
| **省略 `system`** | **0** | — |

39 处直给的 `system` 值按取数口分:

| 取数口 | 处数 | 例 |
|---|---|---|
| `Prompts.get(key)` / `Prompts.fill(key, …)` 直取 | 31 | `review.system`、`split.system`、`beat.system`、`persona.editSystem`… |
| `WfCore.*System()` 装配口(人设句仍是 `Prompts.get`,其后按键接 KB 方法论段) | 5 | `sbSystem` / `extractSystem` / `optimizeSystem` / `genPromptSystem` / `evolveSystem` |
| 本地装配口(末端同样是 `Prompts.get`) | 3 | `Experts.FORGE_SYS`(`forge.system`)、`prearrPrompt`(`agent.previsSystem`)、路由步 `sys`(`agent.routeSystem`) |

两个 `Object.assign` 基对象也是这一类(`panelSystem` → `agent.panelSystem`、`buildGlobalPrompt` → `agent.drawerSystem`)。
**42 处一处不漏,人设句末端全在注册表里。**

方法论注记:粗判据会给假阳性,本盘点排掉了两类,判据写进夹具注释——
`js/episode-util.js:131` 是注释行里的记账文案(`// R1 收敛:统一走 API.chatJSONRobust(…)`),
`js/director.js:102` 的 `await call({ local: true })` 是 `Commands.execute` 的别名、与本入口无关。
`js/skills.js` 里那两处 `chatJSON/chatJSONRobust` 字面在字符串里(是账本正文),同样不算调用点。

### 2.3 第三问:用户改得到那句「专业助手」吗——改不到,但也踩不着

| 探针 | 实测 |
|---|---|
| 注册表条目数 | **41** |
| 其中 `def === '你是专业助手。'` | **0** 条(它确实不在表里,用户在设置/专家/覆盖表都改不到) |
| `Prompts.get('api.fallbackSystem')`(未登记键) | `''`——收编它必须真加一条注册表条目,不是改个取值口 |
| 把已登记键覆盖成空白(`{'sb.system': '   '}`) | 取值**回落 `def`**,不返回空串 |
| `Prompts.setAll({key: ''})` | 直接**删掉那条覆盖**(恢复系统默认) |

即:覆盖表这条路造不出一个空 `system`,**用户没有任何办法把某一步逼进这句缺省**。
"改不到"与"踩不着"同时成立,于是这个"改不到"没有产品后果。

### 2.4 headless 那半没有同一处兜底

| 端 | 缺 `system` 时的行为 |
|---|---|
| `server.js:1633`(`wfLLM` 装配) | `opt.system` 缺位就只发 `[{role:'user'}]`,**不垫任何人设** |
| `cli.js:1436`(`hujing llm`) | `if (f.system) messages.push(…)`,**不垫任何人设** |

这一格是"不收进注册表"的第二条理由:收了它就是**只有浏览器一端存在的可覆盖项**,
另外两端没有对应物,注册表的双端单一来源口径当场多出一个不对称键。

## 3. 判定

| 停工位自称 | 实测 |
|---|---|
| 「`chatJSON`/`chatJSONRobust` 在调用方不给 `system` 时垫这句」 | **成立**(第 2.1 节),而且真会发出去 |
| 「它不在提示词注册表」 | **成立**(第 2.3 节) |
| 「用户覆盖不到」 | 字面成立,但**够不到任何生产请求**——42/42 显式给,且给的全是注册表里的键 |
| 「所以生产上有一句用户改不了的人设」 | **不成立**。真实请求里这句话一次都不出现 |

**结论:不进注册表。** 理由三条,按分量排:

1. **收了没有消费者**。加一条 `api.fallbackSystem`,用户改它一次也影响不到任何一次请求——
   注册表是"用户改这里、下一次生成就跟着变"的面,放一条改了没反应的键进去,是往用户面上加噪音。
2. **它不是人设,是契约的一半**。那两行真正的作用是把 ` 只返回纯 JSON,…` 这句解析契约无条件缀上去
   (那半按注册表的既有纪律本就不开放覆盖——改坏即整轮解析失败),前半的「你是专业助手。」只是
   契约句不能以空串开头的占位。开成开关就是把契约句的前缀交出去。
3. **双端不对称**(第 2.4 节)。

**G-13 / SK-10 / SK-11 三处记账一个字未动**,`Skills.gaps()` 与 `GUARD_TOPICS` 同样一个字未动:
账本记的"余量还在"按其自身口径**是对的**——那两行确实还在、确实不在注册表。
本槽改的不是账本文案,是给那句余量补上"它打不到上游"这一向的判据;
按"不为了清标记去改 `gaps()` 装清"的口径,标记留着。

## 4. 落地:1 条判据(零产品代码)

`tests/unit.js` `contract` 套件新增 1 条 `API 层 JSON 兜底缺省的可达面:生产调用点一律显式给 system,那句缺省打不到上游`,
配一个顶层夹具 `jsonEntryCallSites()`(判据与例外口径写在它的注释里)。三面分工:

| 面 | 断言 | 转红含义 |
|---|---|---|
| A 上游实况 | 不给 `system` / 给空串两种入参发出的 system 位逐字节等于那句缺省;给了就一字不垫 | 缺省字面被改、或兜底条件被改成 `??` 之类 |
| B 调用面 | 省略 `system` 的调用点名单为空;总处数 42;间接给法三处逐点点名;成员引用名单只许是 `js/agent-ops.js:125` 那行三元 | **新加一个不给 `system` 的调用点**(停工位由此成立)、或新开一个盘点不到的转发口 |
| C 覆盖面 | 注册表零条同 `def`;空白覆盖回落 `def`;未登记键取值为空串 | 有人把它收进注册表(该同轮把本条与既有那两条一起翻面)、或 `Prompts.get` 的回落被改坏 |

B 面的处数与三处点名有意分开写:`Object.assign` 基对象与整参转发这两种形态判起来最容易误绿,
混进一个计数里就看不出是哪一处松了。

## 6. 没碰的面 / 交接

- `listModels` 失败回落(W192 的地)、`smartReview`/`produce` 的 `maxRetry` 候选、`gaps()` 键、`GUARD_TOPICS`:**一个字未动**。
- `review.userSystem` 仍只有一份;没有新造第二份 `FORGE_SYS`(`Experts.FORGE_SYS` 那个 getter 一行未改)。
- **B 面的处数 42 是个要跟着实况走的数**:正常加一个调用点就把它抬到当轮实况(与三处点名一起),
  这不是棘轮下限、没有"只增不减"的语义。
- **本条与既有那两条是一组三向**:那句进注册表的那一天,`|| '你是专业助手。')` 计数为 2、
  `def === '你是专业助手。'` 为 0、本条 C 面的"零条同 def"三句要一起翻面。
- 剩下没做的那半:「要不要允许覆盖这句」这道产品题按本槽 live 已经有了答案(不允许,因为没有消费者),
  但如果日后真有一条链路要在不给 `system` 的形态下发请求(例如某个不属于任何主线步的工具调用),
  正确的做法是**给那条链路自己登记一条注册表键**,而不是把层内兜底开成开关。
