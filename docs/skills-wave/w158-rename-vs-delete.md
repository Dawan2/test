# W158 · 「翻面重写并改名」与「真删掉一条」:给合同一条能分开这两件事的机器判据

> 范围:`tests/unit.js`(`contract` 套件 +2、`blankNonCode` 收一个参数、新增护栏主题清单 `GUARD_TOPICS`)、
> `README.md` 两处数字 + 契约段一句、`docs/skills-wave/README.md` 索引行与明写份数,以及本记账件。
> **零产品代码改动**:`js/`、`server.js`、`cli.js`、`mcp.js` 一行未改;注册表、`gaps()`、面表、`playbooks()`、`CHECKS` 一个数没动。
> **不做**:不禁止给既有用例改名、不动任何一条既有判据、不删任何一条用例、不摘任何一个 `gaps()` 键、不碰计费与发布门。
> 基线 `origin/cursor/w151-integration-2bc5 @ 31d7aeb`(现取核实为该支 HEAD,基线三套件 `unit 520/520`、`integration 141/141`、`cli.smoke 105/107`,`contract` 113)。

## 1. 结果一句话

`w151-integration-log.md` 第 6 节残留 10 登记的那件事——**按名成集比对把「同主题翻面重写并改名」与「真删掉一条用例」报成同一形态**,判哪一种至今零机器判据——本槽给合同一条最小能力:

**护栏主题清单 `GUARD_TOPICS`**:每条登记一道护栏读的那几个**实况取数口**(注册表键 / 源码标识符 / 文件路径片段),判据只问「这条主题此刻还有没有用例在读它」,**用例名一个字都不参与判定**。
改名、挪套件、按新实况翻面重写,只要还读同一份实况就一条不红;真删掉且没有继任者接手时,报的是**主题编号与它的锚点**,不是"少了一条用例"这种数字口径。

判据的两头都在登记时就报出来:锚点写太泛(把别的用例也算成落点)当场红、写太窄(一条都点不到)当场红。清单本身另有一层护着:条数只增不减、编号唯一、每条至少两个锚点、承载用例断言少于两处按"名存实亡"报,取锚点前先抹注释(锚点只写在注释里不算落点)且字面量原样留着——这两条口径各有一句自检断言钉着。

回归 **`unit 522/522`**(`contract` **115/115**)、**`integration 141/141`**、**`cli.smoke 105/107`**(2 项失败与基线逐字同名同表现,分母未动)。

**本槽最值得记下的三件事:**

1. **"分不出来"这句话本槽第一次被量成了两组逐字相同的读数。** 在基线上做两次改动——(甲)把那条 SK-25 护栏改名并另加 1 条无关用例、(乙)把它真删掉并另加 2 条无关用例——两次的按名成集读数都是 **`基线独有 1 条 / 新增 2 条`**,两次都 **521/521 全绿**。
   此前的记录只说"报成同一形态",本槽把"同"落到了逐字相同的两个数上:名集比对里那个 `+N` 混着"真新增"与"改名后的继任者",而**哪一条是继任者、它还覆不覆盖原来那件事,名集本身答不出来**(3.1)。
2. **判据没有做成"禁止改名",而这一点是可测的。** 同一处改名在本槽 tip 上仍是 **522/522 全绿**;把它按新实况翻面重写(名换了、正文重排、读的实况没变)同样全绿;只有真删掉才红,且红的那句点名 `sk25-g03-ledger` 与它的两个锚点(5.2)。
3. **把这张清单原样搬到 W150 那次改名之前的那一版上(`23b7a60`)跑,`sk25` 这条主题在旧名字 `SK-25 仍欠段护栏(G-03 余面)…` 下照样找得到落点、两条新用例都绿。** 即:本槽这条判据**回放到那次真实的改名上不会误报**,而它对真删掉会报——这不是设计意图的重述,是在那一版真实源码上跑出来的(5.4)。

## 2. 病灶:名集比对能看见"少了一个名字",看不见"那件事还有没有人管"

「用例名成集双向比对」是本目录从 W21 起用的零吃测手段,`w114-int-dup-casename.md` 与 `w102-ledger-assert-smoke-int.md` 先后治过它的两个盲区(重名会吃掉一条、两侧去重口径不一致会凭空多报一条),`w151-integration-log.md` 记下第三个:

> 本线第一次有既有用例被改名……由此暴露一件此前没量过的事:"没删测"的按名成集比对,把"翻面重写"与"真删掉"报成同一种形态(都是"只在基线里有的 N 条")。本槽是靠人工逐条核对新旧两条的断言才判定它没被削弱的,**这一步没有任何机器判据**。

那次的具体形态:W136 立的 `contract · SK-25 仍欠段护栏(G-03 余面):…` 在 W150 收敛面落地后被**翻面重写并改名**成 `contract · SK-25 记账两向对账(G-03):…`,覆盖面变大(多出四个消费点的源码形态与跑批档位两层)。名集比对当时报的是"只在基线里有的 1 条 / 只在合并后有的 12 条",而那 12 条里哪一条是它的继任者,只有人读得出来。

### 2.1 名集之外那三条数字判据管的是别的事

仓里此刻拦"删测"的判据有三条,都是**数字**口径:README 明写的单元用例数、`contract` 段自报的条数、三套件用例数下限。它们钉的是"少没少",答不出"少的是不是一道护栏、有没有人接手"——而且三个数一起改小就都不响。基线上逐格实测:

| 在基线 `31d7aeb` 上做的事 | 全套 | 按名成集读数 |
|---|---|---|
| 把那条 SK-25 护栏**真删掉** | 516/519,红 3(两条 README 对账 + 下限) | 基线独有 1 条 / 新增 0 条 |
| **只改它的名字**,判据一个字不动 | **520/520 全绿** | 基线独有 1 条 / 新增 1 条 |
| 删掉它、并把 README 两个数与下限**一起改小** | **519/519 全绿** | 基线独有 1 条 / 新增 0 条 |

第一行与第三行是同一件事(护栏没了),红不红只取决于有没有顺手改三个数字;第二行是另一件事(护栏还在),而它与第三行在名集里的差别只是 `+1` 与 `+0`。

### 2.2 而真实的槽里连这个 `+1`/`+0` 的差别也没有

上面那三行是"这一槽只改这一处"的理想情形。真实的槽都会另加用例,于是 `+N` 那一格混进真新增,`+1` 与 `+0` 的差别当场消失。在基线上各做一次:

| 在基线 `31d7aeb` 上做的事 | 全套 | 按名成集读数 |
|---|---|---|
| 改名 + 另加 1 条无关用例 | 521/521 全绿 | **基线独有 1 条 / 新增 2 条** |
| 真删掉 + 另加 2 条无关用例 | 521/521 全绿 | **基线独有 1 条 / 新增 2 条** |

**两组读数逐字相同,两次都全绿。** 这就是"零机器判据"的实测形态:比对结果、回归结果、三个数字,四处都分不出来,只剩人工读两边的断言。

## 3. 判据怎么选的

### 3.1 不选"禁止改名"

最省事的写法是把用例名钉住(名集只许增不许减)。本槽不这么做,三个理由,前两个有实测:

1. **改名那次是对的。** W150 那次翻面重写覆盖面比旧那条大——旧那条钉的是"两个余面都还欠着",收敛面落地后那句话本身就不成立了,它**只能翻面,不能原样留着**。禁改名等于把"记账随实况改写"这条纪律与"不许删测"这条纪律对立起来。
2. **名字本来就不是判据的载体。** 本目录里用例名要写清"这一条钉的是哪一处"(`w114` 那次改名正是为此),措辞会随实况变;把措辞钉死会让下一个人为了不动名字而把话说得越来越不准。
3. 禁改名也拦不住真正想绕的人:改判据不改名字,名集一样全绿(这一路归"变异转红"那半,不归名集)。

### 3.2 选"主题还有没有承载它的用例"

判据换个问法:不问"这个名字还在不在",问**"这道护栏读的那几个实况取数口,此刻还有没有用例在读"**。

锚点取**实况取数口**而不是消息措辞,是因为翻面重写会重写措辞、但不会改它读的是哪一份实况——`sk25` 那条无论怎么翻面,读的都是 `Skills.byId('review.reviseLoop')` 的那段 `仍欠(G-03)`。锚点因此选注册表键、源码标识符、被读的文件路径片段这三类。

反过来,哪天连它读的实况都变了(比如形态面也落地、`仍欠(G-03)` 整段消失),这条主题会红——那时要改的是清单里的锚点,**且必须有人写下为什么**,这正是本条想要的:主题的存废是一次有记录的决定,不是一次静默的删除。

### 3.3 收哪些主题

本槽登记 **10 条**,都是**记账/欠账类与单源类**护栏——它们钉的是"某份记录与源码实况一致",正是最容易被一句改写抹平、也最容易在翻面时被顺手删掉的那一类:

| 主题编号 | 锚点 | 守的是什么 |
|---|---|---|
| `sk25-g03-ledger` | `review.reviseLoop` + `仍欠(G-03)` | SK-25 的 G-03 两向对账(W136 立、W150 翻面重写并改名——本槽这条判据的由来) |
| `sk26-g11-ledger` | `review.memoryFeedback` + `仍欠(G-11)` + `core.memoryDual` | SK-26 记账与实况同步:回流面清 pending、自进化面仍欠,SK-04 那处余量跟着改 |
| `gaps-key-set` | `Skills.gaps()` + `w1-selected-skills.md` | `gaps()` 键集逐字点名并与两份缺口图谱双向对账 |
| `gate-blockers-single` | `Domain.gateBlockers` + `subject-no-image` | 前置门槛码只在派生一处,消费侧按码投影不另写 |
| `plans-gate-read` | `Domain.gateBlockers(p)` + `plans.js` | 计划层不许回潮成第三份门槛判据 |
| `revise-subset-single` | `WfCore.reviseSubset` + `lowShots` | 重抽面派生只此一份,四处消费点都不自筛低分镜 |
| `suite-count-floor` | `单元测试` + `CLI 冒烟` + `README.md` | 三套件用例数只增不减 |
| `floor-slack` | `SLACK` + `记账件份数` | 四条 `FLOOR` 与 live 的差额有上限 |
| `unit-name-unique` | `套件 · 用例名` + `SUITES` | 单元用例名全局唯一(名集比对的口径不被重名吃掉) |
| `ledger-count-3way` | `索引表共 ` + `FLOOR` | 记账件份数三方对齐且只增不减 |

后四条是**取证工具自己那一层**:名集比对与三条数字判据一旦被删,上面六条护栏是不是还在就没人看得见了。它们此前只靠彼此的数字互相兜,没有任何一条判据说"这一层不许消失"。

清单不求全:加护栏时不必都登记进来(那会变成又一份要人工同步的表),但**登记过的不许无声消失**。

## 4. 落地

### 4.1 `blankNonCode` 收一个参数

既有的 `blankNonCode(src)` 把注释、字符串、模板串、正则一律抹成等长空白,给 `report(...)` 块链还原用(它要的是"只剩代码骨架,括号才配得准")。本条要的是另一半:注释不算数,而字面量得留着——**锚点大多写在断言的取值与消息字面里**。

故加一个 `keepText` 位:为真时只抹注释。新增 4 行(一个 `wipeText` 与三处调用点改名),既有调用点一个字未改,默认行为逐字节不变。

这一步不是可选的。W136 记过一次假红:变异体里顺手写的一句注释替被测断言把活干了,字面级判据当场命中注释。同一形状放到这里就是"把断言删光、把锚点留在注释里"照旧全绿(5.2 的 M3 实测过这一路)。

### 4.2 两条用例,失败含义分开

- **`contract · 护栏主题不许失联`**:逐条主题按锚点在**全部套件**的用例源码上找落点(取 `fn` 的运行时源码,不按文件切段——用例挪到别的套件、换个写法都不影响取数,判的是"这段判据还在不在跑"),落点为 0 报**失联**并点名主题编号、锚点与它守的是什么;落点数与登记不符报**落点数不符**并列出都是哪几条。两句分开报:前者是"这道护栏没人管了",后者是"锚点写得不准,这条判据本身不可信",含义不合并。
- **`contract · 护栏主题清单自身不许被架空`**:上一条只在"清单里还有这条主题"时才拦得住,把那一行连同用例一起删掉它一条都不遍历。这一条钉四层——清单条数只增不减(`TOPIC_FLOOR`,销号得先改这个字面)、编号唯一、每条主题至少两个锚点且每个锚点不短于 3 字(单锚点太容易被一句改写绕开、也太容易撞上别的用例)、承载用例断言少于两处按"名存实亡"报;末尾三句是**取数口自检**:注释抹没抹掉、字面量有没有被一并抹掉、遍历口径与套件表求和对不对得上——三者任一失效,上一条会整条退化成恒真句,故先红在这里。

### 4.3 `hosts` 这一格为什么是"恰等于"而不是"至少一条"

登记里的 `hosts` 缺省 1,判据取**恰等于**:

- 写成"至少一条"时,锚点写泛没有任何代价——`gate-blockers-single` 的第二个锚点若从 `subject-no-image` 松成 `js/domain.js`,它会同时点到另一条用例,于是**那条真被删掉时有人替它顶着**,判据静默失效(5.2 的 M6 实测:松掉即红,报"登记 1 处、实测 2 处");
- 取"恰等于"的代价是:一道护栏有意拆成两条用例时要把 `hosts` 抬到实况。这是一次显式登记,与"新增主题时抬 `TOPIC_FLOOR`"同性质,不是新造一个要人工同步的数——不拆就不动它。

### 5.4 回放:把这张清单搬到那次真实改名之前的那一版上

前面几条变异都是本槽自己造的改动。**那次真实的改名**发生在 `23b7a60`(合入 W150 之前)→ `5a4a95a`(合入之后)之间,故把本槽的清单、`keepText` 与两条新用例原样搬到 `23b7a60` 那一版的 `tests/unit.js` 上跑一遍:

```
PASS | contract · 护栏主题不许失联:清单里每条主题都还找得到承载它的用例(同主题改名翻面照旧绿,真删掉当场点名)
PASS | contract · 护栏主题清单自身不许被架空:锚点须落在断言里、条数只增不减、取数口失效先红在这里
===== 113/115 PASS, 2 FAIL =====
--- 旧树上 sk25 那条护栏的用例名:
    SK-25 仍欠段护栏(G-03 余面):段在不在与段里点名的两处余量对照源码,抹段或写成已清都红
```

十条主题在那一版上**全部找得到落点、落点数也都对**,`sk25` 那条落在**改名之前的旧名字**上。

## 6. 边界

- **不禁改名**:名集比对那一向照旧会报"这个名字消失了",本槽既不加严也不放宽它;本条只回答"那件事还有没有人管"。
- **只管登记过的主题**:没登记进 `GUARD_TOPICS` 的用例被删,仍旧只有三条数字判据兜着(5.2 的 M10 实测)。这是有意的——把 522 条用例都登记一遍等于再造一份要人工同步的表,而本目录已经为"要人工同步的数"付过好几次账。
- **"同等覆盖"是按锚点近似的**,不是语义等价:继任者只要还读同一份实况就算接手,它把断言写得比原来弱(但仍多于两处)本条看不出来——那一半归"变异转红",归各条护栏自己。
- **零产品代码、零计费、不动发布门**:`Tasks.run`/`billingAction`/G1–G10 一个字未改。
- **`tests/e2e.js` 仍在所有对账之外**(它按 tab 列表循环登记,行首点数不等于实跑条数),本槽未跑。

## 7. 残留与交接

1. **"删用例 + 销号 + 改小两个下限"这条路仍是通的(5.5 ⑤)。** 本槽把它从 3 处改抬到 5 处,并把最后两处挪进一张带 `why` 的表里,但棘轮终究是棘轮——改小它的人不会被拦住,只会被看见。要封死得另立一份不随 `tests/unit.js` 一起改的记录(比如把主题清单外置成数据文件再与本文件双向对账),那是另一槽的事,且要先判它值不值得再造一处双向对账。
