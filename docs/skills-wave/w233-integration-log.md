## 九、交接:三格残留原样留着

### 9.1 未收(交接明令不代修):存量重复 id 迁移

W226 的闸只管**新进来的**导入。全仓现取**没有任何存量迁移实现**
(`dedupeShotIds` / `migrateShotIds` 之类一处都没有),故闸上线之前就已经躺在库里的同 id 多行不会被清。
本槽 §2.3 那次 live 现取把「灌进去会长回来」又量了一遍:
import 闸刚把表修成唯一数 2,同一份 `state.json` 经逃生舱再灌一次就回到唯一数 1,再整表重导又回到 2。
即"只迁存量"与"只堵一处"是同一件事的两面,收它得连 §9.2 一起判。

要收的话得单开一槽:落点是"读到分镜表时发现重复即改发新 id 并回报",而这会**改动已落库数据的寻址键**,
用户手上按老 id 记的脚本会失配,故不该顺手塞进集成槽里。

### 9.2 已判定不收(本槽新形状):`state-put` 与 `PUT /api/state` 的不校验是契约

`cli.js` 的 `CMD['state-put']` 仍是全量覆盖(`--force` 才放行),直接 `PUT /api/state`,

tip 上的成色:

- 行为面 `exit=2`(缺 `--force`)/ `exit=0` 后落库 `["sh_dup","sh_dup"]`,与判定一致;
- 声明面三处锚点在册,调用方读得到"唯一性归自己";
- 收拾的出路在册且现跑得通:整表重导 `shots-import`(报 `renamedIds`),或自己改完再灌一次。

**下一个人要注意**:这一格不再是"待修",给它补闸就是推翻 W231 的停工结论,得先重新判。
但它与 §9.1 的因果没解除——逃生舱还能再造存量重复,故 §9.1 那一槽仍要连它一起设计(哪怕结论仍是不设闸)。
