## 4. 冲突怎么解(逐处)

两处冲突都是并集型或"取更新的一侧",没有一处需要择一丢弃对侧的实质内容。

`README.md` 的长行问题本轮**没有触发**:`w30` §6 明写"`README.md` 未动,不参与其口径行的合并",`w31` 也没动主 README。主 README 全轮只改了一个数字(342 → 343),是对账契约逼出来的,不是合并冲突。W25 的句级 `merge-file` 与 W29 的"取一侧 + 按 word-diff 折回对侧"两套解法本轮都没用上——记在这里是为了说明**它们没过期,只是本轮没有长行相撞**。

两侧增量的复核仍按 W29 那条口径做:`git diff --word-diff=porcelain <merge-base> <branch> -- <file>` 先把该分支对这个文件的全部增量列出来,再逐条确认终态在位,而不是只看冲突块。`w31` 对 `docs/skills-wave/README.md` 的增量是两条(索引行 + 摘要里「编排层也已跟上」那句),其中摘要那句落在冲突块之外、已自动合上,靠这一步才确认它没被漏掉。

### 4.1 `tests/unit.js`:一行注释,取 HEAD 侧

第 1 步唯一的冲突,在契约用例「skill 索引对齐短名单 30 条」的一行注释上:

- HEAD(基线)侧:`// 四类既有单源键全覆盖:KB 条目 / Prompts key / 领域命令 / 专家 id 一个不落(新增单源键必须进索引;各类的条数由 contract 套件的「注册表口径」对账断言钉在 README 上,此处只查覆盖不查条数)`
- `w30` 侧:`// 四类既有单源键全覆盖:KB 18 条 / Prompts 6 key / 命令 11 条 / 专家 16 位(新增单源键必须进索引)`

**取 HEAD 侧**。理由不是"基线优先",而是两句说的不是同一件事:W23 之后条数由对账契约钉住,基线这句是**把写死的条数从注释里撤掉之后**的形态;`w30` 那句只是把旧形态里过期的 `17` 抬到 `18`(它的 §6 末条也是这么写的:"要改的只有那句注释")。基线侧已经把这句注释需要维护的数字整个删掉了,`w30` 的这处维护因此自然作废。

**这不是丢弃 `w30` 的增量**:它这一步的实质产出是新增的那条契约用例,整块自动合入、一字未改;实测终态 `Skills.byId('core.stageIndex').kb` 为 18 条、与 `Object.keys(KB.SECTIONS)` 双向对齐,断言在跑。

### 4.2 `docs/skills-wave/README.md`:索引表表尾三行并集
