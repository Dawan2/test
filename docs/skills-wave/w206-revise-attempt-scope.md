## 1. 停工位原话与它要的举证

W191 §6 留下的那一条:**两端重抽计数器都不落库,只活在这一次调用的内存里**。
交接口径给的停工条件很硬:只有证到**用户会被骗**(回执说已到顶、刷新后同一批镜又能自动重抽且不提示这是新会话)才改;
若产品口径就是「每次点按钮是新会话、limit 只约束这一次调用」,则**停工位不成立,停**。
下面两节先在基线 `0010394` 上把两端各跑一遍真代码,再逐条对着这个条件判。

## 2. 基线 live:两端确实都从 0 重新开始烧

### 2.1 浏览器:刷新页面再点一次,同一批镜又拿到一整份 limit

真的 `js/produce.js` 装进最小 `window` 壳里跑 `SB.autoSmartReview`,`Review.reviewShot` / `SBGen.createShotVideo` 打桩计数,
回执原样取 `dock.say` 的每一行;**「刷新页面」= 把 `Store.save()` 之后的项目对象整份 JSON 序列化,再装进一个全新沙箱重跑**
(真刷新时页面正是从落库那份重新水化,而上一次调用的内存全丢)。夹具:两镜恒 5.0 分、`sbConfig.maxRetry = 3`。

第一次点(live 原文,已去 HTML 标签):

```
【面板标题】🧠 智能审片 · 第一集(2 镜)
达标线 7.0 分 · 不达标先按问题修订提示词再重生成(每镜最多 3 次)· 超限转人工处理 · 评审期间可正常操作页面

▶ 镜头 1 评审中(第 2 次重生成后)…   ⚠️ 5.0 分不达标 …
```

刷新后第二次、第三次点,**逐字相同**:`{"pass":0,"retry":6,"manual":2}`、逐镜 `{s1:3, s2:3}`、开场仍是「每镜最多 3 次」。
落库对象上一个计数字段都没有——问题一的答案是 **是,又能从 0 开始烧额度**。

### 2.2 CLI:第一轮跑满后再 exec 一次不带入参,再给一整份 limit

真的 `node cli.js exec episode.produce`,上游由一个只实现 `/api/state`(GET/PUT)、`/api/wallet`、`/api/volc/video`(创建 + 轮询)、
`/api/wf/smart-review`、`/api/llm/chat`、`/api/ffmpeg/compose` 的常驻桩顶着,**state 跨多次 CLI 调用持久**(这正是要量的那一面);
重抽次数按桩收到的 `POST /api/volc/video` 现数。夹具同上:两镜恒 5.0 分、`ep.sbConfig.maxRetry = 3`、命令入参不给 `maxRetry`。

| --- | --- | --- | --- |
| `POST /api/volc/video` | **8**(首轮批量 2 + 重抽 6) | **6** | **6** |
| `POST /api/wf/smart-review` | 4 | 4 | 4 |

再花一整份。问题二的答案同样是 **是**。

## 3. 判定:停工位不成立——回执承诺的就是这一次

两端的实况都摆在上面,分歧只在**回执到底承诺了什么**。逐条对着停工条件看:

**① 注册表上 `maxRetry` 就是「每次调用」的入参。** `js/cmd-registry.js` 给 `episode.produce` 登记的是
`maxRetry` / `number` / 「审片不达标重试上限 1-5(默认 2)」,W191 定下的候选链是 **命令入参 → 分集 `sbConfig` → 缺省**。
一个每次调用都可以重新递进来的数,按构造就是这一次调用的预算:同一条命令第二次带 `maxRetry:5` 时"上一次已经用掉的 6 次算不算",
在终身语义下根本答不上来——那个问题只有产品决策答得了,不是实现漏了一次落盘。

**② 参数配置面板给的是一个旋钮,不是一本额度账。** 面板上那一栏写的是
「智能审片最大重生成次数(不达标自动重抽)」,选项 `1 次 … 5 次`,提示语「仅「智能审片」开启时生效;每镜评审 1 积分,重生成 5 积分/次」;
开关那一栏的说明是「批量生成后逐镜自动审片,不达标自动重生成,**直至达标或达到最大重试次数**」——说的是**一次批量生成之后那一趟**。
而且这个旋钮用户随时可以从 1 改到 5,真按终身额度实现的话,改一下旋钮就把额度重开了,那本身就不是额度语义。

**③ 回执的作用域是这一次。** CLI 印的是「第 x/3 轮」——一个 x-of-N 的进度分母,没人会把它读成项目开张至今的总账;
浏览器那句「每镜最多 3 次」是**这一次审片进度面板**(标题 `🧠 智能审片 · 第一集(2 镜)`)的开场白,
收尾那句「完成:达标 0 镜 · 自动重生成 6 次 · 待人工 2 镜」报的也是这一趟的花销。
「已达最大重试,转人工处理」说的是"自动循环到此为止,交给人",不是"这几镜此后再也不许重抽"。

**④ 平台自己推荐的下一步就是再来一次。** 到顶那一刻 `Domain.episodeState` 落到
`{ status: 'needs_human', action: { key: 'review', label: '审片修订' } }`,`Domain.epFixOf` 给的处置是 `episode.produce`;
CLI 的回执尾巴上原样印着 `"next":{"status":"needs_human","key":"review","label":"审片修订"}`。
**把计数落库当终身次数,等于把平台自己印在回执上的那颗按钮变成一个花不出钱、也不解释为什么的死胡同。**

**⑤ 浏览器那一路每次点都重新报价。** `oneClickProduce` 每次都先弹
「预计消耗:… 积分(逐条扣减、失败返还;审片重抽另计)。开始吗?」——每一次点都是一次重新授权的花销。

按停工条件,这正是「每次点按钮是新会话、limit 只约束这一次调用」那一档。
**停工位不成立,产品代码一个字不改。** 交接口径同时点名了不许走的那条路——把「本次调用上限」改成「项目终身上限」,
上面五条没有一条支持 UI 是那么承诺的,故不改。

## 4. 不改,但把这条口径钉成判据(加测 2 条,两端各一)

判成"不成立"之后最容易烂掉的一面是:下一个人读到 W191 §6 那句「计数器都不落库」,当成缺陷顺手"修好",
于是每次调用的预算无声变成终身额度,而回执一个字没改。故本槽把这条口径正面钉住,两端各一条:

| 套件 | 用例 | 守什么 |
| --- | --- | --- |
| `produce` | `autoSmartReview:重抽上限是这一次调用的预算——落库那份数据重新水化再跑,拿到的是同样一整份 limit,回执也只报这一次的花销` | 浏览器端:首跑逐镜 3 次/共 6 次,把落库那份 JSON 换个全新沙箱重跑仍是 6 次;开场那句仍按这一次解析报「每镜最多 3 次」,收尾报的是本次的 6 次而不是累计 12 次 |
| `commands` | `CLI exec produce:修订轮次是这一次调用的预算——同一份 state 再 exec 一次,拿到的仍是一整份轮次,回执分母也不递减` | headless 端:`cli.js` 全文真跑(只换 `api()` 记录桩),同一份 state 上连 exec 两次,`revise1..3` 三步与 6 次真下发逐格相同;落库的分集对象上不许冒出第二份轮次账 |

两条**都各自钉住绝对值,不只钉"两次相等"**——这是本目录反复量到的老坑(W164 M5、W170、W191 M2:两端/两次一起退化时相等断言全绿),
第 5 节的 M4 就是拿这一路量的。CLI 那一条另有一处形态说明:`cli.js` 里 `POST`/`GET` 是 `const` 词法绑定覆盖不到,
故桩打在 `api()` 上——桩下面全是产品代码,`reviseTargets` / `reviseLowShots` / 轮次循环一行没换。

**两条都不登记进 `GUARD_TOPICS`**(任务口径)。另有一处顺带的边界:CLI 那条最初的桩里调了 `WfCore.reviseSubset`,
正好把既有护栏主题 `revise-subset-single`(锚点 `WfCore.reviseSubset` + `lowShots`)的落点从 1 撞成 2,
`contract` 那两条当场红。它不是那道护栏的真承载(它一句都没判"重抽面派生只此一份"),
故处置是把桩改成不调那个函数、回执里那份名单留空——编排层每轮本来就现取实况自己派生(W131),桩不喂它照跑得起来;
**没有抬 `hosts`,也没有收窄锚点**。

## 6. 仍欠(如实留着)

- **回执口径面只有字面这一层护栏**(第 5 节 M5)。「每镜最多 N 次」被改写成任何别的说法都会红在那一句上,
  但判据判不出新说法承诺的是本次还是终身——那一步要人来判。真要收,得先给回执里「这一次」这个作用域一个可判定的取数口
  (比如把作用域词从上限那一处一并派生出来),那是回执文案的产品面,本槽不顺手做。
- **`episode.smartReview` 单独调用在 CLI 那一端仍只评一次**(W194 交接第 1 条),故本槽 CLI 那一条钉的是 `produce` 编排那个循环;
  哪天那一端补了循环,同一条口径要在那里再钉一次。
- **W191 §6 那句「两端的计数器都不落库」原样留着,一个字没改**:它记的是实况,而本槽补的是"这个实况是口径"这半句——
  两句不冲突,第 3 节就是那半句的举证。有意不去改 W191 的正文(记账件落笔即定)。
- **写回不对称仍在**(W191 §6):浏览器命令层把解析结果写回 `ep.sbConfig.maxRetry`、CLI 只读不写。
  那是**配置**那一面,与本槽这条 attempt 计数不是同一件事,W204 在那一面上另有处置,本槽不碰。
