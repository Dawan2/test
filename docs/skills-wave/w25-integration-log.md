## 4. 冲突怎么解(逐处)

十二处冲突全是并集型。解法一律是**先用 `git diff --word-diff=porcelain <merge-base> <branch> -- <file>` 把该分支对这个文件的全部增量列出来,再逐条补进基线全文**,而不是凭冲突块里看到的那点内容判断——冲突块只是分支增量的一部分,另一部分在同一次合并里已自动合并成功。

`README.md` 的冲突有个额外麻烦,值得单列一条口径:那几段各自是**一整行**(单行超过 4000 字),行级三方合并对它们完全无能为力,哪怕两侧改的是行内相距很远的两句话也照样整行冲突。本轮的做法是**把三份文件(base/ours/theirs)按 `;`/`。` 切成一行一句后再跑 `git merge-file`**,让三方合并在句级生效:

```
# 切分:每行按句末标点拆成多行,原换行位置用一个哨兵行占住(可逆)
node -e "...split(/(?<=[;;。])/)..."   # base.md/ours.md/theirs.md → *.s
git merge-file -L ours -L base -L theirs merged.s base.s theirs.s
# 回拼:哨兵行还原成换行,句行拼回原行
```

第 1 步六处里的四处、第 3 步六处里的四处因此自动合上,只剩"同一句两侧都改了"的留给人解。切分与回拼是纯文本可逆变换,合并后 `diff` 复核过非冲突段逐字节未动,并逐条 `grep` 复核两侧独有的标识符(`subjects.genRefDiscipline`/`ai-cliche`/`shot-size-linkage`/`preflightStages` 等)在终态都在。

> **口径**:README 这类"一段一行"的长行文档,冲突时不要在行级硬解,更不要 `git checkout --ours <file>` 整份取(W16 第 5.1 节记过那个坑)。句级切分后跑 `merge-file`,能把"两侧改的是不同句子"这一大类自动消化掉,剩下的才是真需要判断的。

## 5. 合并后必须重新对齐的五条断言(逐条说明为什么不是删测换绿)

合并本身零冲突地把三侧代码并到了一起,但**各侧断言描述的都是自己那一半的世界**,并到一起后有五条对不上。逐条记录改法与理由,便于复核这里没有一条是判据变弱:

| # | 断言 | 原判据 | 改成 | 为什么不是放宽 |
|---|---|---|---|---|
| 1 | 面表源级:`五面共 N 条已落地校验项` | 期望 9 | 期望 12 | 期望值是**实况快照**,不是阈值。校验项多了三条,9 就是错的;写死 12 后再加校验项照样先红 |

| 3 | `w22` 的源级消费断言:`js/commands.js`/`cli.js` 里出现过 `Skills.check('subjects'` | 正则扫全文 | 改用 W17 的 `assertPreflightFace('subjects', …)` | **判据是加严的**。W17 收表后两端段内**不允许**再出现写死面名(那正是收表要防的事),`w22` 的正则在本线上永远为假。换用的助手判三件事:该面在单源表里、两端 preflight 段确实读该表、段内不写死面名——比"全文出现过某字符串"严格得多 |
