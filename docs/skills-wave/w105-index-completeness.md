# W105 · 目录索引契约补完备性:每份记账件都必须在索引表里,且判据不借道散文链接

范围:只动 `tests/unit.js`(contract 套件加一条)与 `docs/skills-wave/README.md`(明写份数 + 本文的索引行)。产品代码一行未改。

## 1. 上一槽的洞在哪

基线上索引契约已有两条(一条都没删,本槽只加):

1. **双向集合相等**:`docs/skills-wave/` 下除 `README.md` 外的 `.md` 文件名集合,与索引表 `| [x](./x)` 行的文件名集合逐字相等,且链接文字必须就是文件名。
2. **按份点名 + 相对链接不悬空**:目录里每份 `wNN-*.md` 都要有自己那行索引;任何文档里 `./` 开头的 markdown 相对链接都要指到真文件,指到的若是 `wNN-*.md` 还必须在索引里。

这两条在「文件还在、索引行被删」时都会红。**但「文件与索引行一起消失」此前全绿**,原因是机械的:

- 第 1 条比的是两个集合,两边同时少一份,等式照样成立。
- 第 2 条的按份点名写成 `readdirSync(dir).filter(...).forEach(...)`——**遍历的是目录里还在的文件**。文件没了,那份就一次也不被遍历,断言不是没通过而是根本没执行。
- 于是只剩第 2 条的后半段(相对链接不悬空)兜着:别处散文若用 markdown 链接点过这份记账件,链接会当场悬空报红。

这一层的覆盖面是实测出来的:本槽落地前目录里 116 份 `wNN-*.md`,其中 **39 份除索引表那一行之外,全目录再没有第二处 markdown 链接指向它**(逐份数它被相对链接指到的次数,只有索引表那一次的即这 39 份;这个数随分支上的散文而变,W96 核验时在 107 份里数出 34 份,判据同一套)。这 39 份一旦连文件带索引行一起消失,三条断言全绿。

这不是假想的删法。目录里已有两次实际发生:合并时只合到分支的父提交,该分支后来那条自己的记账件与索引行一起没进来(见 [w80-integration-log.md](./w80-integration-log.md) 记的「W53 那个洞的第二次发生」)。漏合的形状恰好就是「文件与索引行同时缺」。

## 2. 本槽加的那条:第三份记录

补的完备性判据是「份数」,判据里**不含任何"别处是否链过"的条件**:

```
docs/skills-wave 索引完备性:记账件份数由 README 明写并与目录/索引表三方对齐,且只增不减
```

四层:

| 层 | 判据 | 拦的是 |
|---|---|---|
| 明写份数存在 | `docs/skills-wave/README.md` 里必须有「索引表共 N 份记账件」这句 | 把这句删掉/改写以绕过对账 |
| 三方对齐 | 目录里 `wNN-*.md` 份数 == 索引表里 `wNN-*.md` 行数 == 明写的 N | **文件连同索引行一起删而份数没跟着改** |
| 下限 | 目录份数与明写份数都 `>= FLOOR`(本槽落地时 117) | 把三处一起改小以迁就删除 |
| 逐份点名 | 每份 `wNN-*.md` 都在索引表行集合里 | 文件在、行不在(与旧那条同判据,但本条自足) |

关键在**第三份记录不随目录与索引表一起消失**:「明写份数」是 README 里的一行散文,「下限」是用例里的一个字面。删一份记账件要真正静默,得同时改动四处(文件、索引行、明写份数、用例下限),而后两处一个在记账文档里、一个在测试里——改测试就是删测。

### 2.1 下限为什么写成 `>=` 而不是 `==`

`==` 会让"加一份记账件"这件事同时红在下限上,等于每槽多一处必改的字面且毫无收益(三方对齐已经把"加文件不补行/不改份数"全拦住了)。`>=` 是棘轮:只在往下走时报红。新开一槽时把下限抬到当轮实况,漏合就会被上一槽抬过的下限接住——**这是下限相对明写份数的额外价值**:漏合可能把 README 的整段改动一起丢掉(份数退回旧值,与丢掉一份文件后的实况自洽),但 `tests/unit.js` 的改动正是合并时最不会被丢的那部分,下限于是仍然报红。

### 2.2 为什么不用「波次号连续」当判据

第一版想过更强的判据:波次号 1…max 每个号都要有至少一份被索引的记账件。当场否掉——目录里 **W96 与 W98 就是空的**,它们是如实登记在 [w99-integration-log.md](./w99-integration-log.md) 的「剩余未合」槽,号被占了但记账件不在这条线上。连续性判据会把这种如实记录判成红,而"例外名单"要么写死(下一次未合又要改)要么去解析散文的剩余未合段(比它要拦的问题更脆)。

同理否掉了「散文里以 `Wnn` 形式点到的号都要有记账件」:实测目录里出现 99 个不同的 `Wnn` 号,与文件对不上的恰好是 W96/W98 这两个未合号。判据本身站不住。

## 3. 变异实测

做法:`git worktree` 开一份独立副本,在副本里改、在副本里跑,生产记账一份没动过。用来验证的那份记账件是 **`w34-integration-log.md`**——它属于「只有索引表那一行链接」的 39 份之一(全目录扫它的相对链接只有索引表一处),正是旧契约看不见的那一类;它同时也是一份收敛记录,与真实漏合的形状对得上。

| # | 变异 | 收严前 | 收严后 |
|---|---|---|---|
| 1 | 只删 `w34-integration-log.md` 的索引行,文件留着 | 红 2 条(双向集合相等 / 按份点名) | 红 3 条(多出本条) |
| 2 | 文件与索引行一起删,明写份数不动 | **全绿(0 红)** | **红 1 条**(目录份数 116 ≠ 明写 117) |
| 3 | 文件、索引行、明写份数三处一起改小(117 → 116) | 全绿 | **红 2 条**(下限那两条:目录份数与明写份数都低于 117) |
| 4 | 加一份 `w200-x.md` 但不补索引行、不改份数 | 红 2 条 | 红 4 条(多出本条的三方对齐与逐份点名) |

变异 2 是本槽的靶心:它是收严前后**唯一一处由全绿转红**的删法,也正是漏合的形状。变异 3 证明「把明写份数一起改小」这条绕行路径也堵住了。

## 4. 没纳入的部分(诚实位)

- **份数只数 `wNN-*.md`**。索引表若将来收进不带波次前缀的文档(目前一份也没有),那种行不进份数、只受旧那条双向集合相等的约束。
- **拦得住"丢了几份",拦不住"丢的是哪一份"**。同一轮里删掉一份旧记账件、又加进一份新的,份数不变、三方仍然对齐、下限也不降,本条不报红(此时只剩人工评审)。要拦住这种,得把整份名单钉进用例里逐份对照——那是一张每槽都要改一行的清单,收益与维护成本不划算,故如实记在这里。
- **下限的强度取决于有人抬它**。下限停在 117 不动,则往后每加一份记账件,可被静默删掉的余量就多一份。抬下限这件事只有靠新开槽时顺手做,契约本身不会催。
- 本条落在 `contract` 套件,与产品行为无关:`node tests/unit.js contract` 单跑即可,不需要服务与网络。
