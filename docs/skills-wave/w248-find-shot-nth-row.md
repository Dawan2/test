## 一、先 live:写回到底落在哪一行

沙箱直接 `runInContext` 真 `cli.js` 本体(只掐掉末尾 `main()` 入口),换掉的只有服务端往返与生成引擎;
落库面一律读 **clone 语义的 disk 夹具**——`stateGet` 每次现取一份拷贝,只有 `withProject` 真提交的补丁才落盘。
共享同一个对象的夹具量不出「编排层只在自己手里那份快照上改一改」的假落库,这一条是取证前提。

夹具:分镜表 `dup(首行)` / `solo(不重复)` / `dup(第二行)` / `dup(第三行)` 四行、三行同 id,
全部已确认已有底图、全部未出片(与 W246 §1.4 那一格同一份形状,便于两槽数字对得上)。

### 1.1 点名一档与整集一档都中招

| 档 | 引擎实收 | 回执 | 落库 | 出片 |
|---|---|---|---|---|
| 点名 `["dup"]` | 3 次 | `ok:true total:3 ok:3 failed:[]` | `首行:v3.mp4` / 其余三行无片 | **1 行** |
| 整集(不点名) | 4 次 | `total:4 ok:4` | `首行:v4.mp4`、`不重复:v2.mp4`、第二/第三行无片 | **2 行** |

`首行` 那一格是被 `v1 → v2 → v3` 连写三遍的结果:三笔视频钱买到的是同一行的第三段片,
前两段连同那两笔钱一起没了,而回执一个字的失败都没报。

### 1.2 这不是一次性的,是每轮复发的漏

同一份表连跑三轮整集补片(每轮都是「补未就绪的那几行」):

```
基线 cli.js   第 1 轮:扣 4 笔,回执 total:4 ok:4,库里出片 2/4
              第 2 轮:扣 2 笔,回执 total:2 ok:2,库里出片 2/4
              第 3 轮:扣 2 笔,回执 total:2 ok:2,库里出片 2/4
              三轮共扣 8 笔,出片行数永远停在 2/4
```

第二、三行每一轮都被重新判成「未就绪」、每一轮都真扣一笔、每一轮的片又都写去了首行。
**这个漏没有收敛点**:跑到第 N 轮仍是 2/4,回执仍是 `ok` 全绿。
交接登记的数字(点名 3 笔 1 行、三轮 8 笔停在 2/4)现跑逐个对上。

### 1.3 交接没登记的一格:首行已出片时那段片会被覆盖

整集那一路上先给首行一段 `old.mp4`(已出片,被「未就绪」筛子跳过),再跑一趟:

```
基线 cli.js   引擎实收 3 次;落库 首行:v3.mp4 | 不重复:v1.mp4 | 第二行:无片 | 第三行:无片
```

**首行那段已经在手的片被这一趟盖掉了**——用户既没点它、它也没进待跑清单,产物却没了。
这一档比 §1.1 更难受:那边是钱白花,这边是已到手的东西倒赔进去。
修完之后 `old.mp4` 一个字不动(§二 2.2 的序数取材面就是冲着它立的)。

### 1.4 停工条件:不成立

交接给的停工条件是「现跑已按行写回则只记账」。现跑逐档反过来:
点名档 3 笔换 1 行、整集档 4 笔换 2 行、连跑三轮 8 笔仍是 2/4、首行已有的片还被覆盖。故不停工,改写回。

### 1.5 单镜命令那一路不算这一格

`shot.generateVideo`(以及 `gen-shot-video`)点名一个 id 而表里有多行时现跑落在首行、扣一笔、到手一段——
**取首行是这条命令的既有语义**(用户点名的就是一镜,只扣了一笔,没有「多花的钱」),本槽一个字没动它。
这一格与批量那一档的区别是「扣了几笔」,不是「取的第几行」。

### 1.6 浏览器那一端不是这个形态

`js/commands.js` 的 `episode.generateVideos` 把 `pend` 这一批**对象本身**整批交给 `SBGen.batchGenVideos`,
没有第二次寻址,三行各得一段。两端的差异来自 CLI 有 `withProject` 这一道「重取最新状态再打补丁」的往返。
交接明令这一端不硬改,现跑核过确实不需要改。

## 二、改了什么(产品码一处,`cli.js` +11 −1)

### 2.1 `nthShot(ep, sid, nth)`:紧跟 `nthSubject` 之后

```
const nthShot = (ep, sid, nth) => {
  const rows = (ep.shots || []).filter(x => x.id === sid);
  return rows.length ? (rows[nth] || rows[0]) : findShot(ep, sid);
};
```

同 id 一行都没有时**委托回 `findShot`**:「镜头不存在」的 exit 4 仍由它抛,本槽不另造第二个错误出口。
`rows[nth] || rows[0]` 是并发改表(这一趟跑到一半别处删了行)时的兜底:退回原行为,
不静默丢产物、不让 `undefined.image` 把整趟炸成失败。
落点选在 `nthSubject` 之后而不是 `findShot` 之后:`findShot`/`findSubject` 那一对不拆开,两个 `nth*` 挨着读。

### 2.2 调用点:序数在**快照全表**上数,不在待跑清单上数

```
const nthOf = new Map();
const seenIds = Object.create(null);
(ep.shots || []).forEach(s => { const n = seenIds[s.id] || 0; seenIds[s.id] = n + 1; nthOf.set(s, n); });
…
const sLive = nthShot(epLive, s.id, nthOf.get(s) || 0);
```

`nthOf` 按对象身份记(`todo` 里的元素就是 `ep.shots` 里的那几个对象),不按 id 记——同 id 那几行的序数各不相同。

**为什么必须在全表上数**:待跑清单是过滤过的。首行已出片被「未就绪」筛子跳过时,
在 `todo` 上数出来的序数是 `0,1`,写回落到全表的第 0、1 行——**首行那段已有的片被覆盖、末行仍补不上**
(正是 §1.3 那个形状)。这一档单独钉了一条判据(§三 ③),变异 2、4 现跑都是这个形状。

`confirmAll` 那一路仍安全:它先 `withProject` 写回 `confirm` 再 `execCtx` 重取,
`ep` 是写回之后的那份快照,`todo` 与 `nthOf` 取材于同一棵树,对象身份对得上。

### 2.3 没碰的

选人闸 `pend`/`todo` 那两句逐字未动(按行筛是对的:改成按 id 只跑一行会让第二、三行永远跑不到);
`Domain.dupRowsNote` 与它的调用点未动(那句话说的是「多花了几行的钱」,与「钱买到了什么」是两件事,
**两件都成立时它照旧说得对**:三行真跑三行,只是此前三份产物落在一行身上);
`Domain.dupRowsNote` 的 `extra` 算术未动(W245 的地);`nthSubject` 行为未动(照抄的是形态);
`findShot` 本体未动(单镜那几路照旧取首行);`shots-dedupe` 未动、未新增第二条命令;
`state-put` 仍只有 `need(f.force)` 一道闸;`Skills.gaps()` 仍 20 键;
`js/` 与 `server.js` / `mcp.js` **零 diff**——本槽只动 `cli.js`、`tests/unit.js`、`README.md` 与本目录。
