## 1. 一分钟结论

- 本槽的题目是「`KB.SECTIONS` 每个键必须被至少一条 `skill.kb` 登记,漏登即红」。**这一向的断言早已存在**(`tests/unit.js` contract 套件「skill 索引对齐短名单 30 条」里的 `assertEq(kbKeys.filter(k => !uniq('kb').includes(k)) …, '', 'KB 全部条目应被 skill 索引引用')`),按"断言已存在则不重做"的口径**一行未改**。实测它确实是红的(见 §2 M0)。
- 真正的残留是它**盲掉的一向**:该断言取的是全表 `kb` 的并集,只要某键被任一步条目登记过,把它从索引宿主 SK-01 摘掉照样全绿。W27 §8 已把这一向如实记下,本槽补成硬断言:`SK-01.kb` 与 `Object.keys(KB.SECTIONS)` **双向逐条对齐**、宿主内**不重复登记**、且**不得出现第二个全库宿主**。
- **没有键需要补登**:实测当前 18 个键全部在 SK-01 已登记(见 §3 表),故"必要时把漏登键补到既有 skill 条目"这一条不触发,一个 `kb` 数组都没改——注入拼块的逐字节对账基准因此全部原样。
- 验收:`node tests/unit.js` **320/320**(基线 319,只增不改);`node tests/integration.js` 93/93;`node tests/cli.smoke.js` 62/64(与基线同样的两项,与本轮无关)。未删测、未放宽任何既有断言。

## 4. 断言写法

落在 contract 套件里,紧跟既有那条「skill 索引对齐短名单 30 条」之后(两条一读到底:上一条管并集,本条管宿主):

```js
const idx = Skills.byId('core.stageIndex');
assert(idx && idx.stage === Skills.CROSS && idx.kinds.includes('infra'), …);
assertEq(kbKeys.filter(k => !idx.kb.includes(k)).join('、'), '', '新增 KB 条目须同时登记进索引宿主 SK-01 的 kb');
assertEq(idx.kb.filter(k => !kbKeys.includes(k)).join('、'), '', '索引宿主不得留 KB.SECTIONS 之外的键(条目改名/删条后的残留)');
assertEq(idx.kb.filter((k, i) => idx.kb.indexOf(k) !== i).join('、'), '', '索引宿主每条只登记一次');
Skills.list().filter(s => s.id !== idx.id).forEach(s => assert(s.kb.length < kbKeys.length, …));
```

四处口径说明:

- **宿主按 id 取,不按下标或 SK 号猜**。`Skills.byId('core.stageIndex')` 加一句身份断言(贯通层 `infra`),宿主哪天改名或挪位,断言先红而不是静默失效。
- **报错点名缺的键**,`filter` 后 `join('、')` 与既有断言同款——转红时直接看到"少了哪个",不必回去数数组。
- **不断言顺序**。W27 §7 定的并行合并解法是"`SECTIONS` 表尾与 SK-01 的 `kb` 数组按键名取并集",顺序不是纪律;把顺序也钉住只会给三方合并加无谓的红。
- **第二宿主用"整库登记"判**,不用"是否等于全表"判:`s.kb.length < kbKeys.length` 对任何一条步条目都是宽松的(现有最多 5 键),而复制整库必然撞线。

`js/skills.js` 侧只改 SK-01 的 `note` 一句:登记一次这件事从"约定"变成"契约断言,漏登即红",注释与实况保持一致。

## 6. 与并行槽的边界
