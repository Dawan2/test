## 三、先量现网实现:实现已对,本槽只加测

沙箱直接 `runInContext` 真 `cli.js` 本体(只掐掉末尾 `main()` 入口),换掉的只有 `stateGet` 与 `api`;
`PUT /api/state` 的桩按服务端那份增量合并口径写(`changes.projects` 按 id 覆盖/追加,见 `server.js` 那段)。
源库夹具:`dup(A-首位)` / `solo(B-不重复)` / `dup(C-第二位)` / `dup(D-第三位)` 四位、三位同 id,各带各的图与提示词。

| 点名方式 | 取到的源 | 副本 id | 目标库 | 源库 |
|---|---|---|---|---|
| `subject-copy p1 dup p2` | **A-首位**(`/uploads/img/a.png`、提示词A、设定A、形态「战损」) | `sj_mtep6uqm_6b7e5f`(新发) | 只多这 1 位 | 四位逐字段未动 |

`findSubject(p1,'dup')` 现取 `A-首位`。取源那一行是
`const src = findSubject(from, a[1]);`,而 `findSubject` 是
`(proj.subjects || []).find(x => x.id === sid || x.name === sid)` ——**按 id 落首位、按名字够得着后几位**,
与 `cli.js` `subjects-dedupe` 头顶那段注释说的是同一件事。

**故停工条件成立那一半、不成立那一半各归各:**

本槽**没有**把取源改成 `nthSubject`:按 id 点名单位只复制一位、只花一份力气,
与批量补图那两档「点一个 id 库里几位就收几笔生图钱」不是同一件事(W246 §1.5 已判过同形的一格)。

## 四、加的那一条(`tests/unit.js` +1 条,`commands` 套件)

用例名:

```
CLI subject-copy 按 id 点名取的是第 1 位:同 id 多位时源落首位、后几位按 id 够不着(按名字够得着),副本一律重发新 id
```

插在 `CLI subjects-dedupe …` 那条之后——那条把「按 id 那几处一律 find 首位语义」当成引用面的**前提**用了,
而这条跨项目复制此前无人看守;两条连着读,前一条说"去重前后落到同一位",这一条说"落的到底是哪一位"。

| 档 | 钉的是 |
|---|---|
| ① 按 id 点名 `dup` | 取到的源是第 1 位,且**名字之外**图/提示词/描述/形态逐字段都得是首位那一份(只对上名字、内容取了后几位这种错法只看名字接不住);目标库只多 1 位;回执 `forms` 与落库那份对得上 |
| ② 副本是新发的 id | 不沿用源 id(`!== 'dup'`、前缀 `sj_`)、不与源库任何一位撞车、形态 id 一并重发(`!== 'fm_a'`);**源库四位逐字段一个都不许被改**(这是复制不是搬家) |
| ③ 后几位按名字够得着 | 点名 `C-第二位` 拿到的就是 C 那一份,且同样重发新 id——这是现成的绕路,不是缺陷;按名引用那一路被收成只认 id 时红在这里 |
| ④ 首位缺图、后几位有图 | 取的仍是第 1 位、副本如实没图:选的是"**第一位**",不是"第一位**有图**的" |

落库面读 clone 语义的 disk 夹具(命令只在自己手里那份快照上改一改也会看起来"落库了",共享同一个对象量不出真假);
夹具另钉住这条命令走的确是 `PUT /api/state`。

`tests/integration.js` 未加(本槽不新增端点);`tests/cli.smoke.js` 未加(那三条旧用例一个字未动)。

## 八、这一槽可复用的一件事

**"实现已对"与"树上有判据"是两件事,先量后写才分得开。**
本槽起手三档现跑(按 id 取首位、副本新 id、按名字够得着后几位)全部符合预期,
按"跑一遍看着对"的读法这一槽本该零产出;而同一刻变异 1–4 在基线上**一手都不红**——
四种把它改坏的写法,树上一条判据都拦不住。
量的是行为、判的是看守面,两个读数分开取,才不会把"现在是对的"错读成"往后也保得住"。

**判据的档要按"改坏的方式"分,不按"要断言的字段"分。**
①档已经把首位那一份逐字段对完了,变异 4(改成"第一位有图的")照样漏网:
两种改法在"首位有图"的夹具下产出完全相同。多出来的 ④ 档只改了夹具一处(首位删掉图),
接住的是一整类"换选位规则"的改法。
