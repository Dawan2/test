## 1. 先核实:预置专家是"被有意锁死"还是"漏了入口"

动手前要先分清这两种情况——若产品上是有意锁死,本槽就该只留一份核实记账、不硬开。逐处查下来的结论是
**漏入口**,判据三条:

1. **源码里没有锁死的理由,只有一句实况描述。** `js/experts.js` 那段注释原文是「仅自定义专家可用
   (预置 EXPERTS 不挂此按钮)」——它说的是"现在没挂",不是"不该挂";全仓再无第二处写过预置专家不得进化。
2. **上游记账把它记成待接的余量,而且连接法都写好了。** W43 的交接第 1 条点名"要接:让蒸馏按板块取记忆
   + 给预置专家一条『进化落到自定义副本』的入口",W65 收掉了前半句,并在自己的交接里写明后半句欠的是
   "复制时机与『副本由哪个预置专家派生』这个字段"。两处都把它当**未做**,不是当**不做**。
3. **零件都是现成的。** 自定义专家库 `customExperts()`、副本落库、`allExperts()` 合并、卡片渲染都在,
   缺的只是"谁来造这份副本、什么时候造"。

所以本槽按"补入口"办。

## 2. 为什么不能让预置专家原地进化

最省事的写法是把预置专家对象直接交给 `evolveExpert`,让它往 `e.persona` 上追加条款。这条路是死的,两个理由都是硬的:

- **存不住**。预置库 `EXPERTS` 是 `js/experts-data.js` 里的模块级常量,不在 `Store.state` 里;
  `Store.save()` 存的是 state 树,追加进 `EXPERTS[i].persona` 的条款刷新即失,用户会看到"进化成功"的
  toast 与"什么都没变"的人设。
- **两端会漂移**。同一份 `experts-data.js` 被服务端 `require`(`/api/wf/*` 按 `projTypeOf` 判解说/剧情模式,
  `personaFor` 按同一份表装配提示词)。浏览器内存里改一份,浏览器与服务端对同一个专家的 persona 就不再是同一份,
  而"两端提示词逐字节一致"正是这条链路一直在守的东西。

故落点只能是**自定义副本**:副本进 `Store.state.customExperts`,存得住、可编辑、可雇佣、可删除,
预置注册表一个字不改。

## 3. 落地

### 3.1 副本:`presetCopy`(`js/experts.js`)

```js
function presetCopy(e) {
  const had = customExperts().find(x => x.from === e.id);
  if (had) return had;
  const c = Object.assign(JSON.parse(JSON.stringify(e)), {
    id: 'cx_' + Date.now(), custom: true, from: e.id, name: (e.name + '·我的').slice(0, 20),
  });
  customExperts().push(c);
  Store.save();
  U.toast(`预置专家不可改写:已建可进化副本「${c.name}」,条款写进副本,雇佣该副本后生效`, 'info', 4000);
  return c;
}
```

四个决定各有出处:

| 决定 | 为什么 |
|---|---|
| `from` 记派生源 id | 雇佣事实挂在预置 id 上(`settings.hiredExpert` 或 `p.boards[板].expert` 存的都是 `ex_*`),副本要能算出生效板块就得认这一层;这个字段也正是 W65 交接点名欠的那个 |
| 同一预置专家只派生一份 | 每点一次进化造一份副本,用户的专家库会长出一串同名条目,且条款分散在各份上,谁都不完整 |
| 深拷贝(`JSON.parse(JSON.stringify)`) | 浅拷贝会让副本与预置共用 `dims`/`tpl` 两个嵌套对象——用户在工坊里改副本的五维就改到了注册表上(内存内污染,且服务端那份不跟随) |
| 名字带派生源名 | 专家库里两张卡不能都叫「摄影指导」;`·我的` 与卡上的「我的」标签同义,列表里一眼看得出它派生自谁 |

`projType` 这类判定字段随深拷贝带走,不用另接:`ExpertsData.projTypeOf` 判的是**字段**(`e.projType === 'narration'`)
而不是预置 id,所以副本被雇佣后解说模式不丢。这正好回答了 W65 交接里"副本被雇佣后 `projTypeOf` 之类按 id
判定的地方要不要跟着认派生源"——查下来按 id 判的地方只有"取出哪个专家对象"(`expertOf`),
取到副本本身即可,不需要认派生源。

### 3.2 生效板块:`expertBoards` 多认一个 `from`(`js/wf-core.js`)

```js
const ids = [e.id, e.from].filter(Boolean);
return list.filter(b => projects.some(p => {
  const bd = (p && p.boards && p.boards[b]) || null;
  return ids.indexOf((bd && bd.expert) || o.hiredId) >= 0;
}));
```

不加这一句,预置专家第一次点进化就会被第一道闸挡下:副本刚造出来时谁也没雇过它,`expertBoards` 回空。
按"雇佣事实"取板块是 W65 定下的口径(该专家的 persona 会被注入到哪些链路,就只吃这些链路所在板块的沉淀),
副本承接的正是派生源在那些板块上的活,所以认 `from` 是**沿用**这条口径而不是给它开口子:

- 派生源与副本都没被雇过,仍回空数组(`from` 不是"全部板块"的后门);
- 副本自己被雇在别的板块时两者取并集(它在两处都在工作);
- 不带 `from` 的普通自定义专家一个字不受影响(`ids` 就是原来那一个 id);
- 只有 `from` 没有 `id` 仍回空——`id` 仍是必备判据,与"专家无 id 不拿 `undefined` 去匹配"那条既有断言同序。

### 3.3 `evolveExpert`:目标换成 `t`,副本在两道闸之后才落库

```js
if (!mem.length) return U.toast(`「${bt}」板块暂无使用记录…`, 'info', 4000);
const t = EXPERTS.some(x => x.id === e.id) ? presetCopy(e) : e;
if (!U.requireCredits(1, '专家自进化')) return;
const tk = Tasks.start({ type: '专家自进化', model: 'LLM', target: t.name, cost: 1 });
```

三处要点:

- **判"是不是预置"用注册表反查,不用 `e.custom`。** 自定义专家不一定带 `custom: true`(手写入库那条路径带,
  测试夹具与早年数据不带),拿它当判据会把自定义专家误当预置去派生副本。
- **落库位置卡在两道闸之后、`requireCredits` 之前。** 闸没过就跳过,不给用户的专家库留一条什么也没蒸出来的
  空副本;而落在扣费之前,是因为副本本身零成本、也不该跟着扣费失败一起回滚(它已经是用户库里的一条正经专家了)。
  这个顺序有一条源级断言按三个字面的下标先后钉住。
- **`e` 只用来算板块与派生,`t` 承接后面全部写入**:LLM 的 `user` 半、本地去重、条款追加、`evolutions` 计数、
  任务 `target`、成功 toast 全部改取 `t`。去重取 `t.persona` 这一处尤其要紧——同一预置专家第二次进化时,
  要比对的是副本上已有的条款,不是预置那份原始人设。

板块过滤那一段(`expertBoards` → `memForBoards` → 两道闸)一行未动,所以预置路径与自定义路径吃到的是同一套过滤:
只收 `scope` 落在生效板块里的条目,无 `scope` 的手工沉淀不收,`system`/`user` 两侧都点名板块。

### 3.4 入口:两类预置卡各一个按钮(`js/gsettings.js`)

「偏好学习 → 专家雇佣」页有三类卡:平台预置风格导演、我的自定义专家、功能专家(预置 + 自定义混排)。
自定义那两类原本就有 `data-cevolve`;本槽给**预置风格卡**与**功能卡的预置那一支**各补一个 `data-pevolve`,
统一绑到同一个 `evolveExpert`:

```js
body.querySelectorAll('[data-pevolve]').forEach(b => b.onclick = () => evolveExpert(EXPERTS.find(x => x.id === b.dataset.pevolve), renderExperts));
```

至此人手触发点四个(工坊编辑区、工坊卡片、自定义卡片、预置卡片),四个都调同一个 `evolveExpert`——
断言数的就是这个 4,谁想给预置专家另起一套蒸馏(哪怕逻辑写对了)也会红。

顺带补一处:工坊编辑表单保存时按固定字段重建条目,会把 `from` 丢掉,下次点预置卡的进化就会再派生一份。
现在保存时把已有条目的 `from` 带回去。(同一处丢掉的还有 `evolutions` 角标计数,那是基线上就有的行为,
不在本槽口径内,未动。)

## 7. 交接

1. **G-11 只剩"自动进化"这一面,且本槽没有把它往前推**。要接得先定三件事,定不下来就不该动人手触发点:
   ① 触发时机(每 N 条同板块沉淀?审片闭环达标后?)——自动蒸馏每次 1 积分且**不可撤回地**改写 persona,
   挂错时机就是在用户不知情时连续扣费并改人设;② 可回滚——`persona` 是纯文本,条款进去就分不出是哪一轮蒸的
   (`e.evolutions` 只有计数),自动化之前应先让条款可溯源可撤;③ 预置路径下自动进化会**自动造副本**,
   等于替用户往专家库里加条目,这一层需要单独的产品口径。
2. **副本与派生源之间目前只有 `from` 一条线,没有同步**。预置专家的 persona 由平台版本更新,副本是那一刻的快照——
   平台改了预置人设,已派生的副本不跟随(也不该静默跟随,那会冲掉用户已蒸出的条款)。要做"派生源已更新"的提示,
   现成的判据是把派生那一刻的 `persona` 存一份指纹到副本上再比对,本槽没做。
3. **副本被雇佣前,蒸出来的条款不进任何链路**。`personaFor` 按 hired id 装配,副本没被雇就注入不到;
   派生时的 toast 明说了这一点,但用户仍可能"进化完以为生效了"。可接的做法是进化成功后在成功 toast 里
   给一个"立即雇佣该副本"的动作,本槽没做——那会把一次蒸馏变成一次雇佣(覆盖导演五维与三件套模板),
   属于产品决定不是补口。
4. **工坊编辑保存仍会丢 `evolutions` 角标计数**(基线上就有,本槽只补回了 `from`)。要修就把保存那段从
   "按固定字段重建"改成"在原条目上合并",顺带能保住将来可能加的派生源指纹之类字段。
