# W1 · skill 候选相关性判定标准(纳入 / 降级 / 拒绝)

> 基线 `master @ 9adcf0f`。本文是**判定标准**,不是功能清单,也不含任何代码改动。
> 上游输入:`w1-pipeline-skill-map.md`(资产图谱 + 缺口 G-01…G-15 + 建议纳入/丢弃的 skill 概念)、`w1-architecture-spec.md`(W2–W4 拆分与通用验收)、`w1-feishu-doc-b-extract.md`(外部资料 53 条结构化清单)。
> 本文第 7 章把标准逐条套到那 53 条上,给出**预判分档**;分档是判定结果,**不是排期承诺**,落地与否由用户筛选决定。

## 1. 这份标准解决什么

候选源源不断(外部资料提取、用户提议、并行分支的副产物),但仓库的约束是硬的:无构建、零依赖、双端单源、计费唯一权威在服务端。缺一把尺子,讨论就会停在"这个看起来挺有用"上——而"有用"和"能在这个仓库里落成可验收的单源实现"是两回事。

本文给的是**可操作**的尺子:每条判据都写清楚**用什么证据判**(读哪个文件、跑哪条 `rg`、写哪条断言),判完落成一条带分数与证据的记录。

### 1.1 判定对象

判定对象是**能力主张**(capability claim),不是外部文件、不是某个产品的功能。一条能力主张 = 「在主线的哪一步、给谁、解决什么可观测的问题」。

- 外部清单只是**发现候选的来源**;进入判定后,一律按本平台自己的口径重述,不携带来源信息。
- 一条外部条目可以拆成多条能力主张分别判(例如配音类条目拆成「渲染清单」与「禁止静默降级」两条,结论可以不同);多条外部条目也可以合并成一条(例如「钩子选型」与「钩子诊断」合并为一条前后配对的能力)。

### 1.2 与既有缺口的关系

缺口 `G-01…G-15` 是**已确认的工作项**,走 `w1-architecture-spec.md` 的 W2/W3/W4 波次,**不走本标准**——它们的问题是"何时做",不是"要不要做"。

本标准只判新候选。判定时必须先查重:

- 候选与某个缺口**同解** → 判定结论写"并入 G-xx",不另立条目(防止同一件事在两处排期)。
- 候选与**已实现能力**同解 → 命中否决项 V11(见第 3 章),拒绝并给出实现位置。

### 1.3 落地时的表述纪律

任一条目一旦判为"纳入",后续实现的代码注释、README、UI 文案**只描述功能本身**,不写来源、不做对比表述。判定记录留在本目录内即可,不外溢到产品面。

## 2. 打分维度

四个正向维度各 0–3 分,一个成本维度扣 0–3 分,总分区间 **−3 … 12**。

### R1 主线定位(0–3)

候选能不能挂到主线七步(`script/subjects/eps/shots/gen/review/film`)的某一步或某个明确的步间交接上?

| 分 | 判据 | 证据 |
|---|---|---|
| 3 | 明确落在某一步,`stage` 取值直接是 `Domain.workflow` 的主线步骤键 | 指出步骤键 |
| 2 | 落在两步之间的交接(如 `gen→review` 的产物移交) | 指出上下游两步 |
| 1 | 全线适用但无法定位到具体步骤(纯横切) | 说明横切面 |
| 0 | 落在主线之外(选题前、图文形态、非视频产物) | 说明落在何处 |

> `review` 目前不是 `Domain.workflow` 的一等步骤(G-03)。判定时按**七步口径**给分,并在记录里标注"依赖 G-03 落地"。

### R2 单源落点(0–3)

候选能不能落到既有单源件上,不新起一套?可落点只有这几个:`js/knowledge.js`(方法论文本)、`js/prompts.js`(可覆盖提示词)、`js/cmd-registry.js`(领域命令)、`js/skills.js`(W2 新增的索引注册表)、`js/domain.js`(领域推导)、`js/wf-core.js`(提示词拼装)、`js/release.js`(发布门)、`js/issues.js`(问题中心)。

| 分 | 判据 |
|---|---|
| 3 | 落点唯一且明确,只是往既有注册表加条目(加 `KB` 条目 / 加 `Prompts` key / 加 `Skills` 校验项 / 加发布门) |
| 2 | 落点明确但需要扩展既有结构(加字段、扩既有函数的返回) |
| 1 | 需要新增一个模块或新数据实体,但能沿用既有存储桶与加载方式 |
| 0 | 需要新存储桶 / 新页面 / 新交互体系,或落点讲不清 |

### R3 可验收(0–3)

判据是能不能**写成断言**。不能写成断言的能力主张,后续没人能证明它还在正常工作。

| 分 | 判据 |
|---|---|
| 3 | 纯本地可判定:能在 `tests/unit.js` 用"干净 fixture 全 pass / 脏 fixture 命中且分级正确"两组断言锁住 |
| 2 | 需要端到端但可锁:`tests/integration.js` 或 `tests/cli.smoke.js`(`MOCK_LLM=1`)能断言回执结构与写回 |
| 1 | 只能断言"提示词里出现了某段文本",判定本身仍靠 LLM 或人 |
| 0 | 结论完全主观,无 fixture 可锁 |

### R4 贯通收益(0–3)

对照本目录的发展重点——主线上的数据双向流动、状态一致、断点闭环。

| 分 | 判据 |
|---|---|
| 3 | 修复主线断点或两端不一致(浏览器与 `server.js`/`cli.js`/`mcp.js` 产出不同),或补上一段缺失的回写闭环 |
| 2 | 让某一步的产出可追溯 / 可复核 / 失败可续,主线不再靠人记状态 |
| 1 | 单点体验或单点质量改善,不改变主线的连通性 |
| 0 | 与主线连通性无关 |

### C1 接入成本(扣 0–3)

| 扣分 | 判据 |
|---|---|
| 0 | 只加注册表条目与断言 |
| 1 | 需要改一个既有构造点(提示词拼装点、命令 handler、发布门) |
| 2 | 需要新模块 / 新实体 / 改动生成指纹与判旧口径 / 新增服务端端点 |
| 3 | 需要动主线步骤集合、动计费路径、动既有产出口径(扇出到流程条、tab、跑批映射、Agent 步骤图) |

> 改动**生成指纹**(`Domain.shotInputHash`/`composedInputHash`)一律至少扣 2:指纹变了,存量项目的"素材过期"判定会一夜变化。

### 计分示例

`3/3/3/2−1 = 10` 表示 R1=3、R2=3、R3=3、R4=2、C1=1,总分 10。

## 3. 否决项(命中即拒绝,不再计分)

| 编号 | 否决项 | 怎么判 |
|---|---|---|
| V1 | 需要 npm / CDN / 打包器 / YAML 解析器 / 任何新运行时依赖 | 看候选的最小实现是否绕不开第三方;第三方库若确需,只能本地化到 `js/vendor/` 并单独评估 |
| V2 | 需要运行时动态加载 skill 文件(`import()` / `fetch` 拉 md/js) | `index.html` 是显式顺序清单,动态层会引入首屏竞态 |
| V3 | 需要沙箱执行任意 JS | 安全面与体积不划算,且与计费白名单冲突 |
| V4 | 引入新的计费标签面,或让付费动作绕开 `Tasks.run` / 服务端动作白名单 | 见第 4 章 T3/T9 |
| V5 | 需要新建与 `settings.promptOverrides` / `state.customExperts` 同类的存储桶 | 覆盖与自定义各只有一个桶 |
| V6 | 跨端逻辑必然写成两份(浏览器一份、服务端一份) | 见第 6 章 U1/U2 |
| V7 | 不可验收:结论靠人主观判断且无 fixture 可锁,同时**没有降级为纪律的余地** | R3=0 且不能改写成"提示词条款 + warn 级校验项" |
| V8 | 需要**移植**受限许可(如 CC BY-NC 4.0 等非商业许可)的文本 / 提示词 / 代码 | 只禁移植,不禁独立实现同类机制;判定记录须写明"独立实现,零文本拷贝" |
| V9 | 用占位或静默降级冒充成功 | 登录后端时失败必须如实报错并退费;仅离线回退 PH 占位 |
| V10 | 需要删除或跳过既有测试 | 只允许新增断言与新增套件 |
| V11 | 与**已实现**能力同解 | 必须给出实现位置(文件:行);给不出位置的不算命中 |

V11 是最常命中的一条,也是最容易判错的一条:**"部分重复"不算命中**。做法是把候选拆到最小能力主张,逐条查重,重复的部分判 V11 并注明位置,剩余的差量继续计分。

适用范围:候选会触发任何**上游调用或付费动作**时,本表全部项必须过。纯本地校验型候选只需过 T1。

| T1 | **零成本声明**:候选是否触发付费动作?若声称不触发,须证明零 LLM、零上游、零服务端生成端点 | 列出候选的全部外呼点;`check` 型 skill 的硬要求就是这一条 | 声称零成本却有外呼 → 退回重述,按付费路径重判 |

## 6. 契合检查表 C · 双端 UMD 契合

适用范围:候选逻辑会被浏览器与 `server.js`/`cli.js`/`mcp.js` 中的任意两方使用。

| 编号 | 检查项 | 判定方法 | 不过怎么办 |
|---|---|---|---|
| U1 | **跨端判定**:先回答"这段逻辑会不会在两个以上环境跑" | 列出使用方 | 会跨端却打算各写一份 → 命中 V6,拒绝 |
| U2 | **UMD 形态一致**:头部沿用仓库既有写法——`(function(root, factory){ … })(typeof self!=='undefined'?self:globalThis, function(deps){ … })`,Node 侧 `require` 注入依赖,浏览器侧从 `root` 取 | 对照 `js/prompts.js:5-9`、`js/wf-core.js:6-13`、`js/cmd-registry.js:6-10` | 形态不一致 → 加载顺序与 `node --check` 都会踩坑 |
| U3 | **模块内不碰环境**:模块体内零 `window` / `Store` / `document` / `location` / `fetch`;环境差异(生效专家、板块专家、记忆、覆盖表、在线态、`uid`/`now`)一律经 `ctx` 参数注入 | `rg -n "window\|Store\|document\|location\|fetch" js/<新模块>.js` 应只命中 UMD 头 | 有命中 → 服务端 require 即炸,或多用户串扰 |
| U4 | **文本不复制**:跨端模块只存 `KB` 条目键与 `Prompts` key,不内联方法论或提示词正文 | `rg` 候选文本在仓库内只有一处定义 | 复制文本 → 改一处忘一处,两端措辞漂移(G-15 就是这么来的) |
| U5 | **覆盖表显式传入**:服务端读提示词覆盖时,覆盖表由调用方经参数传入,模块不自己去取 | 读 `js/prompts.js:43-51`(`get(key, ov)`) | 模块自取 → 多用户串扰 |
| U6 | **加载点成对**:`index.html` 有显式插入位置,`server.js` 有对应 `require`,两处同一次提交改 | 对照 `js/knowledge.js` 的既有两处 | 只改一处 → 一端 `undefined` |
| U7 | **词表不另起**:景别 / 运镜 / 视角 / 角度以 `js/wf-core.js` 的 `SIZES`/`CAMERAS`/`VIEWS`/`ANGLES` 为准 | 读 `js/wf-core.js:21-24` | 另起一套 → 复制 G-07 的老问题 |
| U8 | **字面一致断言**:提供固定 fixture,断言两端输出**逐字节相同** | 沿用 `wf-core` 的既有做法,断言进 `tests/unit.js`(套件见 `tests/unit.js:3090` 的 `SUITES`) | 无此断言 → R3 最高给 1 |

**给分影响**:U1 判为跨端而 U2–U6 任一不过 → 不得判"纳入";U8 缺失 → R3 上限 1。

## 7. 分档规则与判定流程

### 7.1 三档

| 档 | 判据 | 含义 |
|---|---|---|
| **纳入** | 总分 ≥ 8,且 R1 ≥ 2,且 R2 ≥ 2,且无否决项,且第 4/5/6 章适用的检查表全过 | 进入排期讨论;记录里必须写清落点文件与验收断言 |
| **降级** | 总分 4–7;或总分 ≥ 8 但 R1/R2 有单项 < 2;或检查表有"给分影响"级不过项 | 不进代码排期,按 7.2 落到三个去向之一 |
| **拒绝** | 总分 ≤ 3,或命中任一否决项 | 硬拒(命中否决项)不再评;低分拒须附**再评条件** |

单项门槛(R1 ≥ 2、R2 ≥ 2)是为了挡住"分数靠 R3/R4 凑够、但既挂不到主线也说不清落点"的候选。

### 7.2 降级的三个去向

降级不是"以后再说",必须选一个去向并写下退出条件:

| 去向 | 什么时候选 | 落到哪里 | 退出条件 |
|---|---|---|---|
| **降级为纪律** | 判据清楚、成本主要在"约束人"而不是"写代码" | 写进 `AGENTS.md` 的改动纪律,或作为条款并入某条既有提示词 / `KB` 条目 | 纪律被违反两次以上 → 升级为 `check` 型校验项重判 |
| **降级为校验项** | 能判定但不该硬拦,或口径尚未稳定 | `js/skills.js` 的 `CHECKS`,默认 `warn` 级,不进发布门的 fail 面 | 连续两个版本 warn 命中率低于阈值且无误报 → 重判是否升为可选门 |
| **降级为待观察** | 方向合理但前提未成立(依赖某缺口先落地,或需要先核实既有实现的覆盖面) | 本文附录 B,一行一条,写明**前提**与**核实动作** | 前提成立 → 重新走一遍完整判定 |

### 7.3 判定流程

1. 把候选拆成最小能力主张,逐条判(不允许"一揽子"判定)。
2. 查重:命中 V11 → 拒绝并给出实现位置;与既有缺口同解 → 并入 G-xx。
3. 过否决项 V1–V11,命中即拒绝,记录停在这里。
4. 判适用的检查表(A/B/C),记下不过项。
5. 打 R1/R2/R3/R4/C1,算总分。
6. 按 7.1 分档;降级的选去向、拒绝的写再评条件。
7. 落成一条判定记录(模板见 7.4)。
