## 4. 冲突怎么解(逐处)

本轮 **14 处冲突全是"两侧各加了一半"的并集型**,没有一处是"择一丢弃"。四条被合分支的起支点都早于基线,所以形态高度一致:基线侧是超集(有审片消费、有分镜面、有面表),分支侧带一条基线没有的新增量。解法一律是**取基线全文 + 把分支侧独有的增量逐条补进去**。

补进去之前先用 `git diff --word-diff=porcelain <merge-base> <branch> -- <file>` 把该分支对这个文件的**全部**增量列出来,逐条勾掉,而不是凭冲突块里看到的那点内容判断——冲突块只是分支增量的一部分,另一部分在同一次合并里自动合并成功了(这一点见 5.1)。

## 5. 过程中踩到的两件事(方法面)

### 5.1 W16 第 5.1 节那个坑本轮换了个入口又踩了一次

W16 记的教训是「不要用 `git checkout --ours <file>` 整份取,它会把同一次合并里本已自动合并成功的 hunk 一并回退」。本轮**没有**用 `--ours`(冲突全部逐块手改),但在第 1 步冲突已解、测试已绿之后,为了取一份对照数据跑了 `git stash` + `git checkout <w16> -- .`。后者对**全部路径**生效:三个已手工解好的冲突文件、以及 `js/skills.js`/`js/commands.js`/`cli.js` 三个自动合并成功的文件,全被退回基线版本,索引也一并被改写(`git status` 只剩两个新增文档件)。

`MERGE_HEAD` 还在,故按 `git merge --abort` 干净退回,再重跑 `git merge` 并按同一套解法重做,重做后 `unit` 实测仍是 310/310(与被冲掉之前逐字相同),未留下残迹。

> **口径**:合并未提交期间,取对照数据只能在**独立 worktree**(`git worktree add`)里跑,不能在工作树上跑任何"按某个 commit 覆盖路径"的命令——`checkout <commit> -- <pathspec>` 与 `--ours` 是同一类风险的两个入口,前者甚至连非冲突文件也一起冲掉。本轮后续的三步对照数据全部改在 `/tmp/wt15`、`/tmp/wt16`、`/tmp/wt17`、`/tmp/wt18`、`/tmp/wt19` 五个独立 worktree 里取。

### 5.2 用例名集合比对,是"没删测"的唯一可核查证据

四步里有三步出现"分支的用例被取代",总数只 `+1`。如果只看总数,`+1` 与"合进来 2 条、吃掉 1 条"完全无法区分。本轮每一步都落一次名字集合(见 3.1 的表),比对结论逐条写进合并提交信息里,理由是:**README 的断言数是个标量,标量对不上时无法自证是加严还是删测**。
