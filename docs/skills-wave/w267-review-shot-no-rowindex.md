## 一、这一格具体错在哪

`order` 是落到库里的字段,不是"这一镜此刻排在第几行"。它与实位在这些动作后就分家:

| 动作 | `order` 字段 | 表内实位 | 屏幕上看到的 |
|---|---|---|---|
| 中间插一镜而没重排后续 | 后面几镜仍是旧号 | 逐行顺延 | 两镜同号(两个"镜头 5") |
| 删掉中间一镜 | 剩下的号中间空一格 | 逐行补齐 | 跳号(3 之后直接 5) |
| 拖动换序 | 不跟着换 | 跟着换 | 号与顺序对不上 |
| 同 id 多行 | 两行可能记着同一个号 | 两行各占一位 | 两行同号,点进去却是不同报告 |

而这两处展示面此前四处取号,分两族:

```
镜头 ${x.shot.order + 1}          // 清单行、导出文本、批量优化进度提示——读镜头对象上的字段
镜头 ${(ps.order || 0) + 1}       // "原报告已缺失"那一行——读 perShot 快照里记下的旧位
```

后一族更远一层:那是**审片当时**记进 `lastReview.perShot` 的号,快照之后表怎么变它都不知道,
于是缺失行报的号既不是实位、也不必等于同一份报告在别处报的号。

行本身早在 W263/W265 就按行对位取好了(`Domain.reviewRows` 落行、行键即行号、报告从清单里直接取),
唯独"给人看的那个数字"还从字段上读——**行取对了、号报错了**:点第三行确实开的是第三行那份报告,
而这一行的标签写着"镜头 8"。

## 二、改了什么

### 2.1 `js/domain.js` +7:镜号取法下沉一处

```
D.shotNo = function (rows, shot) {
  const i = D.rowIndexOf(rows, shot);
  return i >= 0 ? i + 1 : 0;
};
```

三点交代:

- **长在 `D.rowIndexOf` 之上,不另抄一份对位**:同 id 多行时按行对象身份定位,拿不到身份(不是同一棵树上的
  对象)才退回按 id 首行——与 `nthShot` / `reviewRows` 的兜底逐字同口径,不在展示层重新定义一遍"这是第几行"。
- **表里已经没有这一镜时回 0**:0 不是任何一镜的镜号,展示面据此按"未知"出(`${… || '?'}`);
  不拿首行的号冒充,也不算出 `0` 当成"镜头 0"糊在屏幕上。
- 只管**给人看的序号**:库里的 `order` 字段一个没改写,任何按 `order` 排序/落库/回写的路径都不经本函数。

### 2.2 `js/review.js` +9 −8:整集报告视图 `openEpisodeReport` 四处

清单行、"原报告已缺失"行、导出文本、批量一键优化的进度提示,一律改成 `Domain.shotNo(ep.shots, …)`。
缺失行那一处顺带把 `missing.push(t.ps)` 换成 `missing.push(t)`——`t` 是 `Domain.reviewRows` 落好行的那一条
(带 `ps` / `i` / `shot` 三样),换过去之后这一行才有"自己那一行"可指,不必再回快照里读旧位;
渲染处相应改读 `t.ps.score`,分数取的仍是当时那份快照(镜号换取法不动分)。

### 2.3 `js/batchops.js` +2 −1:汇总面 `openReviewSummary` 一处

清单行同改。这一处与 2.2 的清单行**必须同轮**:同一批镜在两块面上报不同的号,比两块都报错还难查。

### 有意没碰的

- 库里的 `order` 字段**不批量改写**(按明令):本槽只改"给人看的序号怎么取"。
- 合入侧一个字未动(`landed` / `state-put` / `gaps()` / SK-04 / `mergeReviewPerShot` 一律未触);
  浏览器闭环 `common` / `cut` 空壳 vs 服务端沿用、`openEpisodeReview` 整表与 generating 过滤,
  三条产品口径按明令不碰;同 id 多行的源头与 `shots-dedupe` 未碰。
- 计费一处未触(两块展示面零 LLM 零上游,不经 `Tasks.run`)。
- 这两处之外的「镜头 N」仍读 `order`(报告页页头 `视频 #N-M`、审片记录列表标题、生成中拦截提示、
  分镜卡与批量面板那一批)——不在本槽的两处展示面内,原样留档见 §六。

M1 与 M2 是本槽设计上的要点:**只改一处的改法必须能被点名**。两手各自只红自己那一块面,
另一块面的行为判据一条不红——这正是"两处必须一起改"这句交接能被判据兜住的证据,
而不是靠一条大用例把两块面糊在一起(那样只改一处也会红,但报的句子分不出漏的是哪一块)。
M5 是取法层的:它不动任何展示面,两条行为面用例(夹具里逐行 id 互不相同)一条不红,由 `domain` 那条咬住。

## 六、残留(按明令一条没代修,原话保留)

1. **浏览器闭环 `common` / `cut` 空壳 vs 服务端沿用**(W261 §六 2、W263 §六 2、W265 §六 1 记的):
   写回的一直是空壳,不是被子集跑弄丢的;要收得先定「浏览器闭环该不该沿用上一轮的集级结论」,
   属产品口径不属寻址。

2. **`js/review.js` 的 `openEpisodeReview` 整表覆盖与 generating 过滤**(W261 §六 3、W265 §六 2、W266 §六 3 记的):
   整表那一档合并对它是恒等;有镜在生成中时上一轮那些行不在新 `perShot` 里,是否算行为差归同一笔产品口径。

   它明写的「引用面按 find 首行语义解析、首行留原 id」这条前提**在本槽之后仍成立**——
   `shotNo` 改的是"给人看的序号从哪儿取",不改任何按 id 的库形态解析。

4. **本槽两处之外的「镜头 N」仍读 `order` 字段**(新记一条,不代修):现取点名——
   `js/review.js:246` 报告页页头 `视频 #${epIdx}-${s.order + 1}`(集号早已按行对位取,镜号这一半还没有)、
   `:195` / `:198` / `:200` 生成中拦截与任务名/扣费摘要、`:726` 审片记录列表标题;
   另有 `js/sb-io.js`、`js/sb-gen.js`、`js/sb-batch.js`、`js/batchops.js` 前段、`js/issues.js`、`js/produce.js` 同形。
   收法已经现成(`Domain.shotNo` 就位),但它们分属分镜面、生成面、任务/扣费摘要、问题中心几条不同的面,
   各有各的口径要定(任务名与扣费摘要是**落库文本**,改取法等于改历史记录的可读性对照,不能与展示面一起顺手改)。

5. **库里的 `order` 字段本身仍可能与实位漂移**(明令不在本槽改):本槽只让"给人看的序号"绕开它,
   没有做任何重排或回写。它还被排序、落库、回写路径读着,要收是另一条线。
