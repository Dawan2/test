**本槽最值得记下的三件事:**

1. **「两侧同值故零冲突块」这个形态第一次是错的,而且错得静默。**
   前十来槽把数字撞车归成三种形态(两侧同值故零冲突块 / 只有一侧在 diff 里 / 两侧不同值进冲突块),
   头一种一直被当成良性:两边写一样的数,`git` 直接合上,人不用判。
   本槽两条槽**叉在同一个基线 tip 上、又各加一份记账件**,于是两边都把明写份数从 144 改成 **145**——
   逐字相同,`git` 零冲突块自动合上,而合并后目录里的实况是 **146**。
   两侧同值这次不代表"没有分歧",它代表**两边算的是同一个错**(各自只看得见自己那一份)。
   接住它的是 W105 那条三方对齐(份数 / 目录实况 / 索引行数),合上就报「期望 145,实际 146」;
   **零冲突块的那一处反而是本槽唯一一处 `git` 帮不上忙、只有断言拦得住的地方**(见 4.1)。

2. **W132 那条新判据接得住它自己那侧的旧值,接不住 W131 那侧的。**
   合并后单元 live 是 492,两侧带过来的 `FLOOR` 一个是 491(W131)、一个是 487(W132)。
   照 W132 自己立的 `live - floor <= 3`:487 差 5 格**当场红**,491 差 1 格**全绿**(变异 12 实测)。
   这不是判据失灵,正是它明写过的设计——常规加测槽(一轮 1–3 条)不必同轮改那个字面,
   否则就变回 W105 拒过的 `==`。但落到"合并槽不许抄父分支的数"这件事上,结论是明确的:
   **两个 `FLOOR` 字面没有机器判据逼你取 live**(变异 12/13 两处各静默一次),
   本槽是照 W121/W129 传下来的人工纪律抬到 492 / 146 的,而 README 那三处数各有断言逼着(变异 8/9)。
   两类数在"抄父分支会不会被逮住"这一点上**不同类**,本文分开记(见 4.2)。

3. **`js/` 与四个 Node 端这次全面进 diff,而七个治理数一个没动。**
   W131 一条槽同时改了 `cli.js`、`server.js` 与四个 `js/` 模块——本线自 W117 以来最宽的一次代码面,
   而它是把**同一份判据**从四处调用侧收进 `Domain` 一处,故广度来自"消费点多"而不是"新增了什么"。

## 4. 逐处怎么解

### 4.1 五个数一律现取合并后 live,一个不抄父分支

| 落点 | 基线 | `w131` | `w132` | 合入后 live | 形态 |
|---|---|---|---|---|---|
| `README.md`「`contract` 实测 N 条断言」 | 104 | 106 | 105 | **107** | 两侧不同值,进冲突块 |
| `README.md`「单元测试(N 项断言)」 | 486 | 491 | 487 | **492** | 两侧不同值,进冲突块 |
| `tests/unit.js` 三套件下限表·单元格 | 486 | 491 | 487 | **492** | 两侧不同值,进冲突块 |
| `docs/skills-wave/README.md` 明写份数 | 144 | 145 | 145 | **146** | **两侧同值,零冲突块** |
| `tests/unit.js` 记账件 `FLOOR` | 144 | 145 | 145 | **146** | **两侧同值,零冲突块** |

前三处是老形态,按本线一贯口径取合并后实况即可:
`contract` 是 104 + W131 的 2 条 + W132 的 1 条 = 107,单元是 486 + 5 + 1 = 492,两个都现跑对过(5.1)。

**后两处是本线第一次踩的新形态**。两侧写的都是 145,因为各自只看得见自己那一份记账件
(基线 144 + 自己 1);合并后目录里同时有 `w131-g03-shotids.md` 与 `w132-floor-lag.md`,实况是 **146**。
"两侧同值"在前十来槽里一直等价于"没有分歧、不用判",本槽把这个等价关系证伪了:
**同值也可以是同错**,而且因为零冲突块,它是这次唯一一处 `git` 不会请你过目的改动。
接住它的是 W105 那条三方对齐(明写份数 / 目录实况 / 索引行数),合上即报
「目录里的 `wNN-*.md` 份数应等于 README 明写的份数:期望 145,实际 146」——**是断言逮到的,不是人看出来的**。

本文落地后这两个数再各抬一格到 **147**(含本文那一份),落在记账提交里。

### 4.2 两类数在"抄父分支会不会被逮住"上不同类

上表五个落点分两类,本槽逐个实测过(变异 8/9/12/13):

| 类 | 落点 | 抄父分支的值会怎样 |
|---|---|---|
| **有断言逼着取 live** | `README.md` 两处数字、明写份数 | 抄 106 红「与实测不符」;抄 491 红两条(相等对账 + 三套件下限的文档那一句);留 145 红三方对齐 |
| **没有断言逼着取 live** | `tests/unit.js` 两个 `FLOOR` 字面 | 留 491 **全绿**(差 1 ≤ SLACK 3);留 145 **全绿**(同理);只有 W132 自己那侧的 487 会红(差 5) |

第二类不是缺陷,是 W132 明写的取舍(不写成 `live === floor`,否则每加一条用例都得同轮改那个字面)。
但它对合并槽的含义要写清楚:**"禁止抄父分支的数字"这条纪律在两个 `FLOOR` 上是纯人工的**,
本槽照 W121 立规、W129 复述的那条义务("新增用例的槽有义务把 `FLOOR` 抬到当轮实况")抬到 492 / 146。
顺带一记:W132 这条新判据**接得住它自己带来的旧值、接不住 W131 带来的**——
如果本槽只合 `w132` 一条,漏抬当场红;两条一起合、又先合了 `w131`,那个静默窗口就重新出现。

### 4.3 索引表两行是并集,不是二选一

两侧各在索引表尾插了自己那一行(`w131` 一行、`w132` 一行),位置相邻故进冲突块。
**解法是并集**:两行都留、按波次号排在 `w129` 之后,不做任何取舍。
这一处有机器判据兜底且是**按份点名**的(W105 那条"每份 `wNN-*.md` 各要有自己那行索引"):
变异 7 只摘掉 `w131` 那一行(文件仍在)当场红三条,其中一条直接点名
「记账件 `w131-g03-shotids.md` 在目录里但索引表没有它那一行(合入时漏登记,**或只合到了漏掉索引行的那一版**)」——
那句括号里的话正是为本槽这种场景写的。

### 4.4 契约段那句散文:两侧不是口径之争,是纯插入

W127 那槽撞过「两侧改的是同一句话、给的是两种口径」,当时的解法是"取有机器判据那一侧的口径"。
本槽这一处**不是那回事**,现查如下:把两侧那一整行按条数归一化后与基线逐字比对,
`w131` 侧与基线**逐字相同**(它只改了那个数),`w132` 侧相对基线是**一处纯插入**(零删除):
插进去的是「**四条下限自己也不许静默落后实况**……」那一段,描述的正是它新加的那条断言。

故并集是唯一解、不需要判谁的口径:**取 `w132` 的散文 + live 条数 107**。
本文把这一处单列出来,是因为它与 W127 那处形状很像而处置不同——
分辨点是"两侧的差异里有没有删除":有删除才可能是口径之争,纯插入就只是两件事凑在同一行。

### 4.5 接进来的散文里的历史时点数,一律不改

`w131-g03-shotids.md` 与 `w132-floor-lag.md` 正文里写着「unit 486 → 491」「某槽一次松 6 格」这类
**它们自己那条线上的读数**。这些不改(改了就是篡改别人的记账),它们都带时点语境。
本槽逐处确认:`w131` 那份写的 491 与 `w132` 那份写的 487 **都不等于合并后 live 492**,
这与 W129 那次(叉点重合故对侧的数恰好也是 live)不同——**两条槽一起合进来时,谁的数都不再是答案**。
