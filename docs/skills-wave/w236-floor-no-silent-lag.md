## 1. 本槽要判的那件事

W234 合入线上现跑的记账件那格棘轮是这么两层:

```
assertEq(waves.length, declared, …)   // 目录实况 == README 明写份数
assert(waves.length >= FLOOR, …)      // 只增不减
```

外加 W132 立的第三层「差额有上限」:`live - floor <= SLACK`,而 `SLACK = 3`。

三层叠起来仍放行这一条路:**合入时那个 `FLOOR` 字面从某一侧父分支的冲突块里抄过来**(必然偏低——
那一侧看不见别槽新增的条数),而**声明份数照合并后的实况写成 live**。于是目录 == 声明成立、
`live >= floor` 成立、差额 1–2 格也在预算内,**整套全绿**。落后的那 1–2 份从此删起来只剩文档数字一道守卫,
等于"后来把记账件删掉也不报警"。

这一条不是假想:`w134-integration-log.md` 已经量过同一形状(合并后 live 149,抄我方父值 147 差 2 格全绿、
抄对侧父值 145 差 4 格当场红),并把结论写成「这条判据逮不逮得住取决于 `live − 父值` 有没有越过 3,与"抄没抄"无关」。
本槽要回答的是它的后半句:**这 3 格该不该收成 0。**

## 2. 现判据 live 现取:不止记账件一格,是五格共用一个 `SLACK`

开工现取 `tests/unit.js`,`contract` 套件里与下限有关的判据一共三层、五格:

| 层 | 用例 | 判的是 | 覆盖 |
|---|---|---|---|
| L1 相等 | 三套件用例数由各自源码实计 / 记账件三方对齐 | 实测 == 文档明写 | 单元、集成、CLI 冒烟、记账件份数 |
| L2 只增不减 | 三套件用例数只增不减 / 记账件份数只增不减 / 护栏主题总数不低于 `TOPIC_FLOOR` | `live >= floor` | 五格 |
| L3 差额上限 | 棘轮下限不得静默落后实况 | `live - floor <= SLACK`,`SLACK = 3` | 五格(单元、集成、CLI 冒烟、记账件份数、护栏主题) |

五个字面现取自 `tests/unit.js` 自己的源码:三套件那张表按 `['套件名', 数字,` 取三格、
记账件那条按 `const FLOOR = 数字;` 取一格、护栏主题那格按 `const TOPIC_FLOOR = 数字;` 取一格,取不到即红。
本槽落地前的实况(基线 `99ab79e`):

| 格 | FLOOR | live | 差额 |
|---|---|---|---|
| 单元测试 | 653 | 653 | 0 |
| 集成测试 | 148 | 148 | 0 |
| CLI 冒烟 | 113 | 113 | 0 |
| 记账件份数 | 249 | 249 | 0 |
| 护栏主题 | 19 | 19(在册 19 + 销号 0) | 0 |

**五格差额现取全为 0**,`node tests/unit.js` 在基线上 653/653 全绿、`contract` 140/140。
也就是说本槽要判的不是一处正在流血的伤口,而是一个此刻关着、合入时才张开的口子——
下一次多槽合并它就又张到 1–2 格(§3 逐次量了它历史上张开过几次、张到多大)。

## 3. 取证一:这 3 格缓冲,合入纪律用过没有

遍历本分支 first-parent 全历史(`git rev-list --first-parent`),逐提交把五格的 `FLOOR` 字面与
当时的 live 现算出来(单元取 `README.md` 明写数——它由 L1 强制等于实测;集成/冒烟取行首 `report(` 行数;
记账件取 `git ls-tree` 下的 `wNN-*.md` 份数;护栏主题按数组段里的条目数),得到:

- 含 `tests/unit.js` 的提交 **288** 个;
- 差额非 0 的 (提交, 格) 共 **21** 处,分布 `{1: 12, 2: 5, 3: 1, 6: 1, -1: 2}`。

按"当时有没有 L3 这条判据"(该提交的 `tests/unit.js` 里有没有 `const SLACK`)切开:

| 时期 | 落后 1–3 格 | 落后 4 格以上 | 下限反超 live |
|---|---|---|---|
| W132 之前(无 L3) | 4 处 | 1 处(`00cf2f8` merge(w128) 单元格松 6 格,W129 交接第 2 条记的就是它) | 0 |
| W132 之后(`SLACK = 3`) | **14 处** | 0 | 2 处 |

W132 之后那 14 处落在 **13 个提交**上,其中 **12 个是合并提交**(`--no-ff` 的两父提交),
1 个是集成记账件那一提交(`ba97ae3`)。形状高度一致:多槽并进时每合一支 live 就 +1,
而 `FLOOR` 字面来自某一侧父分支的冲突块解,差额于是沿着合并线一格一格涨,
直到集成记账件那一提交才按"含本文的 live"一次校回 0(W234 那次的提交标题写的就是「份数与记账件下限按含本文的 live 校到 249」)。

差额取到 **3** 的那一次是 `5fdef56`(merge(w167)):记账件那格 `FLOOR = 179`、live 182,**恰好用满预算**。
它前面两个提交分别是 1 格(`c889fcd`)与 2 格(`8787438`)——同一条集成线上连合三支,第三支合完正好顶格。

**结论:这 3 格不是没人用的余量,它就是合入期的减压阀本身。** 把 `SLACK` 改成 0,
上面 13 个提交会当场全红——合入员必须在**每一个合并提交内部**把 `FLOOR` 字面改成"合并后的实况",
而合并后的实况要合完才算得出来,等于把"合完再校一次"这道工序塞进每一次冲突解。
这正是 W105 拒 `==`、W132 写明"常规加测槽照旧不必改那些字面"时算过的那笔账。

## 4. 取证二:静默落后有没有真造成过误收

判「误收」按最直接的口径查:**有没有哪一份记账件或哪一条用例真的少过。**

- `git log --diff-filter=D -- 'docs/skills-wave/w*.md'` → **零条**,历史上没有任何一份 `wNN-*.md` 被删过。
- `git log --diff-filter=D -- tests/` → **零条**。
- 逐提交比对四个 live 序列(单元 / 集成 / CLI 冒烟 / 记账件份数)有没有相对前一提交下降 → **一次都没有**。

那 2 处「下限反超 live」(`7724e5b` merge(w222) 记账件 `FLOOR = 236` 而 live 235、
`73aec65` merge(w229) `FLOOR = 243` 而 live 242)不是删除,是合并当轮**记账件文件没跟着索引行一起落地**。
现跑核实 `7724e5b` 那棵树:`node tests/unit.js contract` **138/139,红 1 条**,报的是
「目录里的 `wNN-*.md` 份数应等于 README 明写的份数:期望 236,实际 235」——
**真少一份时接住它的是 L1 相等那一层,不是 `FLOOR`**。这一点很要紧:
只要"声明份数"照实写,少一份当场红;`FLOOR` 落后并不参与这一路。

**结论:静默落后至今零误收。** 它是一个开着的口子,不是一次已经发生的事故。

### 4.1 口子比想的窄一格:被别处链过的记账件删不掉

现跑量口子的实际宽度时撞出一条本槽之前没人写下来的事实。
第一次拿 `w105` / `w120` 两份去演"静默删两份",**红了**——报的不是份数,是
「目录内相对链接不许悬空:`w109-integration-log.md → w105-index-completeness.md`(文件不存在)」等 6 条:
别的记账件正文里用目录内相对链接点过它们。换两份**全目录内除索引行外零链接**的(`w94` / `w97`)再演,才 141/141 全绿。

按现取扫一遍:250 份里**除索引行外零链接的有 129 份**,另外 121 份被别处正文点着,
删它们会红在"相对链接不许悬空"那一层而与 `FLOOR` 无关。
所以这个口子的准确宽度是「落后 N 格 × **只在那 129 份里挑**」。这不改变判定(129 份足够大),
但它解释了为什么这条口子至今没被踩响过一次。

## 5. 判定:停在停工位,`SLACK` 一字不改

本槽的停工条件是两条**同时**成立才动手:缓冲从未被合入纪律需要、且静默落后已真发生过误收。
§3 与 §4 现跑给的答案是**两条都不成立**:

- 缓冲被用过 14 次、顶格用满过 1 次,改成 0 会让 13 个历史合并提交转红,也会给往后每一次多槽合并加一道工序;
- 误收零次,少一份的那两次都由相等那一层当场接住。

故 **不把 `SLACK` 改成 0,也不改成 `FLOOR === live`**。本槽只做记账,外加把 §1 那个反例从"人记得"钉成"机器记着"。

顺带划清一句:这 3 格能被静默删掉的前提是**同轮把声明份数一起改小**——
只删文件不改声明,L1 当场红(§4 实测);只改声明不删文件,L1 同样红。
所以口子的准确形状是「**下限落后 N 格 + 一次同步改小两处,且只在没被别处链过的那 129 份里挑** = N 份可静默撤走」
(§4.1),而不是"随手就能删"。

## 6. 落地:判词抽成纯函数,再拿造出来的格子钉它自己

L3 那条用例此前把判据写在自己的 `forEach` 里,于是"它到底放行什么"只能靠读代码。
照 `topicLedgerVerdict`(W175/W178)与 `guardSpread`(W170)的既有做法,把判词抽成纯函数:

```
function floorLagVerdict({ live, floors, slack }) → 红句数组(全绿回 [])
```

**判据逻辑一字未变**:仍是 `live[label] - floor > slack` 才出句,句子内容逐字沿用原报错文案。
只多了一路——格名与 `live` 表对不上时报「这一格取不到实况」,与"下限落后"分成两句不混报
(改格名只改一头时,此前那一路会算出 `NaN > slack === false` 而**静默判绿**)。

L3 那条用例改成把五格现取的 `floor` 与 live 喂进这个函数、`assertEq(lines.join(' / '), '')`;
新增一条用例喂造出来的格子,把 §1 那个反例钉成明面:

| 喂进去的 | 钉住的 |
|---|---|
| 差额 `0 … slack` 逐格 | 判词回空——**这就是"抄偏低 FLOOR + 声明写成 live"在合入槽里一路全绿的全部原因**,是判据明写的承诺不是漏判 |
| 差额 `slack + 1` | 恰报 1 条、以格名打头、句里写得出落后几格与上限几格 |
| 下限高于 live 2 格 | 回空——抬过头归 `live >= floor` 那一层,两种失败处置相反,不许混进同一句 |
| 两格同喂、只有一格越界 | 只报越界那格,没越界的那格不被拖红也不被盖住 |
| 格名与 live 表对不上 | 报「取不到实况」,与"下限落后"可分 |
| L3 那条用例的源码 | 必须真的经 `floorLagVerdict(` 取判词(它自己另写一遍循环,本条抽样证到的就不是它在跑的那份) |

`slack` 与五个 `FLOOR` 同口径现取自 `tests/unit.js` 源码里那个 `const SLACK = 数字;` 字面,
取不到即红——**改名、挪窝、把 L3 整条搬走时本条先红,不许静默退化成恒真**。
有意**不**断言 `slack === 3`:那会把"收紧"也变成红,而收紧本来就该是允许的动作。
