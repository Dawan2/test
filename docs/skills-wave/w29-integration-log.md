## 4. 冲突怎么解(逐处)

二十三处冲突全是并集型,没有一处需要择一丢弃。解法一律是**先用 `git diff --word-diff=porcelain <merge-base> <branch> -- <file>` 把该分支对这个文件的全部增量列出来,再逐条补进基线全文**,而不是凭冲突块里看到的那点内容判断——冲突块只是分支增量的一部分,另一部分在同一次合并里已自动合并成功。本轮 `w27` 与 `w28` 的 README 增量都有一半落在冲突块之外,靠这一步才捞回来。

`README.md` 的长行问题原样存在(几段各自是**一整行**,单行超过 4000 字,行级三方合并对它们完全无能为力)。W25 用的是"按句切分后跑 `git merge-file`",本轮换了个更省事、也更容易复核的路子:

```
# 1) 冲突块一律先取 HEAD 侧(基线是三路里的超集,冲突块内它一侧最全)
# 2) 再把对侧的增量逐句 StrReplace 折回去 —— 增量清单来自上面那条 word-diff
```

这不是 `git checkout --ours <file>`。区别在第 2 步:`--ours` 整份取会**静默丢掉**对侧那一整行里的全部新句子,而本轮对每一处都按 word-diff 清单把对侧新增句子折了回来,并逐条 `grep` 复核终态在位(`shots.stableLexicon`/`stable-word-partial`/`vague-word`/`校验层同源`/`gen.renderCredential`/`credential-missing`/`sim-credential` 等)。

> **口径**:README 这类"一段一行"的长行文档,冲突时不要在行级硬解,更不要 `git checkout --ours <file>` 整份取(W16 第 5.1 节记过那个坑)。两条路都行:句级切分跑 `merge-file`(W25),或"取一侧 + 按 word-diff 折回对侧增量"(本轮)。后者的复核点更集中——只要 word-diff 清单逐条在终态 `grep` 得到,就没有静默丢句。

## 5. 合并后必须重新对齐的断言(逐条说明为什么不是删测换绿)

合并本身零冲突地把四侧代码并到了一起,但**各侧断言描述的都是自己那一半的世界**。逐条记录改法与理由,便于复核这里没有一条是判据变弱:

| # | 断言 | 原判据 | 改成 | 为什么不是放宽 |
|---|---|---|---|---|
