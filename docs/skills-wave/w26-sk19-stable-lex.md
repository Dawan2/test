## 2. 判定输入为什么是 `Domain.buildVideoRequest`

抽卡军规治的是**模型读到的那条提示词**,而分镜字段 `s.prompt` 只是它的一部分。真实请求由 `Domain.buildVideoRequest` 装配(与真实发送、生成指纹同一构造点):

```
prompt = 主体定义前置 + s.prompt/s.plot + 轴线规则 + 运镜 + 机位 + 美术风格后缀 + 负面约束
```

判 `s.prompt` 会在两个方向上判错:

| 情形 | 判分镜字段 | 判真实请求 |
|---|---|---|
| 稳定词写在**本集美术风格后缀**(`ep.styleSuffix`)里,逐镜提示词不重复写 | 全集每一镜都报"没写稳定词" | 无命中(后缀已随请求发出) |
| 项目负面约束/主体定义前置带进来的词 | 看不见 | 看得见,与模型口径一致 |

这两条各有一条用例钉着,其中第一条同时断言 `DomainMod.buildVideoRequest(...).prompt` 确实含该词而 `shot.prompt` 不含——把"判的是同一份输入"写成可执行断言而不是注释里的说法。变异实测:把判定基面从 `q.prompt` 换成 `s.prompt || s.plot`,该用例当场红。

**不注入、不改指纹**:本项只**读**这份请求,`Domain.buildVideoRequest` 与 `shotInputHash` 的字段清单一字未动(与 W15/W19 同一条纪律——生成请求构造点不注方法论文本,否则存量已出片镜头全量失配)。

## 3. 判什么、不判什么

三条命中码,全部 `warn`:

| 码 | 判据 | 出处 |
|---|---|---|
| `no-stable-word` | 整条提示词一个稳定词都没有;`miss` 列出该补的三个字面 | 军规③「必加稳定词」 |
| `stable-word-partial` | 稳定词只写了一部分;`name` 给已写的、`miss` 给缺的 | 同上 |
| `vague-word` | 命中条目自己列的模糊词,逐词一条 | 军规⑤「"好看/很美/很酷"等于没写」 |

不判的几件事,以及为什么:

- **通用的"稳定"二字不收进稳定词表**。运镜与机位描述里也出现得到(「平稳横移」「固定镜头」「画面稳定」),收进来会把一条根本没写解剖稳定约束的提示词判成写了。用例里正有一条 `镜头平稳,画面稳定,缓慢推镜` 仍判 `no-stable-word`。
- **军规③ 第四面「同一角色服装发型一致」不收**。有主体参考图组时,那句一致性声明由请求装配自带(`shotRefImages` 的主体定义后缀),收进来等于每个带参考图的镜都自动"及格";而锁得住锁不住本就是 SK-13 跨镜一致性面的判据,不在本项重复。用例断言:请求里含「严格保持一致」的镜,稳定词面照报 `no-stable-word`。
- **军规①(动作写慢写连续)与②(运镜写稳写简单)不在本项**。它们的字面判据与 SK-13 那条多镜头写法校验(`w22` 槽的 `frames-motion-overrun`)会在大动作词表上重叠,两处都报同一件事是噪音。
- **八维填得全不全、动作写得慢不慢、这个提示词好不好**仍归 LLM 审片(G-10)。本层只判文本层看得见的字面,不冒充质量评分——与剧本段/分集段/景别面同一条纪律。

## 4. 词表单源:从条目正文现筛,不写第二份

稳定词与模糊词都不在 skill 层写死清单:

```js
const GC_LEX = String(KB.section('抽卡军规') || '') + String(KB.section('抽卡公式') || '');
const STABLE_WORDS = ['不变形', '结构正常', '不僵硬'].filter(w => GC_LEX.indexOf(w) >= 0);
const VAGUE_WORDS = String((String(KB.section('抽卡军规') || '').match(/模糊词[((]"([^"]*)"/) || [])[1] || '')
  .split('/').map(w => w.trim()).filter(Boolean);
```

稳定词沿用既有的「判据现取条目正文」纪律(SK-09 的单句阈值 `DIALOGUE_MAX`、SK-14 的六段区间同理):候选是两条条目共有的那三面解剖/动作约束,条目里没有的字面一律不进判据。模糊词更进一步——**整份词表从条目正文里切出来**,skill 层连字面都不出现(有一条断言:`js/skills.js` 里不得含「好看/很美/很酷」)。

条目被改写时的行为是**判据退空,不是假命中**。变异实测(两条条目里的相关字面全部改掉):

| 变异 | 校验项行为 | 转红的断言 |
|---|---|---|
| 只改「抽卡军规」③,「抽卡公式」骨架照旧 | 判据不变(取的是两条的并集) | 1 条:词表单源(要求每个字面**同时**在两条正文里) |
| 两条条目的相关字面全改 | 命中数归零,不产出任何结论 | 5 条:三条行为用例 + 词表单源 + 纯函数那条的 plot 分支 |

即:条目改写既不会让校验项拿失配的字面去误报,也不会静默地把这一面变成永远 `info`——口径断言先红,逼着改写方回来对齐。

## 5. 消费点:面表自动跟上,两端实现零改动

SK-19 的登记变化只有三处:

| 字段 | 改前 | 改后 |
|---|---|---|
| `kinds` / `pending` | `['inject','check']` / `['check']` | `['inject','check']` / `[]` |
| `checks` | `[]` | `['shots.stableLexicon']` |
| `cmds` | `['episode.generateStoryboard']` | `['episode.generateStoryboard','episode.preflight']` |

`gaps` 保持 `['G-15','G-05','G-10']` 不动:本槽落地的是文本层那一面,G-10(语义面归审片)照旧开着,另两项与本面无关。

分镜面(`shots`)早在 W13 落 SK-18 时就进了 `Skills.preflightStages()`,所以本条落地后**面表内容一字不变**,而 `Skills.check('shots', …)` 自动多跑一条——`js/commands.js` 与 `cli.js` 的 preflight 段一行未改。这正是 W17 收表要的效果(见 [w17-preflight-stages.md](./w17-preflight-stages.md) 第 6 节第三条变异所预演的路径),本槽是它的第一次真实兑现:新增校验项的完整动作 = 注册表登记一处 + 抬一处口径数字。

抬的口径数字共四处(全部是"现有 N 条"这类快照断言,一条测试都没删):`commands` 套件的九条 `skill` 期望串加一项、`skills` 套件的分镜步条数 1→2、面表两处 9→10。

**只报不拦**,由用例钉住:

- 不进 `blockers`、不改 `ok/status`(preflight 行为断言原样通过);
- 问题中心不新挂提醒——`js/issues.js` 按具体校验项 id 取 `hits`,本面没有取值点,断言 `issues.js` 里不出现 `shots.promptEightDim`(要不要挂低危提醒的产品口径未定,不替产品定);
- 生成动作不加拦截:`js/sb-gen.js`/`js/produce.js` 里不得出现 `Skills.`;
- 发布门 G2 仍只数高/中危,口径未动;`episode.preflight` 仍是 `read` 类零计费。

变异实测:把 SK-19 的 `episode.preflight` 登记摘掉,消费点那条用例红("条目应登记已接通的就绪检查命令面")。行为不随之变(面表由 SK-18 带着 `shots` 面进表,校验项照跑)——这条断言防的正是**记账与实况脱节**:登记面说没接,实际却在跑。

## 6. 新增用例(6 条)

| 用例 | 钉住的事 |
|---|---|
| 三条稳定词写全 → `info`;只写一部分 → `stable-word-partial` | 命中码、`name`/`miss` 两个字面字段、镜号与 `shotId` |
| 一个都没写 → `no-stable-word`;模糊词逐词一条 | 三面缺失的 `miss` 串;模糊词与稳定词面各判各的 |

| 消费点 | `pending` 已清、`checks`/`cmds` 登记、面表推导含本条、零计费、不拦生成、不进问题中心、发布门口径未动 |
