> 波次归属见 `w1-architecture-spec.md` 第 3 节 W2 第 3 项与第 6.5 节。

## 1. 改动前的不一致(三处主病灶 + 四处扩散)

| # | 位置 | 词表 | 问题 |
|---|---|---|---|
| 1 | `js/wf-core.js` `W.SIZES` | 景别 6 档(大全景/全景/中景/近景/特写/超级特写) | 分镜数据的实际白名单,但只是扁平名称数组,没有"阶梯级差"这层结构可供衔接判定复用 |
| 2 | `js/camera.js` `CAM.SHOT_SIZES` | 景别 4 档(特写/近景/中景/全景) | 机位选择器少两档,用户无法在 UI 里选 LLM 已经会输出的大全景/超级特写 |
| 3 | `js/knowledge.js` 「景别运镜」正文 | 景别六级 + 运镜八式 | 正文六档齐全,但没有任何断言把它与 `SIZES` 钉在一起;`DIGESTS.review` 的摘要把"两极"写成全景↔特写,与正文的大全景↔特写自相矛盾 |
| 4 | `js/camera.js` `MOVES`/`REV_MOVE` | 运镜 9 个方向芯片 | 与 `W.CAMERAS` 十项无法一一对应:反向映射只覆盖 6 项(跟镜头/俯拍/仰拍/特写 无映射),且把「摇镜头」映射成了「↘ 升镜」;芯片值不是 `s.camera` 的合法取值,`onSave` 回传即写坏数据 |
| 5 | `js/review.js` 离线景别衔接检查 | 景别 4 档(第四份) | 大全景/超级特写不在这份阶梯上 → 用到这两档的镜头**静默跳过检查**;`gap===3` 被当成"两极",而按正文两极应是大全景↔特写(级差 4) |
| 6 | `js/sb-io.js` CSV 导入白名单 + 模板列说明 | 景别 4 档(第五份) | 导入表里写「大全景」会被静默降级为「中景」 |
| 7 | `js/agent.js` 改镜协议、`js/prompts.js` 摄像评审、`js/tools.js` 多角度 3 档 | 4 档 / 阶梯外的「远景」 | 助手被告知景别只有 4 档;`大全景/远景与特写…`「远景」不在任何枚举里,LLM 照着输出就会被规整成中景 |

第 4、5 项是真实行为缺陷,不只是措辞不齐。

## 2. 改动后的口径

单一来源放在既有双端模块 `js/wf-core.js`(不新增模块),结构表 + 名称投影两层:

```
W.SHOT_SIZES     景别阶梯 6 项 {name, dist, en}      索引即级差:相邻=1、隔一级=2、两极=4~5
W.CAMERA_MOVES   运镜 10 项 {name, axis, arrow?, short?, en?}
                 axis='move'  七项真运镜,带 arrow/short 供选择器芯片
                 axis='angle' 俯拍/仰拍 · axis='size' 特写 —— camera 枚举的早期取值,
                              与「角度」「景别」两栏语义重叠,保留在取值全集内以免动既有数据与生成指纹
W.CAMERA_ANGLES  拍摄角度 4 项 {name, deg, en}
W.CAMERAS / W.ANGLES / W.SIZES   上列三表的名称投影(取值与顺序逐字节不变)
W.VIEWS          视角 3 项(无附加列,保持字面)
W.sizeGap(a, b)  两镜景别级差:同级 0 / 相邻 1 / 隔一级 2 / 两极 4-5 / 任一端在阶梯外 -1
```

分镜数据仍只存名称(`s.camera`、`s.cameraSpec.view|angle|shotSize`),附加列(`dist`/`deg`/`arrow`/`short`/`en`)
只服务 UI 与英文摄影词拼装。景别与运镜的**情绪语义仍是知识库「景别运镜」条目的正文**,结构表不复述——
避免同一方法论出现第二份措辞(与 `w2-kb-sections-wiring.md` 的取用纪律一致)。

## 4. 生成指纹与行为等价

- **生成指纹未动**:`Domain.shotInputHash` / `buildGenerationSignature` 覆盖的字段清单与序列化一字未改;
  `s.camera` 与 `s.cameraSpec` 的取值全集、名称与顺序均逐字节不变,既有分镜的指纹与判旧结论不变。
- **拆镜提示词四栏字面等价**:`buildSBUser` 输出中四栏取值串与归一前逐字节相同,已由契约断言锁住(见第 5 节)。
- **行为变更(有意的)**,三处:① 机位选择器景别 4 → 6 档、运镜芯片改为规范名;
  ② 离线景别衔接检查六档全覆盖且两极判定改按阶梯级差;③ CSV 导入接受六档景别。
  另有五处提示词/说明文本因清除阶梯外的「远景」而少数字之差。

## 5. 验收

`node --check` 通过改动的每个 js 文件;`node tests/unit.js` 212/212;`node tests/integration.js` 79/79;
`node tests/cli.smoke.js` 51/53(2 项在前置分支合并点同样失败,与本改动无关)。

`tests/unit.js contract` 新增 6 条断言(逐条做过变异验证——把改动改回原样会红):

1. `CAMERAS/VIEWS/ANGLES/SIZES` 的取值与顺序逐项锁定,且确为三张结构表的名称投影;
   结构表附加列自洽(景别 `dist` 随阶梯单调收紧;芯片列只出现在 `axis='move'` 项;别名项确属角度或景别栏)。
2. `sizeGap` 语义:同级 0 / 相邻 1 / 隔一级 2 / 两极 4-5 / 阶梯外与空值 -1。
3. 整份词表字面只在 `js/wf-core.js`:其余 js 文件 + `server.js`/`cli.js`/`mcp.js`/`index.html` 出现
   整份数组字面或斜杠拼接串即失败;退役的 4 档景别字面与阶梯外景别词(远景/大特写/超特写/中近景)零残留。
   (三项的 `VIEWS` 只查数组字面——"正面/侧面/背面" 作为三视图行文出现在多处生图提示词里,不是词表。)
4. 四处消费方源级派生:机位选择器取结构表且 `REV_MOVE` 已消失、芯片值是规范名;
   离线衔接检查经 `sizeGap`;CSV 导入与模板取词表;改镜协议取词表。
5. 拆镜模板四栏取值字面等价(四条 `includes` 逐栏比对),且 `SPLIT_RULES`/`PROMPT5` 不含阶梯外景别词。
6. 知识库「景别运镜」正文覆盖阶梯全六档、不含阶梯外景别词(G-07 要求的"逐项对应")。

## 6. 未做(留给后续波次)

- `js/tools.js` 多角度生成器的**垂直俯仰四档**(平视/俯视/仰视/贴地(虫眼))仍是该工具自有的取景说明词,
  与 `ANGLES`(仰拍/平视/俯拍/高角度)不是同一套语义:前者是单图重绘的视角指令、后者是分镜机位字段。本轮只把
  它的景别三档收进阶梯,俯仰四档未动——要归一需先定"工具取景词 与 分镜机位字段 是否同一概念",不宜顺手改。
- `js/camera.js` `CAM.DIRECTIONS`(八方向方位角)与 `CAM.PRESETS`(九宫格机位)仍是零消费或仅取 `name`/`id` 的
  几何表,未与 `VIEWS` 合并——`VIEWS` 是三值字段、`DIRECTIONS` 是八向几何,合并会改分镜字段取值域。
- `CAM.openSpecPicker` 目前全仓无调用方(本轮把它的词表接回单源并使 `onSave` 回传合法值,但没有给它接入口);
  要么接进右栏机位编辑、要么删除,属 G-05 同类的"定性处置",不在本轮范围。
- 运镜枚举里 `axis='angle'/'size'` 的三项(俯拍/仰拍/特写)与角度、景别两栏的语义重叠**未清理**:
  清理会改 `s.camera` 取值全集与 `sb-llm` 兜底轮转(`CAMERAS[i % CAMERAS.length]`)的产出,
  从而动到新生成镜头的提示词与指纹,须单独成波并先锁指纹影响面。
