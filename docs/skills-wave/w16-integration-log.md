### 4.5 唯一一处当场判的记账问题:SK-18 的 `episode.smartReview` 登记在合流后变成假出口

**这是本轮唯一一处被测试当场按红的跨分支矛盾**,值得记全,因为它正是 `w14` 设计断言时**预期**会发生的事。

```
FAIL | skills · 审片报告消费点(源级+展示) | 审片报告漏消费已登记面:shots.sizeProgression(shots)
```

成因是两条分支各改了一半、单独看都自洽:

`w14-review-skills-check.md` 第 128–132 行早就把这个槽写明白了,连转红都预告了:

> **给 W12(景别 check / SK-18)的接线位**:落后若要进审片报告,两步——① `shotChecks` 补 `Skills.check('shots', …)`;② 条目 `cmds` 补 `episode.smartReview`。**只做②不做①会先红**(登记侧反查断言),这正是它的设计意图。

两种改法,取哪一种是本轮唯一的实质判断:

| 改法 | 内容 | 取舍 |
|---|---|---|
| ①(功能面) | 把 `Skills.check('shots', …)` 接进 `shotChecks` | **不取**。这是加消费点=加功能,超出收敛边界;且该文档同处写明景别递进是**跨镜**判定,而 `shotChecks` 的镜级入口 `{p, s}` 取不到相邻镜,"判定输入是集级还是带 `ep` 的镜级"本身还没定(「本槽不预设」);另外 `js/review.js` 的离线本地评审里已有一条基于 `WfCore.sizeGap` 的景别衔接 issue,贸然接线会出现两份判据 |

+ '(景别递进是跨镜判定,审片的镜级入口取不到相邻镜,判定输入未定),故不登记 episode.smartReview',

> 这处值得单独记一笔的地方在于:**它是被断言接住的,不是被人眼看出来的**。两条分支各自全绿、各自的文档都自洽,矛盾只在合流后存在;`w14` 那条反查断言的价值就是把"跨分支的登记与实现失配"变成一次 FAIL,而不是一份没人读的过期 `cmds` 字段。

## 5. 合并当场做完的收敛(第 5 步 `c87da63`)

### 5.1 `git checkout --ours` 连带回退了已自动合并成功的 hunk

本轮解 README 冲突时用了 `git checkout --ours README.md`(因为三处冲突全部判定"取基线"),**这一步有副作用**:它取的是整份 HEAD 版本,把同一次合并里**本已自动合并成功的非冲突 hunk 一并回退**。逐条比对两条被合分支的 README diff 后,查出四处这样被连带丢弃的增量:

| 来源 | 丢的 hunk | 补回时的处理 |
|---|---|---|
| `w12` head | 架构图 `CHECKS 已落地三条…` 段 | 不照抄分支侧的"七条",按当前实况改写为**九条**,列全五面与判定单源(`Domain` + `WfCore`) |
| `w12` head | 架构图 问题中心那两行 | 补剧本与分集方法论提醒、景别衔接(分支侧只有景别衔接) |
| `w12` head | 「机位词表单源」消费方清单 | 补 `分镜面景别衔接校验项(js/skills.js SK-18 同取 sizeGap,不另立阶梯)` |
| `w14` | 审片段「方法论校验命中(只读)」整条 | 原样补回 |

补完用一份 15 条事实的字面核对脚本逐条验过两条分支的 README 增量是否都在树上(或已被更新口径超集取代),全部命中。

> **方法性教训,给下一个集成槽**:冲突文件即使三处冲突全判"取基线",也不该用 `git checkout --ours` 整份取——它不区分"冲突块"与"这次合并本来合成功的块"。要么逐块手改,要么取完之后必须拿 `git show <branch-head> -- <file> | grep '^@@'` 把该分支的全部 hunk 位置过一遍。本轮是靠事后逐 hunk 比对捞回来的,而**没有任何测试会为 README 丢内容转红**。
