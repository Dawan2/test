# W209 停工位判定:计划层那道闸只管一个漏斗——普查下来没有第三条自动路,不成立

> 基线 `cursor/w205-integration-1816`,tip `a2e08b6`;本槽分支 `cursor/w209-plan-exec-funnel-ac34`。
> W203 / W204 / W206 / W207 / W208 在飞或已跳过,按任务口径**一条没碰**。

## 0. 结论先写

W205 残留⑤记的是一句**假设**:

> 计划层这道闸只管 `Plans.execStep` 这一个漏斗。……若日后另开一条不经 `execStep` 的执行路
> (例如服务端替用户跑计划),那条路不在本闸射程内。

按本尖 live 普查,这句里的"另一条路"**今天一条都不存在**:

- 会执行计划步的入口共 **4 个按钮、2 个文件**,全部经 `Plans.execStep` 这一个漏斗;
- headless 三端(`server.js` / `cli.js` / `mcp.js`)**连计划这个概念都没有**——零计划路由、零计划子命令、
  零计划工具、`agentPlan` 三份文件里出现 **0** 次;
- 能把命令名交给命令层的下发口共 **27** 处,其中 21 处是写死的命令名(一条都不是人手命令),
  6 处扫出来是变量、去掉一处误报后是 **5** 处,逐处的来路都查清了,除计划层漏斗与
  (任务口径排除的)导演助手之外,剩下三处要么是人手入口、要么喂它的投影面推不出人手命令。

**故停工位不成立,不新拦任何一条路**(产品码相对基线 **零 diff**)。按任务口径把这次普查**钉成判据**:
`contract` 套件新增两条,现在"再开一条能替用户跑计划步 / 发起人手命令的路"会当场红,
并要求开路的那一槽当轮回答"它经不经漏斗"。

## 2. 为什么"不成立"就该停

任务给的判据是:除 `execStep`、人手入口与(尚未合入的)agent-ops 外没有第三条自动路,就停。
逐条对上了:

- 第三条**执行计划步**的路:没有(1.1 那张表的下半截三端全是 0)。
- 第三条**发起人手命令**的自动路:没有。两个处置口是候选,但它们喂进去的名字来自数据投影,
  投影面全集里一条人手命令都没有(1.3),且用户还要逐条点按钮。

若强行"再拦一道",拦的就是一条今天不存在的路:要么在 `issues-ui`/`release` 的处置口上复制一份
`manual` 判定(那就成了第三处消费,与"两处消费同读一份字段"的现状比,多的是维护面而不是覆盖面),
要么在 `Commands.execute` 里一刀切禁人手命令(那会连四端人手入口一起封死,与产品口径相反)。
两条都不做。

## 3. 本槽真正落地的东西:把普查钉成判据

产品码一行未改(`js/` 与 `cli.js` / `mcp.js` / `server.js` 相对基线**零 diff**)。
改的是 `tests/unit.js`(+2 条 `contract` 用例)与 `README.md`(两个数字 + 计划层那段补一句)。

### 3.1 判据一:下发面普查

`contract · 人手命令的下发面普查:cmd 是变量的下发口逐处登记来路,两个处置口的投影面出不了人手命令`

四层:

1. **前提非空**:注册表里得真有人手命令,否则整条退化成恒真句(清单逐字对账仍在 W198 那条上,不重复);
2. **写死那一路**:所有字面量下发的命令名一律不许是人手命令,且必须在注册表里(打错字先红在源级);
3. **变量那一路**:按「文件 → 实参 × 处数」登记五个下发口,连**处数**一起对——
   同一文件同一写法再开一处照样红(漏斗是"那一个函数"不是"那个文件":在 `js/plans.js` 里另起一个
   绕开 `execStep` 的下发点,键不变而处数会变);
4. **投影那一路**:现取两个处置口的 cmd 全集断言无人手命令,**并先自查夹具摊得全不全**——
   live 取到的集合须恰等于两份投影源码里登记的 `cmd` 字面全集,投影新登记一条而夹具没摊开时先红在这里,
   免得第 4 层变成空扫(第 5 节 M11b 实测过这一格真会红)。

### 3.2 判据二:执行面普查

`contract · 计划步的执行面只有 Plans.execStep 一个漏斗:浏览器两处界面同走它,headless 三端零计划出口`

三层:

1. `p.agentPlan` 的读写只许出现在 `js/plans.js`(别处拿到 `steps` 就能自己逐条下发);
2. 浏览器另一处界面(制作台)必须经 `Plans.execStep` / `Plans.runAll`,且**自己不许出现 `Commands.execute(`**;
   经计划层出口跑步骤的文件按名点住(现只有 `js/workbench.js`),新开一处要在这里登记;
3. headless 三端:服务端路由表零 `plan`、CLI 命令表零 `plan`、MCP 工具表零 `plan`。
   开 `/api/wf/plan-run` 这类替用户跑计划的路会当场红,报错句直接写着"得同轮说清它经不经计划层漏斗"。

三层各带一句取数口自检(路由/命令/工具三张表点不到就先红),不许静默退化成恒真。

## 7. 残留

1. **导演助手那一路没查完,也没拦**(任务口径排除,W203 在飞)。现状是:`run` 类 op 的白名单现取
   `Commands.list()`,人手命令在内;exec 级动作在自动模式下仍要 `U.confirm`、预览卡那一路要用户按
   「应用修改」,故今天不是一条无人值守的自动路。但**自修复轮的重试**(`selfFixRound`)有一格值得后续槽看:
   它的重试白名单是"回执里失败过的命令",即某条人手命令一旦经确认跑过一次并失败,那一轮重试**不再另问一次**。
   今天 `expert.evolve` 的失败路径在扣费前就 `blocked`(不进重试白名单的失败形态),但这一格是靠
   "回执长什么样"撑着,不是靠判据撑着。
2. **本槽两条判据没有主题编号**(见 6.2):改名 / 挪套件不红、真删掉只报"少了一条用例"。
   W205 残留 3 记的那一格在本槽又多了两条同类,立不立编号的收益比上一槽更明确,仍留给后续槽判。
3. **判据封的是"路的条数",不是"路的把关质量"**:第 1.2 表里五个下发口,判据只保证"多一处会红、
   要当轮交代",不保证新开那一处真的把住了——那仍是评审要读的东西,只是从"读全仓"缩成"读表里那一行"。
4. **`cli.js` / `mcp.js` 的 `exec` 透传面照旧全开**:`hujing_exec` 与 `exec <command>` 能发任何注册命令
   包括人手命令,这是四端人手出口的一部分(用户/助手显式发起),本槽不动、也不该动。
