## 1. 结果一句话

`downloadReleaseZip` 那两处占位——打包前先 `ZipUtil.download` 一份只装 `PLACEHOLDER` 空条目的 zip、
落地失败时兜底 `ZipUtil.download` 一份只写着「请重新打包」的空壳 zip——早已删干净,
但「删干净」这件事至今**没有任何一条判据钉着**。本槽补两条,各守一面:

| # | 判据 | 守的是 |
|---|---|---|
| 1 | **源级**:`js/release.js` 的可执行行零 `ZipUtil.download`、零 `PLACEHOLDER`、零「请重新打包」/「空下载兜底」空壳文案;反面钉住真形态(落地动作全函数只此一次 `a.click()`、落的是 `buildReleaseZip` 那份 bytes、失败仍以 `throw` 收尾);`ZipUtil.download` 的调用方名单钉在 `exporter.js` 一家 | 占位换个写法、落在现有用例走不到的分支上 |
| 2 | **运行期**:桩打在 `ZipUtil.download` 函数对象上,成功 / 落地失败 / 交付弹窗打包按钮**三个入口**一次都不许叫到它;逐份落地文件按 zip 解出条目对着打包清单点,条目数 0/1 的空壳当场红 | `const Z = ZipUtil; Z.download(…)` 这类源级扫不出来的别名写法 |

数字 live:`unit` **524 → 526**(`release` 27 → 29,`contract` **114** 未动),`integration` **141** 未动;
记账件份数 170 → **171**(含本文),单元 `FLOOR` 与记账件 `FLOOR` 及两处 README 明写数一并按 live 抬。

## 2. 缺口是怎么来的

`w157-integration-log.md` 第 6.1 条把它写得很清楚,现照该文口径复核一遍(不复写它的时点读数,只核实结论今天仍成立):

  于是既不给冲突块、也不把占位加回来。这一处是**结构上守住的,不是人手守住的**;

- 最接近的既有守卫是那两条行为面用例,但它们钉的是**「用户到手几个文件」**与**「报错带不带原因」**,
  **不是「占位这个字面不许出现」**。

开工时现取核实缺口仍在(基线 `8507194`):

```
$ rg -n 'PLACEHOLDER' js/ tests/ *.js
```

**故本槽不是"字面已钉",是缺口如实还开着,开工。**

## 3. 补了什么

两条都落在 `tests/unit.js` 的 `releaseTests` 表尾,紧跟既有那三条交付 ZIP 用例。

### 3.1 源级那条

判「可执行行」用**行首形态**:整行注释(`//` / `*` / `/*` 开头)与空行豁免,其余全扫。

这么判有两个后果,都是有意的:

- **字符串里的 `//` 骗不过它**。若改用"先剥注释再扫"的写法,`'http://x'; ZipUtil.download(…)` 这类
  会被当成注释整段剥掉——过度剥离是**漏判**,比误判危险;
- **讲占位历史那几段注释原样留着**(`js/release.js` 第 369 行与第 378–380 行分别写着"再走一次
  `ZipUtil.download` 等于另打一个包"与"兜底落一个只有一句「请重新打包」的空壳"),
  它们是这处判据的由来,不该为了让扫描通过而删掉。

`PLACEHOLDER` 那格**区分大小写**:小写的 `placeholder` 是发布说明输入框的占位文案
(`js/release.js` 第 440 行 `<textarea … placeholder="本次发布说明…">`),与本条无关。
第一版写成 `/PLACEHOLDER/i` 时正是被它逮住的,这一格的口径是实测定下来的、不是先验的。

反面三条钉的是「真形态还在」,防的是"把那段整个挪走 / 改名 / 掏空后本条变恒真":

```js
const at = rel.indexOf('async function downloadReleaseZip(');
assert(at > 0, 'downloadReleaseZip 取不到(改名或挪窝就同轮改本条,别把它留成恒真)');
```

调用方名单那格与 `release.dirty` 发出点那条(W149 立的)同形:
`ZipUtil.download` 只该由素材/剪映导出那一家调,交付这条链新开一个落地口即红。

**判据只扫 `js/`。** `tests/` 里 zip 夹具的假文件名(`PLACEHOLDER`、`说明.txt` 之类)一概不管——
测试要造得出空壳才验得了「空壳当场红」,禁掉夹具等于把验证手段也一起禁了。

### 3.2 运行期那条

源级那条有一个已知盲区:别名写法。`const Z = window.ZipUtil; Z['down' + 'load'](…)` 逐行扫不出来。
故第二条把桩打在**函数对象**上(`sb.ZipUtil.download` 换成记账壳,壳里仍走真实现,
这样万一有人加回去,"到手几个文件"那一面也照样看得见),再把交付这条链的三个入口各跑一遍:

| 入口 | 装配 | 断言 |
|---|---|---|
| 成功路径直调 | `loadReleaseZip()` | 零调用、到手 1 个文件、该份的条目数等于 `r.files` |
| 落地失败路径 | `loadReleaseZip(1)`(第 1 次 `createObjectURL` 就抛) | 仍如实抛、零调用、到手 0 个文件 |
| 交付弹窗「📦 打包交付 ZIP」按钮 | `loadReleaseZip()` + `openModal` 真挂载 | 零调用、到手 1 个文件、仍报「交付包已下载」 |

「空壳」的形态判据写死成**条目数 0/1 且不含占位条目**:占位包就是这个形状,
真交付包最少也有 `project_meta.json` + `README.txt` 两条。

第三个入口有意取**成功路径**:失败路径的按钮面已由 W154 那条钉着,这里补的是它没覆盖的那一半。

## 6. 残留与欠账

1. **两个 `FLOOR` 这一轮都被基线父值蒙过去了**(5.4):单元那格 live 526 / 父值 524 / 差 2,
   记账件那格 live 171 / 父值 170 / 差 1,都压在 `SLACK` 3 之内。
   两处 README 明写数逮住了(它们判的是精确相等 + 不低于下限,不吃 `SLACK`),故整体不是漏网——
   但**「棘轮那格能不能逮住父值」逐槽都在随"本槽加了几条"漂移**,这件事本身仍没有判据管。
   W157 那槽四格压在差 4–14 上全逮住,本槽两格直接落到线内:**加测越少,棘轮那层越接近失效**,与直觉相反。
2. **源级那条对别名写法如实扫不出来**(M4,3.2 已写明)。今天由运行期那条兜着,
   而运行期那条只覆盖**三个入口**——若有人在第四个入口上用别名写法落占位,两条都逮不住。
   收紧的路子是把行扫换成真 tokenizer 或把桩下沉到模块加载期,本槽都没做:
   前者要在零依赖约束下自己写词法器,后者会让沙箱装配与生产加载序失真。
3. **「可执行行」的行首形态判法有一处已知误判方向**:代码行尾挂着的行内注释仍会被扫。
   即 `foo(); // 这里以前调 ZipUtil.download` 会红。今天 `js/release.js` 里没有这种行,
   真出现时处置是把那句注释单独成行——**这是判据强加给写法的约束,如实登记**,不是零成本。
4. **调用方名单钉在 `exporter.js` 一家,是白名单不是语义判定。** 它拦的是"多了一个调用点",
   拦不住"`exporter.js` 自己在那两处落了空壳"。素材/剪映导出那条链本槽一个字没看,
   它有没有同类问题不在本槽范围内。
5. **`integration` 侧空白**(5.1):这一面在 headless 没有对端。若将来交付包打包下沉到服务端,
   本槽这两条判据一条都不覆盖那一半。
6. **W157 残留 2–11 本槽一条未动**(零冲突块仍可能打穿既有用例、按名成集比对的两轮口径靠人工、
   `js/release.js` 底部那个空 `catch`、门槛派生的另一半、`G-03` / `G-11`、W147 那条行为余面、
   W142 残留 1、W144 行序判据、散文那半没有判据)。本槽只收 W157 残留 1。
