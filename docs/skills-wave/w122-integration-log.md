## 4. 逐处怎么解

### 4.1 明写份数与 `FLOOR`:两侧都不对,取合入后 live

W105 立的这层判据有三份记录要同时对上:目录实况、`docs/skills-wave/README.md` 明写的份数、索引表行数。
两侧各自从 `w117` 那时的 132 起算,加自己那一份:

```
我方(W119 走完):132 + w113 + w119 = 134
对侧(W120):      132 + w120        = 133
合入后目录实况:  132 + w113 + w119 + w120 = 135
```

**冲突块里两侧给的都不是答案。** 取 135,`tests/unit.js` 的 `FLOOR` 同步取 135,合并提交自身即绿(`contract` 100/100)。
本文与本文那行索引落地后目录是 **136**,明写份数与 `FLOOR` 一并抬到 **136**。分两个提交落地,**每个提交自己都是绿的**:

- `67406db` 合并提交:补两侧索引行的并集 + 明写份数与 `FLOOR` 一并取 **135**;
- 本文落地后 **136**。

**下限写成 `>=` 而不是 `==`** 的理由见 [w105-index-completeness.md](./w105-index-completeness.md) §2.1,
本槽照它交待的做法(「新开一槽记账时把下限抬到当轮实况」)把棘轮往上推。
「最新一份收敛记录」那个指针同步改成本文,`w119` 挪进"更早的分叉登记"那串的队首。

判据是「`report(...)` 的外层块链上有没有循环或迭代回调」。而阻塞 4 的实质是**"静态点数代表不了实跑条数"**,
