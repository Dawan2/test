# W101 · 记忆桶满桶时的淘汰优先级:先挤自动回流条,用户自沉淀的「记住…」留住

**范围**:`js/wf-core.js` 的 `memWrite` 满桶淘汰那一段(4 行 → 8 行)+ `js/skills.js` 的 SK-26 `note` 一句
+ `tests/unit.js` memory 套件 1 条、`tests/integration.js` 4 条 + `README.md` 三处(两个套件数 + memory 覆盖面描述)。
**基线**:`origin/cursor/w95-integration-7c2e`(`6643e12`)。**未合并 W93–W100。**
**不做**:不改 `MEM_MAX = 50` 这个数(见 2.3)、不改 `memFeedback` 的任何一支派生与 `fb` 键口径、
不改 `memRecall`/`memBlock` 召回算法、不改播种与迁移、不新建存储桶、不新增计费、不动发布门。

## 1. 改前的实况:`fb` 原地更新只挡住了「同一集反复跑」这一路

W43 立回流面时就把"别把用户偏好挤掉"写成了设计意图,落地手段是回流键 `fb` 原地更新
(同一集反复审片、同一项目反复发布只留最新一条),`js/wf-core.js` 的注释与 SK-26 的 `note` 都这么写着:

> 按回流键 fb 原地更新——同一集/同一项目反复闭环只留最新一条,不刷满 50 条上限挤掉用户自己沉淀的偏好。

原地更新压住的是**同一个键被反复写**。它压不住的是**键本身在变多**——`fb` 键的粒度里有集号:

| 键 | 粒度 | 每个项目/每集占几条 |
|---|---|---|
| `und:<epid>` / `sb:<epid>` / `review:<epid>` | 每集一条 | 每集 3 条 |
| `split:<pid>` / `extract:<pid>` / `release:<pid>` | 每项目一条 | 每项目 3 条 |

一个项目走完主线,记忆桶里的自动条数是 `3 + 3 × 集数`。桶只有 50 条,截断写法是
`out.slice(-W.MEM_MAX)`(先进先出砍头),于是:

- 第 15 集:`3 + 45 = 48` 条,还没满;
- **第 16 集:`3 + 48 = 51` 条,开始挤人**——被砍掉的是数组头部,而用户手打的「记住…」正是**最早写进去**的那批,
  排在最前面。用户越早沉淀的偏好越先出局,而且**没有任何提示**。

也就是说:回流每集稳定占 3 条这个事实,把 W43 那句"不刷满 50 条上限"的保护给绕过去了——
保护只覆盖了"同一集跑二十次",没覆盖"跑二十集"。而后者是正常使用形态,前者才是异常形态。

## 2. 产品判断

### 2.1 满桶时该淘汰谁

两类条目的**可再生性**完全不对等:

| | 自动回流条(带 `fb`) | 用户自沉淀条(「记住…」) |
|---|---|---|
| 怎么来的 | 闭环跑完自动写 | 用户手打的一句话 |
| 丢了之后 | 下一轮跑同一步就**原样重写一条**(而且更新) | **永久丢失**,用户不会知道该再说一遍 |
| 内容 | 上一轮的计数与缺口(会过期) | 用户对这部剧的口径要求(长期有效) |

结论直接:满桶时先挤最旧的自动回流条。丢一条上一轮的镜数统计,代价是下一轮少一句上下文;
丢一条「女主统一叫林晚晴」,代价是用户得重新发现自己的要求没生效。

### 2.2 三条边界

1. **本次刚写下/刚更新的条目不参与本轮淘汰。** 否则会出现自己挤掉自己:桶里 50 条全是用户条时,
   新回流进来成 51 条,"挑最旧的自动条"唯一命中的就是刚写下的那条,等于这次回流静默失效。
   实现上按对象引用记住本次落位的条目(原地更新的那条也算"刚写下"),淘汰时跳过。
2. **挑不到自动条时退回先进先出。** 空桶、桶里全是用户条这两种情形下,行为与改前一字不差
   (仍然砍头,新写入的留下)——本槽不改"满了就得丢一条"这件事,只改"丢哪一条"。
3. **原地更新不触发淘汰。** 同一集反复跑仍然是条数不变,一条也不挤。

### 2.3 为什么不动 50 这个数,也不给用户条留固定配额

- `MEM_MAX = 50` 在代码里不是可配项,且**两端写入面各写了一份同数字面**
  (`js/agent.js` 的 `mem.slice(-50)`、`cli.js` 的 `mem.concat([entry]).slice(-50)`),
  `tests/unit.js` 有源级断言钉着"三处同数"。抬这个数要同时动三处并重定那条断言,
  而且抬多少都只是把第 16 集推到第 20 集——**问题不在容量,在淘汰顺序**。
- "给用户条留 N 个固定名额"要新引一个常量、一个新口径,还要回答"用户条超过 N 条怎么办";
  按类型排优先级不需要任何新常量,也不需要回答那个问题(用户条多到装不下时自然退回先进先出)。
- "给自动条另开一个桶"直接违反既有纪律(不新建存储桶),而且召回面 `memRecall`/`memBlock`
  就是按同一个桶算的,分桶要连召回一起重做。

## 3. 落地

`js/wf-core.js` 的 `memWrite`,改动只在函数尾部的截断那一段:

```js
while (out.length > W.MEM_MAX) {
  let i = out.findIndex(m => m && m.fb && fresh.indexOf(m) < 0); // 先挑最旧的自动回流条
  if (i < 0) i = out.findIndex(m => fresh.indexOf(m) < 0);       // 没有就挑最旧的旧条(先进先出)
  out.splice(i < 0 ? 0 : i, 1);
}
return out;
```

`fresh` 是本次写入/更新落位的条目(追加与原地更新两条路都登记)。`while` 而非一次性 `splice`:
前段四步在同一次调用里可能一次写四条(`js/commands.js`/`server.js` 的四支合并回流),
要挤几条就逐条按优先级挑几次,不能按"多出 k 条就砍头 k 条"处理。

**写入侧一行未改**:六处写入点仍然是 `X.agentMemory = WfCore.memWrite(X.agentMemory, entries)`,
派生仍是同一份 `memFeedback`,双端单源与"不新增 IO"两条纪律不受影响——本槽全部改动都在那一个纯函数里。

## 4. 记账

`js/skills.js` SK-26 的 `note` 里那句"不刷满 50 条上限挤掉用户自己沉淀的偏好"**改前就已经不成立**
(它描述的是意图,而实况是第 16 集起就会挤)。现改成写清两层机制:

> 同一集/同一项目反复闭环只留最新一条。上限 50 条仍在,但集数会自己长:回流每集占三条,
> 故满桶淘汰按优先级来——先挤最旧的自动回流条(带 fb),用户自沉淀的「记住…」留住,
> 桶里没有自动条时才退回先进先出。

`pending`/`gaps`/`steps`/`prompts` 一字未动(本槽不清任何欠账、不加任何校验项、不动任何缺口标记),
故 `Skills.gaps()`、`preflightStages()`、`playbooks()`、`block()` 拼块逐字节不变。

## 7. 交接

1. **两处用户写入面仍是裸 `slice(-50)`**,本槽有意没动:`js/agent.js` 的 `memRemember` 与
   `cli.js` 的 `memory add` 各自写着一份 50 条字面,`tests/unit.js` 有源级断言钉着这两处的字面
   (`agentMemory = mem.slice(-50)` / `mem.concat([entry]).slice(-50)`)。
   **残留的洞**:桶被自动条占满时,用户**新加**一条「记住…」仍会按先进先出砍掉数组头部,
   而新策略下头部往往正是别的用户条——即"用户条挤用户条"。
   要接的做法是把这两处也改经 `WfCore.memWrite(mem, [entry])`(无 `fb` 的条目本来就走追加,
   淘汰优先级顺带一起生效,双端单源也更进一步),代价是**要重定那条源级断言的锚点**
   (它现在认的是字面,改完两端就不再有 `slice(-50)` 这个字面了),并同步 `README` 里"两端同 50 条口径"那句。
   这不是一行改动,故不塞进本槽。
2. **`fb` 有无仍是唯一分类判据**。判"是自动条还是用户条"就看 `fb` 字段,没有引入第二个标记字段。
   将来若有第三类条目(例如播种进来的知识库种子——它们带 `kb` 键、**不带 `fb`**),
   按现在的实现会被当成"用户条"受保护。这次没动它是判断:种子是幂等可补种的
   (`POST /api/wf/memory-seed` 随时能种回来),但它同时也不该比用户手打的话优先出局,
   而"排在用户条和自动条之间"要引入第三档优先级,收益不足以现在就加。要接的话,
   淘汰顺序改成 `fb` → `kb` → 其余即可,`memSeed` 侧一行不用动。
3. **淘汰是静默的**,与改前一致:桶满挤条时用户界面没有任何提示。
   记忆弹窗要做"回流条 / 用户条"的展示区分或"已达上限"的提示,`fb` 字段仍是现成判据(W61 交接第 3 条同口径)。
4. **未合并 W93–W100**。本槽叉自 `w95` 且只碰 `js/wf-core.js` 的一段、`js/skills.js` 一句 `note`、
   两个测试文件的尾部与 `README` 的两个数字。与那几支若有重叠,冲突面预计在
   `README.md` 的套件数(两侧都会是各自分支上的旧实况,正确值只能由合入后 live 实测给出)、
   `tests/*.js` 的套件尾部,以及 SK-26 那条 `note`——它若在别支上也被改过,
   要按"两层机制都写清"的口径手工合而不是二选一。
