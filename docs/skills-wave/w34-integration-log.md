## 4. 冲突怎么解(逐处)

十四处冲突全是并集型或"取更新的一侧",没有一处需要择一丢弃对侧的实质内容。解法一律是**先用 `git diff --word-diff=porcelain <merge-base> <branch> -- <file>` 把该分支对这个文件的全部增量列出来,再逐条补进基线全文**,而不是凭冲突块里看到的那点内容判断——冲突块只是分支增量的一部分,另一部分在同一次合并里已自动合并成功。本轮 `w31` 对索引文件的摘要增量、`w33` 对主 README 的一半增量都落在冲突块之外,靠这一步才捞回来。

`README.md` 的长行问题在第 3 步真的撞上了(`w33` 改了主 README 的四段,每段各是**一整行**,单行数千字,行级三方合并对它们完全无能为力)。本轮沿用 W29 那条更省事的路子:

```
# 1) 冲突块一律先取 HEAD 侧(基线是三路里的超集,冲突块内它一侧最全)
# 2) 再把对侧的增量逐句折回去 —— 增量清单来自上面那条 word-diff
```

这不是 `git checkout --ours <file>`。区别在第 2 步:`--ours` 整份取会**静默丢掉**对侧那一整行里的全部新句子;本轮对 `w33` 的十三处增量逐条折回,再逐条 `grep` 复核终态在位(`SK-20 镜头动态感准入`/`shots.motionDiscipline`/`分镜面已落地三条`/`分镜面三条 + 生成面一条`/`SK-19/SK-20 即如此接入`/`现有十五条`/`WfCore.CAMERA_MOVES` 的 move 轴/`分镜段三条:景别面按`/`抽卡稳定词面按`/`动态感准入面按`/`六面十五条` 等),十三条全部命中。

> **口径**:README 这类"一段一行"的长行文档,冲突时不要在行级硬解,更不要 `git checkout --ours <file>` 整份取(W16 第 5.1 节记过那个坑)。两条路都行:句级切分跑 `merge-file`(W25),或"取一侧 + 按 word-diff 折回对侧增量"(W29 与本轮)。后者的复核点更集中——只要 word-diff 清单逐条在终态 `grep` 得到,就没有静默丢句。
