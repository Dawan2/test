## 1. 一句话结论

**周期 4 是四个周期里唯一「能力增量压过治理增量」的一轮,也是周期 3 那份核验报告的建议被落实得最彻底的一轮**:
W21 一次性做完了周期 3 报告第 8.3 节第 1 步的全部三小步(三条 tip 收成一条,五次合并**全部取 head**),
W23 做完了第 3 步(给 README 数字加断言),而且比建议的两条多做到四条并把「删掉那句话就能绕过」的后门一起堵上。

三条 tip 并存第三次复发**。但病因这一轮被测准了,且与周期 3 不同:周期 3 是「集成槽从另一条集成线的中间点起分支」,

### 6.1 一处本轮新发现的记账口径不一致:落地后 `gaps` 标记摘不摘

`gaps()` 的实现是 `REG.forEach(s => s.gaps.forEach(...))`——**它投影条目声明的 `gaps` 字段,不看 `pending`**。
于是「某条落地后要不要把对应缺口编号从条目上摘掉」是个人工口径,**周期 4 的四波给了两种答案**:

| 波次 | 清掉的面 | `gaps` 标记处置 | 实测 |
|---|---|---|---|
| **W22** | SK-11 check | **摘掉** `G-06`(SK-11 与 SK-13 两条都摘) | `gaps()` 键 22 → 21 |
| **W27** | SK-10 inject | **摘掉** `S-02` | `gaps()` 键 22 → 21 |
| **W26** | SK-19 check | **保留** `G-15`/`G-05`/`G-10` | 键数不变 |
| **W28** | SK-22 check | **保留** `S-05` | 键数不变 |

后果可测:`w29` 新 head 上 `gaps()` 的 20 个键里,**12 个键关联的条目已经一条 pending 都没有了**
(G-04、G-05、G-07、G-08、G-09、G-13、G-14、G-15、S-01、S-03、S-05、S-06),
只有 8 个是真正未闭的;而 G-06 与 S-02 因为标记被摘掉,**在投影里连键都不出现了**。
即**同一张 `gaps()` 表里,已闭缺口有两种表现:一种留着键、一种键都没了**,取决于当时那一波选了哪种做法。
两种口径各自都有道理(摘掉 = 投影只列未闭缺口;保留 = 投影记该能力关联过哪个缺口),
**但两种同时存在会让 `gaps()` 既不能当「未闭清单」也不能当「关联索引」用**——
要拿它当未闭清单,得再按 `pending` 过滤一遍(第 6 节那张表就是这么算出来的);

这与周期 2 报告查到的 SK-03/SK-04 `note` 不一致是同一类问题,**建议按同一办法处置:定一种,补一条契约断言钉住**。
