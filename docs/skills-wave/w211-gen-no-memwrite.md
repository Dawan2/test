## 1. 停工位怎么判的:先在基线上 live 举证,再决定动不动手

任务给的停工位是「SK-04 仍挂:生成/合成记忆写回被否决」,并明写了一条自毁条件——
**若生成路径已经零写回,停工位不成立,停手**。本槽先把这一条查实,查的结果是:**不成立**。

下面三小节是三问的逐条回答,全部现取 W205 基线的实况,不引任何历史记账件的结论。

### 1.1 三条成功路径调不调 `memWrite`/`memFeedback`?一处也没有

两端六个函数体逐个读完,再各切一段源码作反证。切段的口径与用例里那条一致(见第 3 节),
「可执行行」= 去掉空行与整行注释后剩下的行:

| 端 | 函数体 | 位置 | 可执行行 | `memWrite` | `memFeedback` | `agentMemory` |
|---|---|---|---|---|---|---|
| 浏览器 | `reg('episode.generateVideos'` | `js/commands.js:99` | 38 | 0 | 0 | 0 |
| 浏览器 | `reg('episode.compose'` | `js/commands.js:181` | 14 | 0 | 0 | 0 |
| 浏览器 | `reg('subject.generateImage'` | `js/commands.js:227` | 23 | 0 | 0 | 0 |
| CLI | `EXEC['episode.generateVideos']` | `cli.js:1029` | 49 | 0 | 0 | 0 |
| CLI | `EXEC['episode.compose']` | `cli.js:1108` | 7 | 0 | 0 | 0 |
| CLI | `EXEC['subject.generateImage']` | `cli.js:1277` | 32 | 0 | 0 | 0 |
| CLI | `composeCore(pid, epid, f)` | `cli.js:917` | 31 | 0 | 0 | 0 |

`EXEC['episode.compose']` 只是前置闸的壳(无分镜 / 失败镜两道),真正的写回口径在 `composeCore` 里
(`composed` / `composedAt` / `composedUrl` / `composedSrt` / `composedInputHash` / `composedDialogueSig` /
`composedSourceRev` / `composedGraphRev` / `composedAudio` 九个字段),故第七行单列——**只判那个壳会漏掉半条路**。

CLI 三段的收尾取各自的 `\n} };` 而不取下一条 `\nEXEC[`:`EXEC['episode.compose']` 与下一条 `EXEC` 之间
还夹着 produce 的两个修订辅助函数(`reviseTargets` / `reviseLowShots`),按 `EXEC` 切会把它们一并圈进来
(实测 7 行会变成 63 行),判的就不是这一步自己了。

**CLI 这一端还有一处只读源码看不出来的门**:`withProject(pid, flags, fn, memFeed)` 的**第四位**才是回流通道
(`cli.js:157` 那句 `meta.agentMemory = WfCore.memWrite(...)` 只在 `memFeed` 回出非空条目时才发生)。
全仓传第四位的只有 `cli.js:1349` 的 `project.extractSubjects` 一处;生成三步的 `withProject` 调用**一律只传三位**。
所以 CLI 侧的零写回不是"忘了写",是**根本没接那根管子**。

### 1.2 引擎层往下再看一层:连"读"都没有

命令层干净不等于底下干净——三步各自委托的引擎才是真正落盘的地方。一并查完:

| 引擎 | 位置 | 写记忆桶 | 读记忆桶(`memBlock` 召回) |
|---|---|---|---|
| `SBGen.batchGenVideos` / `createShotVideo` | `js/sb-gen.js` | 无 | 无 |
| `SB.composeVideo` / `doCompose` | `js/sb-io.js` | 无 | 无 |
| `EpisodeUtil.genSubjectImage` | `js/proj-upload.js:119` | 无 | 无 |
| `Media.ffCompose` | `js/media.js` | 无 | 无 |

全仓 `memBlock` 的消费点共 **20** 处,分布在 `server.js`(8)、`js/agent.js`(3)、`js/agent-global.js`(2)、
`js/review.js`(2)、`js/sb-llm.js`(2)、`js/episode-util.js`(2)、`js/understanding.js`(1)——
`js/episode-util.js` 那两处是 `llmExtractSubjects`(主体板块)与 `llmSplitEpisodes`(剧本板块),
都是**有自己提示词的 LLM 步**,不是生图/生视频/合成。

这一格比"没写"更有说服力:**主体生图这一步连召回都没有**。
写下去没人读,不是推断出来的,是这一层直接量到的。

### 1.3 审片是不是唯一自动写记忆的路径?**不是,合法的有六条,审片是其中之一**

任务第 2 问的措辞需要如实纠正一格:自动写记忆的合法路径**不止审片一条**,而是主线**六个闭环**。
全仓写入点普查(`memFeedback` 派生 → `memWrite` 落桶):

| 闭环 | 板块 | 浏览器写入点 | 服务端写入点 | CLI 写入点 |
|---|---|---|---|---|
| 本集理解 | 导演 | `js/understanding.js:53` | `server.js:3383`、`3436`(分镜端点内那次理解步) | — |
| 智能分镜 | 分镜 | `js/sb-llm.js:71` | `server.js:3501` | — |
| 剧本拆集 | 剧本 | `js/proj-upload.js:304` | `server.js:3349` | — |
| 提取主体 | 主体 | `js/commands.js:299` | — | `cli.js:1349`(经 `withProject` 第四位) |
| **整集审片** | 成片 | `js/review.js:603` | `server.js:3619` | — |
| 发布留痕 | 成片 | `js/release.js:269` | `server.js:3688` | — |

另有两处**用户写入面**(不是自动回流):浏览器 `js/agent.js:123` 的「记住…」、CLI `cli.js:1532` 的 `memory add`。
两处都经同一个 `memWrite`(满桶淘汰优先级因此一并生效),但都由用户显式发起。

生成三步在这张表上**一格也没有**。所以准确的说法是:
**自动写记忆的是主线六个闭环,审片是其中合法的一条;生成/主体生图/合成不在其中,且基线上本来就不在。**

### 1.4 结论

三问答完:**没有静默写记忆可删,停工位不成立,产品码不动。**

但"不成立"不等于本槽无事可做——恰恰相反,这种"实况已经对了、只是没人钉住"的格子是最容易被下一个人
当缺陷补上的:六步都回流了就差这两步,覆盖面看着不整齐。所以本槽把这条结论**从散文变成判据**(第 3 节),
并把翻面的条件一起钉进用例的失败信息里。

## 2. 为什么零写回是对的(结论的理由,不是本槽新做的判断)

理由已有定论,此处只复述落点,便于读到失败信息的人当场判断该不该改:

1. **这三步没有自己的、会按板块召回记忆的提示词。** `WfCore.WF_BOARD` 只有五个键
   (`understanding: 导演` / `smart-storyboard: 分镜` / `smart-review: 成片` / `extract-subjects: 主体` / `split-episodes: 剧本`),
   既没有生成也没有合成。「回流下去的结论,下一轮同一步按 `memBlock` 就吃得到」这条**结构保证**在这三步上不成立
   ——合成是零 LLM 步,生成用的是分镜步产出的 `s.prompt`,主体生图连召回都没有(第 1.2 节)。
2. **唯一的旁路已经在同一份提示词里给了实时的同一批数字。** `生成`/`成片` 板块的记忆只有 Agent 对话会召回,
   而同一份提示词的 user 半本来就带一段实时状态摘要(浏览器 `AO.stateBlock`、headless `WfCore.agentStateText`),
   `共10镜/6已出片/2失败/2未生成/2待确认` 这一行**包含了回流那一行的全部内容**且是 live 现算的。
   回流条目是跑批那一刻的快照:用户重抽修好两个失败镜之后,实时行变 `8已出片`,快照行仍写着 `失败 2 镜`——
   两行并排出现在同一份提示词里,只能让模型在互相矛盾的两个数之间挑一个。
3. **失败与素材产出这一面另有三处实时判定**:问题中心 `js/issues.js` 的 `failed-shots`(high 危,逐镜带原因 + 一键重试)、
   发布门 G4 过期镜 / G5 未确认镜 / G6 失败镜、以及主线流程模板把 `failed-shots` 列为断点码。
4. **合成这一步的结论已经有一整圈现成读者**:`composed*` 九个字段是它自己的结构化回执,
   `Domain.epComposedReady` 判旧、`Domain.workflow` 的 `film` 步、问题中心 `composed-stale`、发布门 G1、成片库与版本对比都在读。
   往记忆桶再抄一份不多一个读者,只多一份**会过期的副本**(成片判旧后 `epComposedReady` 翻 `false`,记忆里那句"已落盘"不会跟着翻)。

**翻面判据只有一条**:生成或合成长出了自己的、会按板块召回记忆的提示词步(那会是一个新的 wf 端点 + 一个新的 `WF_BOARD` 键)。
第 3 节最后那句断言就钉在这个条件上——`WF_BOARD` 里一旦出现生成/合成键,用例当场红并把这句话摆到失败信息里,
逼下一个人重判一次,而不是让判据静默变成恒真。

## 3. 把判据钉下来:两条用例,落在 `memory` 套件

两条都紧跟既有的 `前段四步行为面(浏览器真跑)…` 之后(同为记忆写入面)。

### 3.1 行为面(浏览器真跑)

**`生成三步不写记忆桶(浏览器真跑):批量生成/主体生图/合成成功收尾后 agentMemory 一字未动`**

| 断言 | 钉住的事 |
|---|---|
| 桶先播两条(用户「记住…」+ 一条审片回流) | 空桶下「没写」与「写了但被判空」分不开,得让桶里有东西可比 |
| `g.result.ok === 2` / `im.result.ok === 1` / `ep.composed === true` | **先自证真跑到了成功收尾**——没跑到成功档,后面那句"没变"就是恒真 |
| 三步各跑完一次,`JSON.stringify(agentMemory)` 逐字节等于跑之前 | 主判据:三条成功路径都不写记忆桶 |
| 收尾:同一沙箱同一只桶上手工走一次审片回流,桶长度 2 → 3 且 `fb === 'review:ep2'` | **反面自证**——合法那条路径照写得进去,否则前面三句"没变"可能只是这个沙箱根本写不动记忆 |

最后那条反证是本用例的要害。只断言"没变"的用例,在沙箱缺 `WfCore`、缺 `Store.now`、或整个记忆桶被换成只读对象时
一样会绿,而那时候它什么也没在测。

### 3.2 源级双端 + 分支面

**`生成三步不写记忆桶(源级双端 + 分支面):六个函数体零 memWrite,自动回流仍只有主线六个闭环`**

行为面只够到浏览器一端:CLI 那一端的 `withProject` 在单测夹具里就被桩掉了(`sb.withProject` 只接三位、
第四位 `memFeed` 直接丢弃),写没写在那边**观测不到**。故 CLI 侧在此源级点名,两端一起判——一端补上了另一端没补也红。

| 断言 | 钉住的事 |
|---|---|
| 七段各自的 head 找得到 | **防恒真**:函数挪窝或改名时红在"找不到",不是静默跳过 |
| 七段各自可执行行数 ≥ 各自下限(30/18/10/40/25/6/24,实测 38/23/14/49/32/7/31) | **防恒真**:整段被判成注释时切出来的是空字符串,那时"零 `memWrite`"恒真 |
| 七段可执行行里零 `memWrite` / `memFeedback` / `agentMemory` / `闭环回流·` | 主判据,失败信息里直接写明该往哪看(现取 `Domain.episodeState`;处置走 `failed-shots` 与 G4/G5/G6) |
| `memFeedback` 六支入参全给齐,产出的 `fb` 前缀恰是 `extract,release,review,sb,split,und` | **分支面**:零回流是派生层的事实,不是调用方漏接;顺带钉住"审片只是六条里的一条" |
| `WF_BOARD` 的键与值里都没有 `生成`/`合成`/`generate`/`compose` | **翻面判据**:结构理由回实现核对;这两步长出召回面时本条红,提醒重判一次而不是让上面那些断言静默恒真 |

第四条把 `composeCore` 单列进七段(而不是只判 `EXEC['episode.compose']` 那个壳),
是因为 CLI 合成的九个写回字段全在 `composeCore` 里——只判壳,往 `composeCore` 里插一句就漏过去了(第 4 节 M4 实测)。

## 7. 交接

1. **别把零回流当缺陷补上。** 读到 3.2 节那条用例的失败信息时,先回第 2 节看四条理由,
   再看第 1.2 节那张表——**主体生图这一步连 `memBlock` 召回都没有**,写下去连一个潜在读者都指不出来。
2. **要翻面,先长出提示词步。** 判据不在"数字够不够硬"(`ok`/`total`/`failed[]` 都是已落盘的结构化字段,足够硬),
   在"这一步有没有自己的、会按板块召回记忆的提示词"。两个可能的触发点:生成侧长出"按上一轮出片结果改写生成参数"的 LLM 步;
   合成侧长出剪辑决策 LLM 步。那时该回流的多半也不是"成功 N 失败 M"这个总数,而是失败与提示词特征的对应关系。
   翻面时 M5 那格会红,那是提醒不是障碍——同轮把 3.2 节那条断言改掉即可,但**要在记账里写明为什么翻**。
3. **改 CLI 生成三步时留意 `withProject` 的第四位。** 那是 CLI 侧唯一的回流通道,只传三位就是零写回;
   源级那条用例判的是段内零 `memWrite`/`memFeedback`/`agentMemory`,所以接上第四位时它会红(M3 实测)。
4. **合成的写回口径在 `composeCore` 不在 `EXEC` 壳里。** 任何针对 CLI 合成的判据都得单列那一段,否则漏半条路(M4 实测)。
5. **记忆桶上限那处问题优先于任何"再补一步回流"。** `memWrite` 满桶淘汰已按优先级来(先挤最旧的自动回流条、
   用户自沉淀留到最后),但回流面每集仍占三个键(`und`/`sb`/`review`),集数一多键就多。
   要接 SK-26 的下一个槽应先看这一处。
