## 2. 独立键,键名取 `dist`

```js
{
  /* 剧壳发行文案包那步:只收人设句,其后按键接的 KB 钩子六型+付费卡点仍由取值口现拼(方法论正文不随覆盖变动),
   * 六字段返回 JSON 契约仍留在 user 半、不开放覆盖(改坏即整轮解析失败,六个输入框一个都填不上) */
  key: 'dist.copySystem', name: '发行文案包 · 系统人设', vars: [],
  def: '你是短剧发行运营专家,精通平台投稿与投流文案。',
},
```

- **独立键而不复用**:按 W56 立的复用判据(字面同 / 角色同 / 产物落点同)对既有 19 条**一条都不成立**——角色是**发行运营**(平台投稿与投流),产物落在 `p.shell.dist` 的六个发行字段(卖点 / 长短简介 / 话题 / 定档 / 投流文案),既有那些人设是编剧、导演、分镜师、审片、提示词专家、智能体六族,离得最近的 `review.finalSystem`(剪辑审片总监)与它连板块都不同。用例正查这一条:注册表里**没有第二条 `def` 是这句话**,且逐条比过"发行人设不得与既有键同字面"。
- **键名取 `dist` 而不是 `shell`/`projShell`**:前缀取**步名/领域**是注册表既有惯例(`split` / `extract` / `persona` / `review` / `agent`),不取文件名(`proj-shell` 只是它碰巧住的文件,与 W71 不取 `episodes.*` 同理);数据落点本身就是 `p.shell.dist`,页面上「剧壳」是 tab 名而「发行」是这一步真正的领域,所以 `dist.copySystem`(发行 · 文案包 system 半)。
- **后缀取 `copySystem` 而不是 `system`**:这一步的产物是**文案包**(六字段一次出),`dist.system` 读起来像"发行这一整块的人设",而剧壳页往后若再长出别的发行类 LLM 步(如平台投稿合规改写),`dist.copySystem` 才留得下并列的位置。同族先例是 `persona.promptSystem` / `gen.promptSystem`。
- **`vars` 为空**:这一步不做变量替换,user 半由取值口现拼。

**注册顺序按产品流程**:排在 `review.finalSystem` 之后、`agent.*` 那四条之前——发行是成片审片之后的收尾环节,注册表顺序就是「偏好学习 → 全局默认值 → 核心提示词 skill」页面上的排列。两条断言钉住(紧接成片审片之后 + 在 Agent 那几条之前),免得后续槽随手插到别处静默改掉页面排列。

## 3. 收编面到加号为止:KB 摘要尾与 JSON 契约都不进覆盖面

这一步的 system 半是**两段拼的**,收编只收前一段:

| 段 | 处置 | 为什么 |
|---|---|---|
| 人设句 `你是短剧发行运营专家,…` | **进注册表**,用户在「全局默认值」页改得到 | 措辞好坏属人设面,改坏只是"效果差一点" |
| `KB.pick('钩子六型', '付费卡点')` | **留在取值口现拼**,不随人设覆盖变动 | 方法论正文的唯一来源是 `KB.SECTIONS`(条目改写两处一并跟随);做成覆盖面等于允许用户在提示词里存一份 KB 副本,那是 W2 收 KB 单源时明确否掉的 |
| user 半的六字段返回 JSON 契约 | **留在 user 半,不开放覆盖** | 用户把 `logline`/`introLong`/`introShort`/`topics`/`announce`/`promo` 任一字段名改一个字,那一轮就是"六个输入框一个都填不上"整轮失败,而不是效果差一点 |

**"契约半不开放"是正查的**:注册表里不得出现那六个字段名(六条断言逐个点名)。KB 尾那一段则由行为面 + 源级两面各钉一次——行为面断言 `Prompts.get(键, 覆盖) + tail` 里 `tail` 逐字节不变、且 `tail` 恰好是那两条 KB 条目正文按序拼接(条目改名导致取值口静默少半截也拦得住);源级断言取值口的拼法逐字节还在。

## 4. 取值口:纯浏览器链路,不存在第二端

剧壳页 → `API.chatJSON`,`server.js` / `cli.js` 里没有对端(发行文案包不在 `/api/wf/*` 六个端点里,也不在领域命令注册表里)。所以与 W71 那四条同口径:

- 取值口只有 `Prompts.get('dist.copySystem')` 一处,浏览器隐式读 `Store.state.settings.promptOverrides`。
- 断言写成**不许长出第二端**:`server.js` / `cli.js` 里不得出现这一步的 user 半锚点(`为以下短剧写发行文案包`)。
- 收编解决的是"**可覆盖**",不解决"可 headless"——如实写进 README、SK-03 的 `note` 与本件,不含糊成"这一步已双端单源"。

行为面**没有沙箱真跑那一层**:`bindShellEp` 的 handler 挂在 DOM 按钮闭包里(`window.ProjTabs.shell.bind` 要真 DOM 与 `styleOf` 等 `episodes.js` 闭包外的全局),与 W71 同形。能钉的两件事——缺省逐字节 + 覆盖只换人设句——落在注册表取值行为上,取值口落在哪一步由源级配对正则锚住(`system: Prompts.get('dist.copySystem')` 后 600 字内出现该步 user 半锚点),两条合起来覆盖的面与"真跑一遍截获 system"等价。

## 6. 全仓持有者名单:从"每槽各写一次扫描"改成一条按注册表现推

W69 / W71 各自在自己的源级用例里写了一份局部扫描(W69 扫那一句、W71 扫那四句)。本槽**新立一条独立用例**把它收成全仓一份:

```js
{ name: '注册表提示词全仓持有者名单:每条 def 的字面持有者逐键点名,恰好只有 js/prompts.js', fn() { … } }
```

- **名单口径**:四端入口(`server.js` / `cli.js` / `mcp.js` / `index.html`)+ `js/` 下全部 `.js`,按 `Prompts.list()` **逐键**扫一遍,每条 `def` 的字面持有者须**恰好只有** `js/prompts.js`。
- **为什么不改写 W69 / W71 那两条**:那两条各自还钉着自己那一槽的配对关系与记账锚点,拆开会连带改掉不属于本槽的断言;两份并存不冲突(本槽这条是它们的超集,超集红时子集也红,不会互相掩盖)。
- **收成一条的实际好处**:名单随注册表现推,**新增键自动进名单**——下一槽收编第 21 处时不必再写第三份扫描,漏写也不会留下"这一键没人查"的空档。基线 19 条与本槽 20 条实测持有者都是 `js/prompts.js` 一份,所以这条一立即绿,不是靠放宽口径换来的。
- **`tests/` 目录有意不进名单**:用例里那些期望串本身就是字面(与 W69 / W71 同口径),扫进去等于自己红自己。
